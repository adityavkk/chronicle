  <ul>
    <li><strong>A write crosses five files and is decided once.</strong> <code>ServeHTTP</code> routes <code>POST</code> to <code>handleAppend</code>, the backend snapshots the tail and sends one <code>EVALSHA</code>, and <code>append.lua</code> commits or returns <code>RETRY</code> if the live tail moved.</li>

  </ul>

<section class="block" id="append">
  <SectionHead num="01" label="POST" title="A write <em>lands</em>" />

  A `POST` carries a JSON batch to a stream that already exists. The path crosses
  five files. The HTTP handler parses and delegates, the backend snapshots the
  tail and sends one Lua call, the script validates and writes, and the handler
  answers. The diagram below shows the call order. The steps after it show the
  source lines.

  <Diagram name="seq-trace-append" label="Append · call stack" caption="The optimistic-concurrency loop is the part to watch. The backend snapshots the tail before framing, and <code>append.lua</code> rejects the write with <code>RETRY</code> if the live tail has moved. The Go caller then re-snapshots and retries, up to 64 times." />

  <Step n="1" fn="Handler.ServeHTTP" loc="handler.go:212" role="The method switch routes POST to handleAppend. Every verb takes this same switch.">

```go title="handler.go" showLineNumbers startLineNumber=212
	case http.MethodPost:
		err = h.handleAppend(w, r, streamPath)
```

Before control reaches the switch, `ServeHTTP` has set CORS and security
headers, answered any `OPTIONS` preflight, and ruled out the reserved `__ds`
namespace. This switch is the whole router.

  </Step>

  <Step n="2" fn="Handler.handleAppend" loc="handler.go:823" role="Buffer the body, authorize before existence, load stream metadata, parse producer and closure headers, then repeat the live write fence immediately before the store call.">

```go title="handler.go" showLineNumbers startLineNumber=827
	body, err := io.ReadAll(r.Body)
	if err != nil {
		return newHTTPError(http.StatusBadRequest, "failed to read body")
	}
	if err := h.authorizeAppendCredential(r, path); err != nil {
		return err
	}
	meta, err := h.Store.Get(path)
```

The credential preflight runs before stream storage, so an invalid caller
cannot probe existence. The handler then parses `Producer-Id`, `Producer-Epoch`,
`Producer-Seq`, and `Stream-Closed`, verifies the `Content-Type`, and builds
`AppendOptions`. It repeats the live write-token fence immediately before
`h.Store.Append`. The store and script decide ordering and idempotency.

  </Step>

  <Step n="3" fn="redis.Store.Append" loc="store/redis/store.go:533" role="The backend snapshots the tail with HMGET, frames the batch against it, and sends everything to one EVALSHA.">

```go title="store/redis/store.go" showLineNumbers startLineNumber=584
args := append([]any{
	s.nowNsArg(), notifyChannel(path), reqCT, opts.Seq, closeArg,
	hasProd, pid, epochArg, seqArg,
	base.String(), newTail.String(), valOnly,
}, frames...)
raw, err := appendScript.Run(ctx, s.client, keysFor(path), args...).Result()
```

`base.String()` is the snapshot tail. The script checks that the live tail still
matches this value before it commits. `newTail.String()` is where the tail moves
if this write wins. `frames` are the `endOffset|bytes` members to add. `Run` is
`EVALSHA`, and it reloads the script on a `NOSCRIPT` miss. A `RETRY` reply sends
the caller back to re-snapshot and re-run.

  </Step>

  <Step n="4" fn="append.lua commit" loc="store/redis/scripts/append.lua:95" role="Every check has passed and the snapshot tail still matches. The script writes atomically, because the whole script runs as one Redis step.">

```lua title="store/redis/scripts/append.lua" showLineNumbers startLineNumber=95
-- 11. Write frames (chunked: unpack is C-stack bounded) and commit metadata.
if #ARGV >= 13 then
  local i = 13
  while i <= #ARGV do
    local stop = math.min(i + 999, #ARGV)
    local zargs = { 'ZADD', KEYS[2] }
    for j = i, stop do
      zargs[#zargs + 1] = '0'
      zargs[#zargs + 1] = ARGV[j]
    end
    redis.call(unpack(zargs))
    i = stop + 1
  end
  redis.call('HSET', KEYS[1], 'tail', new_tail)
end
```

Every frame goes into the `msg` sorted set at score `0`. The ordering comes from
the offset prefix of each member, so `ZRANGEBYLEX` reads them back in sequence.
Then the tail advances. Just below this, the script records producer state into
the `prod` hash and runs `PUBLISH channel 'a'`. That publish is the wakeup the
[read walkthrough](#read) is waiting on. The script then returns `OK` with the
new tail.

  </Step>

  <Complexity
    time="O(k log N) for a k-frame batch · multiplied by retries under contention"
    space="O(b) for a b-byte batch"
    why="Each frame is one <code>ZADD</code> into a <code>msg</code> sorted set of size N, chunked at 1,000 members because Lua's <code>unpack</code> is C-stack bounded. A concurrent append on the same stream can force the complete snapshot, framing, and script attempt to repeat, up to 64 times."
  />

  <Aside label="Edge case" summary="Why the <code>ZADD</code> is chunked and the retry caps at 64">
    The `ZADD` writes at most 1,000 members per call because Lua's `unpack` is
    bounded by the C stack, so a larger batch is split across calls inside the one
    script. On the Go side, a `RETRY` reply means the live tail moved between the
    snapshot and the commit, so the caller re-snapshots and re-runs, up to
    `maxAppendRetries` (64) times before giving up.
  </Aside>

  <Step n="5" fn="Handler.handleAppend respond" loc="handler.go:1036" role="Set response headers, skip the hook for a producer duplicate, enqueue one dirty path for a new append, then choose the status.">

```go title="handler.go" showLineNumbers startLineNumber=1036
w.Header().Set(protocol.HeaderStreamNextOffset, result.Offset.String())
if result.ProducerResult == store.ProducerResultDuplicate {
	w.WriteHeader(http.StatusNoContent)
	return nil
}
h.onStreamAppend(path)
h.observeAppendSubscriptionHook(appendReturnedAt)
```

`onStreamAppend` makes one bounded process-local queue transition. The
[wake walkthrough](#wake) starts exactly here, while the Manager-owned worker
runs fanout later. A producer append answers `200 OK`. A plain append answers
`204 No Content`. Both carry `Stream-Next-Offset`, the one string a client stores
and passes back as `?offset=` to resume. A producer duplicate returns before the
hook because it wrote no new data.

  </Step>

  Five files, one durable write. The core makes the decisions and the script
  enforces them. The one weak point on this path is concurrency. Several in-flight
  appends on the <em>same</em> stream collide on the `RETRY` loop, and past
  roughly 1,000/s in aggregate the retries run out and useful throughput drops to
  near zero.[^perf] One in-flight append per stream sustains far more.
</section>

<section class="block" id="read">
  <SectionHead num="02" label="GET live=long-poll" title="A reader <em>tails</em>" />

  A `GET` with `offset=now&live=long-poll` means the caller is at the tail and
  wants the <em>next</em> write. Chronicle first confirms a notification
  registration, then captures one atomic root page. The page is authoritative
  for everything Redis ordered before it, and the registration covers
  everything ordered after it. The same tail-follow request has two live modes,
  and only the `live=` value changes.

  <Step n="1" fn="Handler.handleRead authorize and parse" loc="handler.go:445" role="Authorize before existence, then resolve the offset, cursor, live mode, optional limit, envelope, and response framing.">

```go title="handler.go" showLineNumbers startLineNumber=453

	if err != nil {
		return err
	}

	offset, err := store.ParseOffset(offsetStr)

	liveMode := query.Get("live")
```

`ParseOffset` maps `now` to a value that means the current tail, and `-1` to the
start. Any other value parses as `readseq_byteoffset`. `cursor` prevents a CDN
from serving one stale tail response in a loop. The handler authorizes before
the storage lookup so a rejected caller cannot learn whether the path exists.

  </Step>

  <Step n="2" fn="Handler.subscribeNotifications" loc="handler.go:533" role="For offset=now, confirm one notification registration before the authoritative first page.">

```go title="handler.go" showLineNumbers startLineNumber=533

		liveSubscription, _, err = h.subscribeNotifications(r.Context(), path)

		}

```

The Redis implementation waits for the `SUBSCRIBE` acknowledgement before it
returns the registration. The handler owns and closes it unless ownership moves
to an SSE hub. Numeric long-poll offsets keep the older first-page, subscribe,
and no-touch recheck sequence because they may already have historical data.

  </Step>

  <Step n="3" fn="redis.Store.ReadPage and read.lua" loc="store/redis/store.go:670" role="Capture one typed response snapshot. The same atomic script classifies the root range and returns any root-owned bounded frames.">

```go title="store/redis/store.go" showLineNumbers startLineNumber=683

		ctx, path, offset, store.ZeroOffset,

		got := "segment"

			"read.lua: root range decision %q disagrees with Go oracle %q",
			got, wantRootRange,
		)

```

`read.lua` loads metadata once and captures the tail, content type, closure,
expiry configuration, fork boundary, and incarnation. It mirrors the pure Go
classification as empty, inherited, or root-owned. An `offset=now` page is
empty and does not read the message set. A root-owned page fetches one candidate
and an optional byte-bounded range in the same script. An inherited fork prefix
keeps its later source-slot traversal. Producer state never crosses this read
boundary.

The first page renews access only for a sliding TTL. Persistent and absolute
expiry streams perform no write. Continuations, wake rechecks, inherited fork
ranges, sealing, and repair are no-touch.

  </Step>

  <Complexity
    time="O(log N + M) for one storage page"
    space="O(M) for one bounded page"
    why="<code>ZRANGEBYLEX</code> seeks the lower bound in <code>O(log N)</code>. It fetches one candidate, then optionally visits only end offsets inside the remaining byte budget, with at most 1,024 frames in the page. The handler writes each accepted page to the socket and flushes it before asking storage for the next page."
  />

  <Step n="4" fn="Handler.waitForRegisteredPage" loc="handler_stream.go:349" role="Block on the confirmed registration. Every notification, safety poll, or timeout ends with a fresh no-touch durable page.">

```go title="handler_stream.go" showLineNumbers startLineNumber=359

		recheckOpts := opts
		recheckOpts.Snapshot = nil
		recheckOpts.NoTouch = true
		page, err := reader.ReadPage(ctx, path, offset, recheckOpts)
		if err != nil {
			return store.ReadPage{}, false, err
		}

			return store.ReadPage{}, false, store.ErrReadSnapshotChanged

		return page, done, nil
	}
```

There is no immediate attach recheck for `offset=now`. Let `R` be the first
atomic page. An append before `R` is in its captured tail. An append after `R`
is covered by the confirmed registration. Redis orders the boundary race on
one side or the other. The one-second poll recovers a lost Pub/Sub hint. The
incarnation and content type check reject a delete and recreation.

  </Step>

  <Step n="5" fn="Handler.handleRead response" loc="handler.go:720" role="Use the final typed page for status, cursor, closure, next offset, cache policy, and body. Do not reload metadata or producer state.">

```go title="handler.go" showLineNumbers startLineNumber=721

	closedAtTail := firstPage.Snapshot.Closed &&
		effectiveOffset.Equal(firstPage.Snapshot.Tail) &&
		len(firstPage.Messages) == 0
	if waited.TimedOut || closedAtTail {
		w.Header().Set("Content-Type", firstPage.Snapshot.ContentType)
		w.Header().Set(protocol.HeaderStreamNextOffset, firstPage.Snapshot.Tail.String())
		w.Header().Set(protocol.HeaderStreamUpToDate, "true")

			protocol.GenerateResponseCursor(cursor, time.Now()))
		w.WriteHeader(http.StatusNoContent)
```

On an append, the same final page supplies the `200` body and its exact next
offset. On timeout or EOF, it supplies the `204` headers. A credentialed read
uses `Cache-Control: private`. An uncredentialed historical response keeps its
ETag and public cache policy. JSON envelopes, binary bytes, closure, and cursors
use the same framing code as a plain catch-up read.

  </Step>

  When [walkthrough one](#append) runs `PUBLISH channel 'a'`, the registration
  wakes. `waitForRegisteredPage` reads the durable frames, and the handler
  answers `200` from that page. If no data arrives, the timeout path still reads
  one final page before it answers `204 No Content`.

  <Callout icon="info" label="One known cost">
    Each blocked long-poll owns one notification registration. It also performs
    a no-touch durable read after each one-second safety interval. The
    registration removes a duplicate attach read for `offset=now`; it does not
    share work across separate long-poll requests. SSE uses one shared hub per
    active stream on each serving replica.[^perf]
  </Callout>

<section class="block" id="wake">
  <SectionHead num="03" label="OnStreamAppend" title="A subscription <em>wakes</em>" />

  The append walkthrough ended by firing `onStreamAppend`. This walkthrough picks
  it up. A durable write on a matched stream wakes a registered subscriber, in one
  of two ways. A signed webhook, or a pull-wake event that a worker claims. A
  generation counter fences every message, so a crash anywhere costs latency and
  not correctness.

  <Diagram name="seq-trace-wake" label="Subscription wake · call stack" caption="The handler records one dirty path and returns. A Manager-owned worker evaluates subscribers and arms the wake later. <strong>Webhook</strong> signs and POSTs. <strong>Pull-wake</strong> appends a wake event for workers to claim. Recovery repairs any local hint or armed delivery left stranded." />

  <Step n="1" fn="Handler.onStreamAppend" loc="handler.go:146" role="The exact call that closes the append trace. With no subscription layer wired, it is a no-op.">

```go title="handler.go" showLineNumbers startLineNumber=146
func (h *Handler) onStreamAppend(path string) {
	if h.SubHooks != nil {
		h.SubHooks.OnStreamAppend(subStreamPath(path))
	}
}
```

`subStreamPath` strips the leading slash to match the protocol's wire paths.
This runs inline on the append goroutine, right after the durable write. The
call returns after one bounded local handoff. It does not enumerate subscribers,
load cursors, read linked tails, or arm a wake.

  </Step>

  <Step n="2" fn="Manager.OnStreamAppend" loc="webhook/manager.go:537" role="Add or coalesce the path in a fixed queue, expose the enqueue result, and signal the dirty worker without blocking.">

```go title="webhook/manager.go (abridged)" showLineNumbers startLineNumber=537
func (m *Manager) OnStreamAppend(path string) {
	now := m.now()
	m.dirtyMu.Lock()
	result, _ := m.dirty.enqueue(path, now)
	stats := m.dirty.stats(now)
	m.dirtyMu.Unlock()

	m.metrics.DirtyEnqueue(result.String(), stats.depth, stats.capacity, stats.oldestAge)
	if result == dirtyEnqueued || result == dirtyOverflowed {
		m.signalDirty()
	}
}
```

Repeated appends to a queued path coalesce. An append that arrives while the
path is processing marks it dirty again, so it returns once to the queue tail.
If all 1,024 entries are occupied, an overflow epoch requests eager recovery.
No enqueue result blocks the HTTP response.

  </Step>

  <Step n="3" fn="Manager.processDirtyStream" loc="webhook/manager.go:625" role="The background worker looks up subscribers, hydrates their state, reads distinct linked tails in a batch, and applies the pure pending-work decision.">

```go title="webhook/manager.go (abridged)" showLineNumbers startLineNumber=625
ids, _, err := m.store.StreamSubscribers(path)
subs, err := m.store.GetMany(ids)
idle := make([]Subscription, 0, len(subs))
for _, sub := range subs {
	if sub.Phase == PhaseIdle {
		idle = append(idle, sub)
	}
}
paths := distinctLinkPaths(idle)
tails, err := m.streams.TailOffsets(paths)
for _, sub := range idle {
	if HasPendingWorkFrom(sub.Links, tails) {
		m.issueWakeResult(sub, path)
	}
}
```

`StreamSubscribers` reads a bounded occupied-slot bitmap, then pipelines one
fanout-set read for each occupied subscription slot. `GetMany` pipelines state
and cursor hydration. `TailOffsets` reads each distinct linked stream tail once.
Arming an owed wake runs `arm_wake.lua`, which bumps the generation, stamps a
fresh `wake_id`, and records the due mark atomically.

  </Step>

  <Step n="4" fn="claim.lua, the pull-wake fence" loc="webhook/scripts/claim.lua:36" role="Two workers race to claim the wake. The lease compare-and-set picks one, and the fence rotates.">

```lua title="webhook/scripts/claim.lua" showLineNumbers startLineNumber=36
local gen = redis.call('HGET', sub, 'generation')
local wake = redis.call('HGET', sub, 'wake_id')
if not (phase == 'waking' and wake ~= '') then
  gen = tostring(redis.call('HINCRBY', sub, 'generation', 1))
  wake = ARGV[5]
  redis.call('HSET', sub, 'wake_id', wake)
end
local until_ns = now + tonumber(ARGV[4]) * 1000000
redis.call('HSET', sub, 'phase', 'live', 'holder', '1', 'holder_worker', ARGV[2], 'lease_until_ns', tostring(until_ns))
```

The winner takes the lease and the current `generation`. The loser finds a held,
unexpired lease and gets the `409 BUSY` reply. Every ack the holder later sends
carries its generation. Any ack under a stale generation, from a former holder
whose lease expired and was reclaimed, is fenced out. The webhook path skips the
race. `deliverWebhook` signs the body with Ed25519, runs the URL past an SSRF
guard, POSTs it, and auto-acks on a `2xx {done:true}`. That is the same
generation fence applied to a push instead of a pull.

  </Step>

  A backstop keeps the whole plane working through crashes. The dirty worker is
  the low-latency path. Event-triggered recovery and a periodic floor guarantee
  the work still happens if the process-local hint disappears.

  <Aside label="Recovery" summary="How the sweep rebuilds state after a crash">
    The recovery floor runs in `recoveryLoop`, which calls `sweepOnce` on a ticker
    at `defaultSweepInterval`, 30 seconds by default. It re-emits a pull-wake event
    that was armed but never written (`wake_event_sent_ns == 0`), expires a lease
    whose holder vanished, and re-wakes an idle subscription that has pending work.
    The latency-sensitive cases are event-triggered by boot, reconnect, dirty
    processing error, overflow, and owner movement, so the periodic floor only
    bounds the one eventless case. A crash
    between any two steps above is recoverable for this reason. The
    [Subscriptions](../../subscriptions) reference walks the fencing and recovery in
    full.
  </Aside>

  [^perf]: Both the append throughput drop and the wakeup-latency floor are measured and explained in the [benchmark report](https://github.com/adityavkk/chronicle/blob/loadgen/docs/benchmarks/2026-06-10/REPORT.md). The [Overview](./../#performance) summarizes them.
</section>

<section class="block" id="fenced-write">
  <SectionHead num="04" label="POST + Write-Token" title="A fenced write <em>lands</em>" />

  The wake walkthrough ended with a worker holding a claim: a `generation`, a
  `wake_id`, a lease — and, on a write-fenced stream, a **write token**. This
  walkthrough follows that worker's append down to the Lua rung that decides
  it, then shows what the same path does to a zombie — the previous holder
  retrying with a stale token, or a writer with the same `Producer-Id` and no
  token at all. The wire contract is
  [WRITE-FENCING.md](https://github.com/adityavkk/chronicle/blob/main/docs/spec/WRITE-FENCING.md);
  the request carries `Write-Token`, `Producer-Id`, `Producer-Epoch` equal to
  the claim generation, and `Producer-Seq`.

  <Step n="1" fn="Handler.authorizeAppendCredential" loc="authz_write_fence.go:125" role="Phase 1, before any store access: route the credential, read the write-token carriers, enforce the header-only rules.">

```go title="handler.go" showLineNumbers startLineNumber=870
	// Credential preflight runs before stream store access so an invalid token
	// still cannot probe stream existence. The live fence is repeated below,
	// immediately before the mutation.
	cred, err := h.authorizeAppendCredential(r, path)
	if err != nil {
		return err
	}
```

The carriers are read in order — `Write-Token`, `electric-claim-token`, then
`Authorization: Bearer` unless the bearer already authenticated as a service or
wake credential. A duplicated or empty carrier is presented-but-invalid: fail
closed, never fall through. Two rules bind here on any stream in any mode: a
POST asserting `Write-Fence: true` without a token is `401`, and a token minted
for a shard other than 0 is `401`. An invalid token still cannot probe stream
existence — this phase touches no store.

  </Step>

  <Step n="2" fn="Handler.classifyFencedStream" loc="authz_write_fence.go:164" role="After Store.Get, only when the meta says the stream is fenced: derive the write class, once, for every POST shape.">

```go title="handler.go" showLineNumbers startLineNumber=890
	// On a fenced stream every POST — append, append-and-close, close-only —
	// is classed once, here, before any branch (#183 E.1 step c1). A stream
	// that never opted in is never classed and takes today's path.
	var class writeClass
	if meta.WriteFence {
		if class, err = h.classifyFencedStream(path, cred); err != nil {
			return err
		}
	}
```

Token or assertion ⇒ **fenced** class, and the token must verify even when a
service principal also authenticated — both valid, in every auth mode. No
carrier ⇒ **open** class: a wake-typed bearer is `403` (liveness is not
capability), a service principal proceeds under its policy, and an anonymous
write needs a principal per `CHRONICLE_AUTH_MODE`. Our worker is fenced class.

  </Step>

  <Step n="3" fn="the mandatory producer triple" loc="handler.go:947" role="The fenced class binds Producer-Epoch to the claim generation, so the headers that carry it are not optional.">

```go title="handler.go" showLineNumbers startLineNumber=947

		h.countFenceRejection(string(store.FenceProducerRequired))
```

Phase 2 (`authorizeAppendFence`, `authz_write_fence.go:204`) then re-verifies
the token immediately before the mutation and demands the in-slot fence: an

downgrade to an unfenced write.

  </Step>

First hit wins: `sealed` (generation at or below this authority's seal),

  <Step n="5" fn="fence_bind" loc="store/redis/scripts/common.lua:329" role="The write is accepted. Two meta fields record what the fence now owns.">

```lua title="store/redis/scripts/common.lua" showLineNumbers startLineNumber=329
local function fence_bind(hset, m, has_fence, producer_id, f_gen, off)
  if not (has_fence and m.wf == '1') then return end
  hset[#hset + 1] = 'wfLastOff'
  hset[#hset + 1] = off
  hset[#hset + 1] = 'wfbind:' .. producer_id
  hset[#hset + 1] = f_gen
end
```

`wfLastOff` is the fenced class's last offset — what a seal will fix as the
generation's definite end, never a later open-class tail. `wfbind:<id>` is the
producer binding: from now on an open write naming this `Producer-Id` — even a
byte-identical replay of an accepted tuple — is `409 reason=bound`. The zombie
that lost its token cannot keep its identity going unfenced.

  </Step>
