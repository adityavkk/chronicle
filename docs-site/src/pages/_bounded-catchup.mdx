<Tldr>
  <ul>
    <li><strong>Before:</strong> one reader could load all remaining stream data into Redis and Chronicle memory.</li>
    <li><strong>Now:</strong> Chronicle reads and sends about 1 MiB of whole frames at a time, with a separate limit of 1,024 frames per page.</li>
    <li><strong>Result:</strong> the old 128-reader test completed no accepted replay. The new path completed 435 measured, body-checked replays with no server error.</li>
    <li><strong>Cost:</strong> a 16 MiB replay normally needs 16 returned pages, so smaller memory use requires more Redis calls.</li>
  </ul>
</Tldr>

<section class="block" id="old-path">
  <SectionHead num="01" label="Before" title="One reader could ask Redis for <em>the complete suffix</em>" />

  Redis stores stream frames in a sorted set ordered by offset. The old read
  script called `ZRANGEBYLEX` from the requested offset to the stream tail with
  no `LIMIT`. Redis built the complete result while its Lua event loop was
  occupied. Chronicle received that result and then assembled another complete
  HTTP body.

  HTTP `limit` did not solve the storage problem. Chronicle applied it after
  Redis had already returned the full suffix. A 16 MiB stream and 512 concurrent
  readers therefore had an 8 GiB raw suffix shape before decoded frames, Go
  objects, socket buffers, and runtime memory.

  <CatchupPipeline />

  The local base completed 46 reads in the 32-reader cell, with 793.5 MiB peak
  Chronicle RSS and a 10.12-second p99. At 128 readers, Redis read timeouts
  caused all 128 accepted requests to fail.[^evidence]
</section>

<section class="block" id="page-contract">
  <SectionHead num="02" label="Page contract" title="Frame count bounds Redis work; <em>bytes bound the returned prefix</em>" />

  `ReadPage` takes two independent limits. `MaxFrames` limits the number of
  sorted-set members Redis can return to Lua. `TargetBytes` bounds the returned
  whole-frame prefix. Redis reads the first candidate alone, then derives an
  end-offset bound for an optional bulk read from the remaining bytes. It does
  not fetch a lookahead frame. The defaults are 1,024 frames and 1 MiB.

  For the common root-owned range, the atomic script that loads and validates
  root metadata now performs that bounded range read in the same invocation.
  A small root page therefore uses one `EVALSHA` and one metadata `HGETALL`,
  down from two of each. A pure typed Go classifier and its Lua mirror agree on
  empty, inherited, and root-owned ranges. Inherited fork prefixes retain their
  later source-slot reads so cross-slot ordering and fork visibility do not
  change.

  <CatchupBudget />

  An earlier 512-reader branch sample recorded 29,436 MiB fetched into candidate
  batches, 8,127 MiB returned, and 21,309 MiB left for later pages. That gap
  exposed a weak candidate-fetch shape: it selected up to 1,024 frames before
  applying the byte target. The final path makes no lookahead call and, for an
  aligned range, fetches only candidates it returns. Those figures explain the
  change but are not final-path measurements.

  <Complexity
    time="O(log N + F)"
    space="O(Σ candidate frame bytes)"
    why="<strong>N</strong> is the frame count in the stream and <strong>F</strong> is at most 1,024 for one page. The first range fetches one frame. An optional second range ends at the remaining byte budget, with no lookahead."
  />

  <Aside label="Oversized frame" summary="One indivisible frame may exceed the returned byte target">
    Chronicle stores each append frame as one sorted-set member. It cannot split
    that member during a read. If the first valid frame is larger than 1 MiB,
    the page returns that frame so the cursor can make progress. A storage
    format with chunked values would be required for a strict byte ceiling.
  </Aside>
</section>

<section class="block" id="snapshot">
  <SectionHead num="03" label="Snapshot" title="Every page belongs to <em>one response lifetime</em>" />

  Paging must not turn one response into a moving view of the stream. The first
  read captures the response tail and stream metadata. Every later page carries
  that snapshot back to the store.

  <Step
    n={1}
    fn="ReadPageOptions"
    loc="store/page.go:35-50"
    role="The first call has no snapshot. The store returns the tail, content type, closed state, and a random stream incarnation."
  >
    Later calls reuse the returned snapshot. The tail is the inclusive upper
    bound for the whole response.
  </Step>

  <Step
    n={2}
    fn="read.lua"
    loc="store/redis/scripts/read.lua:32-65"
    role="After atomic root validation, Redis classifies the first range. A root-owned range fetches one candidate and optionally the end-offset range that fits the remaining target in that same script. Both calls have a <code>LIMIT</code>."
  >
    The script rejects a different incarnation before it returns data. It also
    refreshes access once at the first root snapshot only when the stream has a
    sliding TTL. Persistent streams, absolute-expiry-only streams, continuation pages,
    long-poll rechecks, and inherited fork sources do not run that write branch.
  </Step>

  <Step
    n={3}
    fn="streamCatchupResponse"
    loc="handler_stream.go:200-258"
    role="The handler writes one page, flushes it, checks cancellation, and asks for the next page from the last returned offset."
  >
    The handler never constructs a second whole-response body. JSON punctuation,
    envelopes, and binary frames are written in response order as pages arrive.
  </Step>

  <Step
    n={4}
    fn="handleSSE"
    loc="handler_sse.go:103"
    role="SSE catch-up starts with the page already captured by handleRead, then continues under the same snapshot before attaching to the shared stream hub."
  >
    Each page ends with a control event that carries the exact resume offset.
    A new hub confirms its notification subscription before this first page,
    then seeds its identity and tail from the page. It reports ready without a
    duplicate initial refresh. A reconnect starts from the last complete
    control offset the client received.
  </Step>

  <Callout icon="alert" label="Interrupted response">
    TCP cannot retract a partial frame after a socket failure. Chronicle stops
    before another frame or page once it observes cancellation. An SSE client
    can resume from its last complete control offset. A non-live HTTP client
    must retry from an offset it has confirmed.
  </Callout>
</section>

  tradeoffs. They are not production capacity numbers.[^evidence]

  The final 32-reader cell completed more reads with lower p99 and 597.6 MiB

  complete failure to 435 measured, body-integrity-checked responses. Counts

  completion drained later; warmup completions remain excluded.

  <Aside label="512-reader comparison" summary="The sealed old result used different hardware">
    The sealed old 512-reader artifact came from a 16 vCPU environment and
    reported 57.60 MiB/s, a 34.10-second p99, and 940 errors. The final
    512-reader value came from the shared local host. The two runs do not support
    a direct latency comparison. The useful new result is 336 complete validated
    bodies, finite memory, and no server errors at a 512-reader cap.

<section class="block" id="writes">
  <SectionHead num="05" label="Write capacity" title="Catch-up cannot pass by <em>starving appends</em>" />

  The mixed workload keeps 32 catch-up readers active while eight writers offer
  40 single-frame appends per second. The accepted local run completed all
  1,200 writes during the 30-second offer window. That is 40.0 successful
  appends per second. Append p99 was 163.33 milliseconds, and no request failed.

  The paid GKE job now has explicit limits. It requires at least 38 successful
  appends per second over the configured offer window and append p99 at or below
  2,000 milliseconds. The existing zero-error check still runs, but zero errors
  alone cannot pass the cell.

<section class="block" id="correctness">
  <SectionHead num="06" label="Correctness" title="The page boundary keeps <em>the original stream contract</em>" />

  The differential tests run the same page cases through `MemoryStore` and
  Redis. They cover empty streams, exact targets, oversized frames, offsets,
  closure, concurrent append, fork inheritance, expiry, and every configured
  page size. Cancellation tests stop before the first page, between pages,
  while waiting for a Redis connection, during a socket write, and after a
  flush.

  <Table>
    | Gate | Result |
    | --- | --- |
    | Durable Streams conformance | **332 / 332 passed** |
    | Paged catch-up Jepsen scenario | **6 attempts: 4 faulted, 1 concurrent snapshot, 1 clean drain** |
    | Fork snapshot oracle | **136 frames matched exactly** |
    | Maintained data-plane Porcupine history | **linearizable across 3,472 operations** |
    | Maintained single-holder Porcupine history | **linearizable across 672 operations** |
  </Table>

  The paged Jepsen scenario used four fault or interruption attempts: client
  cancellation, a client transport interruption, a restart of every Chronicle
  origin, and a Redis restart. It then captured a snapshot during concurrent
  append and close, followed by one clean final drain. The checker required
  forward-only exact-once coverage and compared acknowledged frames with a
  direct Redis sorted-set oracle.[^jepsen]
</section>

<section class="block" id="limits">
  <SectionHead num="07" label="Limits" title="What bounded pages <em>do not solve</em>" />

  - **Candidate bytes do not have an absolute 1 MiB ceiling.** Redis can fetch
    one indivisible oversized first frame. At a fork-segment transition it can
    inspect one non-fitting first candidate before stopping. It cannot
    speculatively materialize a batch of hundreds of oversized frames.
  - **One large frame can exceed the returned target.** Chronicle cannot split
    the current sorted-set member format.
  - **Small pages add round trips.** In the fresh short local comparison, all
    page sizes retained the same offered-window completion rate and 256 KiB had
    the best p99. A managed-Valkey run is needed before claiming a production
    latency optimum.
  - **High concurrency still has long latency.** The 512-reader local p99 was
    28.85 seconds. Paging prevents the old failure shape. It does not make the
    shared laptop a production-sized system.
  - **External stores need the optional page interface.** A third-party backend
    that implements only `store.Store` keeps source compatibility and avoids the
    second handler buffer, but it cannot promise bounded storage work.
  - **The managed Valkey 8 run remains missing.** The local evidence is enough
    to judge the mechanism and memory shape. It is not a GKE capacity result.
