<Tldr>
  <ul>
    <li><strong>Before:</strong> 1,000 clients could cause about 1,000 Redis reads for one append.</li>
    <li><strong>Now:</strong> one hub reads the stream once and shares the formatted event with local clients.</li>
    <li><strong>Result:</strong> the measured ratio fell from 970.5 Redis reads per append to 1.000.</li>
    <li><strong>Cost:</strong> socket writes still happen once per client, and slow clients may have to reconnect from their last saved offset.</li>
  </ul>
</Tldr>

<section class="block" id="old-path">
  <SectionHead num="01" label="Before" title="One append caused <em>the same work N times</em>" />

  The old handler gave every SSE client its own read and wait loop. When an
  append landed, Redis published a short wake message. Every waiting client
  woke, reread the same durable suffix, fetched stream metadata, formatted the
  same SSE data event, and wrote it to its own socket.

  The wake message did not contain the stream data, which was correct. Redis
  Pub/Sub can lose a message during a disconnect, so clients had to read the
  durable stream after every wake. The problem was where that read happened.
  It happened once per client instead of once per stream.

  <Diagram
    name="wiki-sse-old"
    label="Before · one loop per client"
    caption="<strong>Every blue return path is duplicate durable work.</strong> The clients need separate socket writes, but they do not need separate Redis reads or separate copies of the same formatted data event."
  />

  <Table>
    | Sealed workload | Redis publishes | Live `ZRANGEBYLEX` reads | Reads per append |
    | --- | ---: | ---: | ---: |
    | 1 stream, 1,000 clients | 863 | 837,579 | **970.5** |
    | 100 streams, 2,048 clients | 26,900 | 539,956 | **20.1** |
  </Table>

  The difference between 1,000 clients and 970.5 reads per append comes from
  timing and incomplete delivery during the measured window. The mechanism is
  still direct: more clients on one stream create more duplicate reads.
  Increasing Chronicle and Redis from 4 to 16 vCPU did not move the observed
  SSE ceiling beyond roughly 25,000 to 32,000 delivered events per second.[^adr]
</section>

<section class="block" id="new-path">
  <SectionHead num="02" label="After" title="One stream hub does <em>the shared work once</em>" />

  The new handler creates or reuses one hub for the stream on the current
  Chronicle replica. The hub owns one logical notification registration. A
  store-owned multiplexer carries all such registrations over one physical
  Redis Pub/Sub connection by default. After a wake hint, the hub pages through
  one exact durable tail, formats one immutable SSE data event, and places that
  event in a bounded replay window. Each local client has only a coalesced wake
  signal and its own durable offset.

  <Diagram
    name="wiki-sse-new"
    label="After · one hub per active stream and replica"
    caption="<strong>The live Redis path is shared.</strong> Socket writes remain per client because each HTTP connection is real. The data read and data-event formatting happen once."
  />

  <Table>
    | Work | Old setup | New setup |
    | --- | --- | --- |
    | Logical notification registration | one per SSE client | one per active stream on each serving replica |
    | Physical Redis Pub/Sub connection | one per SSE client | one per store by default |
    | Durable live read after an append | one per client | one per stream hub |
    | Data-event formatting and base64 | repeated by every client | one shared immutable event |
    | Client progress lookup | linear ring scan | monotonic sequence plus indexed boundary lookup |
    | Slow client | could keep its loop and socket blocked | disconnects after replay lag or write timeout |
    | Last client leaves | its loop closes | the hub and logical registration close |
  </Table>

  <Complexity

    space="O(S·B + C)"
    why="<strong>S</strong> is the number of active streams, <strong>R</strong> is the number of Chronicle replicas that currently serve clients for those streams, <strong>C</strong> is the client count, and <strong>B</strong> is the bounded replay size. Redis reads now follow streams and serving replicas. Socket writes still follow clients."

<section class="block" id="handoff">
  <SectionHead num="04" label="Safety" title="The hard part is <em>joining without a gap</em>" />

  Sharing the live path creates a handoff problem. A client may arrive while an
  append, delete, or recreation is in flight. Chronicle solves that by starting
  the hub before the client finishes catch-up.

  <Diagram
    name="seq-sse-hub-attach"
    label="Catch-up to live handoff"
    caption="The multiplexer confirms the hub's logical registration before the first catch-up page captures its tail. The handler confirms the stream incarnation and attaches at the exact control offset it flushed. An append can land at any point without being lost or sent before its control offset."
  />

  Eight rules protect this boundary:

  1. **Register before the first page.** The multiplexer waits for the current
     Redis connection generation to acknowledge the hub's logical channel. The
     first `ReadPage` then captures the incarnation and exact tail.
  2. **Seed readiness from page one.** Client catch-up uses `ReadPage` and the
     first confirmed hub generation starts from that authoritative snapshot.
     It does not reread the same offset for readiness. Catch-up stops at its
     captured tail even when appends continue, and neither catch-up nor hub
     refresh can fall back to an unbounded `Store.Read`.
  3. **Flush before advancing.** The handler puts the page's data and control
     flush under one write deadline. It advances the attach offset only after
     that control value reaches the client.
  4. **Attach at the exact boundary.** The handler confirms the durable stream
     identity without renewing its TTL again. It then uses the ring's sequence
     and boundary index to find the exact controlled offset. If eviction removed
     it, Chronicle closes the connection and lets the client resume. It never
     skips to a newer offset. Any failure discovered after SSE headers are
     committed aborts the transport; Chronicle never appends an ordinary HTTP
     error payload to the event stream.
  5. **Recheck the durable stream.** A wake is only a hint. The hub reads Redis
     after a hint and once per second while idle. A lost Pub/Sub message delays
     delivery by at most one poll. It does not lose data.
  6. **Recover the notification connection.** A reconnect invalidates old
     acknowledgements, restores all desired channels, and wakes each hub for an
     immediate durable no-touch refresh. A replacement subscription generation
     refreshes the same way before waiting. Append and close hints and defensive
     polls retain their access-touch semantics. A coalesced nonblocking signal
     keeps one blocked hub from holding another.
  7. **Name each stream lifetime.** Every create stores a random 128-bit
     incarnation ID. If a path is deleted and recreated, the old hub stops
     instead of serving the new stream with old state.
  8. **Bound slow consumers.** The replay window is 1 MiB by default and each
     client flush has a ten-second deadline. A lagging client disconnects and
     resumes from the last control offset it actually received.

  Redis orders an append either before or after the registered first page. An
  append before the page is inside its fixed catch-up tail. An append after the
  page is covered by the confirmed subscription. The safety poll recovers a
  lost notification, and the incarnation check fences a delete and recreation.
  The [SSE endpoint sequence](../../endpoints#get-sse) follows the same request
  from authorization through the final data and control events.

  <Callout icon="alert" label="Correctness gate">
    The optimization is allowed to change how work is shared. It is not allowed
    to change Durable Streams behavior. The complete conformance suite remains
    a merge blocker. The Jepsen and Porcupine suites remain maintained blockers.
    Producer fencing, append atomicity, closure, expiry, forks, offsets, and
    persistence must stay correct even if a faster design is available.
  </Callout>
</section>

<section class="block" id="results">
  <SectionHead num="05" label="Results" title="Read amplification collapsed, then <em>sockets became visible</em>" />

  <SSEResults />

  The issue 13 image was tested with one Chronicle replica, one Redis primary, and
  AOF configured to sync every write. Chronicle had 2 vCPU and 4 GiB. Redis had
  2 vCPU and 12 GiB. The one-stream workload used 1,000 clients for 20 seconds.
  The 100-stream workload used 2,048 clients for 15 seconds. Each workload ran
  three times from fresh result state. The table uses the component median.[^issue13]

  <Table wide>
    | Workload | Result | Delivered | Delivery rate | p50 | p99 | Completion | Errors |
    | --- | --- | ---: | ---: | ---: | ---: | ---: | ---: |
    | 1 stream, 1,000 clients | issue 4 baseline | 992,320 | 49,616/s | 7.123 ms | 19.519 ms | 99.232% | 0 |
    | 1 stream, 1,000 clients | issue 13 median | 981,983 | **49,099/s** | 5.047 ms | **8.591 ms** | 98.198% | 0 |
    | 100 streams, 2,048 clients | issue 4 baseline | 1,173,067 | 78,204/s | 40.159 ms | 71.167 ms | 76.371% | 0 |
    | 100 streams, 2,048 clients | issue 13 median | 1,495,527 | **99,702/s** | 23.967 ms | **51.903 ms** | 97.365% | 0 |
  </Table>

  The exact-counter guard opened 1,000 clients and waited for catch-up reads to
  settle. Redis `PUBLISH` then advanced from 3,480 to 3,580, while
  `ZRANGEBYLEX` advanced from 5,602 to 5,702. The instrumented hub also
  completed 100 `ReadPage` calls. The result was 1.000 Redis read command and
  1.000 durable page per append, which passes the 1.2 gate.[^issue13]

  The fused root-read follow-up supplies one authoritative first page after
  registration. The first confirmed hub generation becomes ready from that
  page with no duplicate initial refresh. Issue 13 retains one final bounded
  no-touch identity confirmation immediately before indexed attach. It fences
  a delete/recreate race without delivering client data twice at the same
  offset. Reconnect generations also refresh durable state immediately with
  no access touch.

  Every final workload repetition recorded zero backpressure and zero other
  client errors. Median peak sampled Chronicle RSS was 134.25 MiB for one stream
  and 396.89 MiB for 100 streams. The 100-stream run used 100 logical
  notification registrations over one physical Redis Pub/Sub connection.

  The frame benchmark also changed the per-client control path. A typed reusable
  buffer reduced allocation from 905 to 216 bytes per update, a 76.1 percent
  reduction, while median time improved by 4.8 percent. A focused CPU profile
  then removed repeated Redis path-escaper construction. The 100-stream median
  moved from a failing 75.647 ms p99 to 51.903 ms.[^issue13]

  <Aside label="How to read the throughput number" summary="The read ratio is the direct proof; the rate comparison is directional">
    The issue 4 baseline and issue 13 image used the same local Kubernetes
    workload shape and resource split, but they were not randomized on an
    untouched cluster. The exact page and Redis command counters prove the
    shared-read mechanism. The three-run medians reduce host noise without
    turning the throughput comparison into a universal capacity claim.
  </Aside>

  The performance work did not stop at happy-path tests. The full 332-test
  conformance suite passed. Four live Jepsen scenarios passed: baseline, origin
  restart, Redis restart, and SSE resume. The SSE scenario delivered 320
  expected events exactly once across eight checked readers and verified 11
  fault actions, including replay lag, write timeout, delete and recreate, and
  attachment at a page boundary. A direct Redis oracle checked the final frames,
  offsets, tail, closed state, and producer state.[^jepsen]
</section>

<section class="block" id="limits">
  <SectionHead num="06" label="Limits" title="What this fix does <em>not</em> remove" />

  The hub removes duplicate live reads. It does not make every SSE cost shared.

  - **Initial catch-up still reads once per client.** A client that starts far
    behind the tail still replays its own history from Redis.
  - **Socket work still scales with clients.** Each connection needs its own
    control event, write, flush, deadline, and kernel socket buffer.
  - **Subscriptions still scale with streams and replicas.** One active stream
    on three serving Chronicle replicas uses three Redis subscriptions.
  - **The safety poll reads idle streams once per second.** This recovers lost
    wake hints and refreshes sliding TTL, but it becomes visible at a high
    active-stream count.
  - **The replay window adds shared state.** It is bounded, but the attach,
    eviction, and delete-recreate paths are more complex than one isolated loop.

  CPU profiles now point mostly at socket syscalls. Remaining allocation work
  includes per-client control framing and Redis connection buffers. Initial
  historical replay also remains per client. Those are separate improvements.
  None should weaken the conformance or Jepsen gates.

  A 30-minute active run added a throttled client and 69,879 protocol
  reconnects. Chronicle averaged 48.2 MiB RSS and peaked at 56.5 MiB. Heap,
  goroutines, descriptors, registrations, and ring bytes stayed bounded in the
  final window. Cleanup returned clients, hubs, registrations, physical
  connections, and every ring byte component to exactly zero.[^issue13]
