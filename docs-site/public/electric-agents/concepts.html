The Nouns

Before any code: what exists in an Electric Agents system, and what each thing is. Every later part builds strictly on these definitions. The order is deliberate — each noun is defined only in terms of the ones before it.

1Entity — the unit of existence

An entity is a durable, addressable thing in the system. Its identity is a URL path: 

/{type}/{instanceId}        e.g.  /assistant/support-42   /judge/debate-7

Every entity has exactly three anatomical parts:

An event stream
One append-only log at /{type}/{id}/main holding everything that ever happened to this entity. This is the entity's memory — there is no other.
A handler
The function for its type, run each time the entity wakes. The handler is code you deploy; the entity is data that outlives any deployment.
A registry row
A control-plane record (in the server's Postgres) tracking its type, status (spawning · running · idle · paused · stopping · stopped · killed), parent, tags, and creator.

Crucially, an entity is not a process. Between wakes, nothing about it is in memory anywhere. It "exists" the way a row in a database exists. An agent is just the most interesting kind of entity — one whose handler runs an LLM loop. But an entity with no LLM at all (a counter, a state machine, an outbox) is equally valid, which is why the docs say entity when talking about the machinery and agent when talking about the behavior.

💡 One sentence to remember

An entity is a URL, a log, and a function — identity, memory, behavior — with all three decoupled from any running process.

2Stream — the unit of memory

A durable stream is an append-only byte/message log addressed as an HTTP resource. Create it with PUT, append with POST, read with GET ?offset=… — including catching up from any historical offset and then live-tailing via long-poll or SSE. Every read returns a Stream-Next-Offset header; hand it back and you resume exactly where you left off.

Electric Agents gives each entity one main stream: /{type}/{id}/main. Everything is an event on that one log — inbound messages, LLM run boundaries, streamed text tokens, tool calls, state changes, signals, tags. (Attachments get sibling streams at /{type}/{id}/attachments/{attachmentId}, and shared state lives in its own streams — both covered later.)

Why a log, and not a database row or KV entry? Three properties do all the work:

  • It's a total order. Concurrent writers are serialized by the server; every consumer sees the same history in the same order. Coordination comes for free.
  • It's resumable. Offsets make consumption stateless — a crashed consumer, a new UI tab, or a freshly woken handler all catch up from wherever they were, then go live in the same request.
  • It's the transport and the storage. Streaming LLM tokens to a UI and durably persisting them is the same write. There is no separate "save to DB" step to forget or to race.
🔗 Chronicle note

This layer is precisely what Chronicle implements: the Durable Streams protocol — PUT/POST/GET with Stream-Next-Offset, long-poll and SSE live modes, idempotent producers, TTLs and closure — backed by Redis instead of the reference server's LMDB. Everything in this explainer above the stream layer is protocol-agnostic about the backend. Part 2 goes deep on the protocol itself.

3Wake — the unit of execution

Entities spend their lives asleep. A wake is the event "something you care about happened", and it is the only reason handler code ever runs. Each wake carries what happened and which stream offsets it covers, so a handler processes a well-defined window of new events.

Four things can produce a wake:

📬 An inbox message
Someone — a user, another entity, a webhook source — appended a message to this entity's inbox. Arrives as wake.type === 'inbox'.
👶 A child finishing
A spawned child's run completed or failed, and the parent asked to be woken (wake: { on: 'runFinished' }). Payload carries finished_child with the response.
👁 An observed change
A stream this entity observes — another entity, a shared DB, a Postgres table, a webhook source — changed (wake: { on: 'change', collections?, ops? }). Payload lists the changes.
⏰ Time
A cron schedule ticked, a delayed send(…, { afterMs }) came due, or a wake registration's timeoutMs expired with nothing happening.

Inside the handler these normalize to just two shapes: wake.type === 'inbox' (a message, with payload and sender) and wake.type === 'wake' (everything else, with a payload describing changes, an optional finished_child, and sibling status in other_children). Wake registrations support debounceMs (coalesce bursts), timeoutMs, oneShot, and includeResponse (inline the child's final text).

⚠ The inversion that matters

In a process-agent, the agent polls or blocks waiting for input. Here the direction is reversed: the data wakes the compute. That's what lets an agent be a serverless function and scale to zero — and it's why "waiting for five children to finish" costs nothing while waiting.

4Handler — the unit of behavior

A handler is the single function you write per entity type. It receives a fully hydrated context and the wake that triggered it: 

registry.define('judge', {
  description: 'Coordinates a three-phase debate',
  state: { debate: { schema: passthrough<Debate>(), primaryKey: 'key' } },

  async handler(ctx, wake) {
    // 1. look at the wake and your durable state
    // 2. decide: run the LLM? spawn children? update state? just sleep?
  }
})

The handler is where deterministic control flow lives. A well-designed handler is a gate in front of the LLM: it reads wake and ctx.state, handles the cases that need no intelligence imperatively (record an argument, forward a rebuttal, ctx.sleep()), and only invokes the LLM for the steps that need judgment. The official walkthrough calls this hybrid control flow, and it is the framework's central design idiom — Part 3 §6 builds it up step by step.

Handlers must be safe to re-run: wake delivery is at-least-once, so the guard-then-act shape (if (ctx.state.debate.get('current')) return ctx.sleep()) is idiomatic, not defensive paranoia.

5Agent — the LLM loop, as a capability

In this stack, "agent" is not a class you instantiate — it's a capability a handler opts into for the duration of one wake: 

ctx.useAgent({
  systemPrompt: 'You are a fair, concise judge…',
  model: 'claude-sonnet-4-6',
  tools: [createStartDebateTool(ctx), ...ctx.electricTools],
})
await ctx.agent.run()

What agent.run() does, conceptually (mechanically in Part 4):

  1. Rebuilds the conversation from the stream. The entity's timeline — past inbox messages, runs, texts, tool calls — is projected into LLM messages. No hidden session memory; context is the log.
  2. Runs the standard tool-use loop. Model streams a response; tool calls are executed (in the entity's sandbox where relevant) and results fed back; repeat until the model stops.
  3. Appends every step back onto the stream as it happens. Run boundaries, token deltas, reasoning, tool calls with results, token usage — each as a typed event. UIs watching the stream render tokens live; the entity's memory and the user's screen are the same data.

If a handler never calls useAgent(), no LLM runs for that wake. An entity might use the LLM on one wake and pure imperative logic on the next — the judge in the walkthrough does exactly that (LLM for briefs and verdict, plain code for the phases in between).

6Collections — state as a view of the stream

Raw logs are miserable to program against. So the runtime materializes each entity's stream into typed TanStack DB collections — an embedded, reactive client database — on every wake. Events of type run become rows in ctx.db.collections.runs; inbox events become rows in inbox; your own declared state events become rows in your collections.

Two kinds of collections:

  • Built-ins (20 of them, every entity): runs, steps, texts, textDeltas, toolCalls, reasoning, reasoningDeltas, errors, inbox, wakes, signals, tags, childStatus, entityCreated, entityStopped, slashCommands, manifests, contextInserted, contextRemoved, replayWatermarks. These are the LLM loop and lifecycle, made queryable.
  • Yours, declared per type: the state: block of the entity definition. Each entry gets a schema (Zod / TypeBox / any Standard Schema), a primary key, and auto-generated writer actions — ctx.state.debate.insert / update / delete — which don't mutate anything directly: they append change events to the stream, which the materializer then applies. Reads and writes both go through the log.

Because collections are TanStack DB, they're not just maps — they support live queries (joins, filters, aggregates that update incrementally as events arrive), which is how UIs, observers, and parents watch an entity in real time. Q&A #3 examines why this layer exists instead of hand-rolled event folding.

7Entity types & the registry

An entity type is the "class": a name plus a definition — description, creationSchema (validated spawn args), inboxSchemas (validated message payloads by type), state collections, permission grants, and the handler. You declare types in an EntityRegistry in your app: 

const registry = createEntityRegistry()
registry.define('assistant', { description, state, handler })
registry.define('judge',     { description, state, handler })

const runtime = createRuntimeHandler({ baseUrl, serveEndpoint, registry })
await runtime.registerTypes()   // ← tells the server these types exist, and where

registerTypes() uploads each type's metadata — including your app's serveEndpoint, the webhook URL the server will POST wakes to. From that moment the server can mint instances of your types (PUT /_electric/entities/judge/debate-7) and knows exactly which URL to hit when one needs to run. The type is the contract; the server owns instances; your app owns behavior.

8Principal — who is acting

Every request into the system carries a principal: <kind>:<id> where kind is user, agent, service, or system — e.g. user:alice, or an agent entity acting as agent:/judge/debate-7. Principals are themselves addressable as entities (/principal/<key>), and every permission — read, write, spawn, signal, fork, schedule, manage — is granted to a principal (or a whole kind) on an entity or type. Creators get full rights on what they create; everything else is explicit grants. The full model, including how you plug in real authentication, is in Q&A #5.

9The Runtime and the Server — two halves, one seam

The names are confusingly similar; the split is the most load-bearing fact in the architecture.

yours @electric-ax/agents-runtime

A library inside your app. Ephemeral by design.

  • Holds the EntityRegistry — your handlers
  • Receives wake webhooks at your serveEndpoint
  • Materializes the entity's stream → ctx
  • Runs your handler and its LLM loop
  • Appends resulting events back via the server

Runs anywhere TypeScript runs: a Hono/Next/Express server, an edge function, a container. Holds no durable state.

infra @electric-ax/agents-server

The always-on control plane. Durable by design.

  • Stores/proxies all durable streams
  • Registry of entities, types, grants (Postgres)
  • Watches streams; evaluates wake conditions
  • Dispatches wakes: webhook push or runner pull
  • Enforces permissions, write tokens, tenancy
  • Serves the observability UI + live Electric sync

One Docker container in dev (electric-ax agents start, port 4437); Electric Cloud or self-hosted in prod.

The seam between them is plain HTTP in both directions: your runtime calls the server's API (register types, spawn, send, append, observe); the server calls your runtime's one webhook endpoint (wake). That narrow, stateless seam is what makes the deployment story flexible — Q&A #4 maps the topologies.
