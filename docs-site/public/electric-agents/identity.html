Evaluation & design

Agent identity, decided at the egress boundary

An Electric agent is a stream path. It has no keypair, no certificate, and no attestable identity of its own, and today every secret it uses to call the outside world lives with the host process: environment variables, a machine-wide token file, or the OS keychain. This page answers three questions, and the design corollary they force. What identity and authorization machinery does Electric Agents actually ship, and what does it tell you to do? Does a forward proxy in the clawpatrol shape verify who is calling it, or only where the bytes came from? And how do you give every agent entity a verifiable cryptographic identity so that a policy layer outside the agent can inspect each request, judge it with rules and a model, inject the real credentials itself, and leave the agent holding no tokens at all? The design in section 5 anchors that identity on machinery chronicle already ships: the Ed25519-signed wake.

§The verdict up front

QuestionAnswerWhere
What does Electric Agents already do about identity? It names identities but does not prove them. There is a real principal model with agent as a first-class kind and a real, enforced grant system for who may touch an entity. But the principal arrives as a plain unauthenticated HTTP header, authentication is delegated to a hook you must write, and on the outbound side there is no per-entity credential concept at all: model keys, tool keys, and MCP OAuth tokens are process-global. Electric's own docs tell you to put an authenticating proxy in front. The gap you suspected is real, and it is documented as yours to fill. §2
Does clawpatrol verify the identity of the agent? Half yes, and the half matters. In its remote modes it cryptographically verifies the device (a WireGuard peer or Tailscale node minted at human-approved onboarding) and refuses to trust anything the agent asserts. But the subject is never an agent entity, rules cannot reference caller identity in conditions, and its identity granularity recently moved coarser, to one daemon per host. One process hosting a thousand entities is a single indistinguishable peer. The shape is right. The subject is wrong. §3
Can "no tokens with the agent" work per entity? Yes, and every piece has shipped prior art: platform-attested identity with local token vending (cloud IMDS), gateway-side credential injection (clawpatrol, Google's Agent Gateway), request-body policy with header injection (Envoy ext_authz), and a model verdict in the blocking path (Cloudflare's guardrails at roughly 500ms). What has not shipped anywhere we could find in public documentation is the granularity you need: a distinct verifiable credential per agent entity, finer than the process. That layer is the thing to build, and it is small, because chronicle already signs a per-wake statement that names the entity. §4, §5
What should chronicle itself take on? Wake attestation and nothing more. Chronicle should sign short-lived, audience-bound statements that a specific entity was legitimately woken at a specific generation, as a pure §11 superset of the protocol. It should not become an OAuth authorization server: it has no model of scopes, consent, or external audiences, and the spec deliberately keeps authentication out of scope. Verification, token custody, exchange, and policy belong in the egress gateway. §5

§What Electric Agents ships today, and what it recommends

The findings below come from the source at commit 5af7ab52 (2026-06-30), with file and line references into packages/agents-server and packages/agents-runtime. primary

The principal model is real. A principal is kind:id where kind is user, agent, service, or system (principal.ts:3), canonicalized to a URL /principal/<kind>:<id>. The authorization layer is also real: DB-backed per-entity grants (read, write, delete, signal, fork, schedule, spawn, manage) plus entity-type grants, checked on every request, with expiry and propagation to descendants (permissions.ts:29-197). Agent-to-agent messages carry a from_agent field that the server checks against the authenticated agent principal (entities-router.ts:1319). The identity schema even carries optional auth_provider, auth_subject, and claims fields, a linkage shape for an external identity provider that nothing in the open-source codebase populates or verifies.

The authentication of that principal is a header. The server resolves the caller from an optional authenticateRequest hook that you supply; when the hook is absent it parses the plain Electric-Principal HTTP header verbatim (server.ts:406-427, principal.ts:64-68). No JWT, no signature, no API key exists anywhere in the inbound path. Three built-in system principals (framework, auth-sync, dev-local) bypass every permission check, so the header electric-principal: system:framework is, by itself, full access. Header-less requests get the all-powerful dev principal whenever NODE_ENV is not production, an embedded test stream server is set, or ELECTRIC_INSECURE=true (server.ts:381-390). The runtime, for its part, authenticates to the server with operator-supplied static headers and echoes back whatever principal key arrived in the wake notification. The docs are explicit that this is by design: production deployments "should authenticate requests and provide an explicit Electric-Principal header for every request", and Electric's sync guides canonize the same posture as proxy auth and gatekeeper auth. The gatekeeper you are imagining is the deployment model they assume. primary

Outbound, there is no identity at all. Model keys are process-wide environment variables or a machine-wide Codex token file, with an optional getApiKey(provider) hook whose signature does not include the entity (model-runner.ts:44-75, types.ts:959-961). Tool keys come from process.env. MCP servers configured with OAuth persist their tokens in the OS keychain and the docs state the resulting tools become available "to every entity at the next wake", so one user's grant is shared by every entity the process hosts. The word "credential" appears exactly once in the two packages' source, in an error message. There is no forward-proxy support: zero matches for HTTPS_PROXY or any proxy agent across the packages. Two seams do exist and matter later: MCP HTTP transports have first-class per-destination token injection, and host-side fetches flow through undici's composable global dispatcher, which Electric's own desktop app already uses to inject its cloud auth. But there is no per-entity anything on the way out. primary

Sandboxes bound egress, not identity. Network policy on the Docker sandbox is only a hard boundary at deny-all; the docs say the allowlist mode is "only a surface protection on docker, NOT a boundary", because exec has direct bridge egress. The E2B adapter maps allowlists to VM-level filtering that appears to match on Host and SNI, which raw-IP or non-HTTP traffic may bypass; we did not verify E2B's enforcement depth. inferred Sandboxes receive secrets as static profile environment variables. And the one piece of cryptography in the whole system points the other way: the agents-server signs outbound wake webhooks with an Ed25519 key and publishes a JWKS, and the runtime verifies those signatures with a 300-second replay window (webhook-signing.ts, webhook-signature.ts:38-90). The server proves itself to the runtime. Nothing proves the agent to anyone. primary

The roadmap says this is deliberate. The runners RFC (issue #4299) states "This RFC does not try to solve authorization in a general sense", ships runner identity as a named row with a same-user check, and defers both "runner-specific cryptography or device credentials" and "delegated credentials if needed by runner apps" to future work. The nearest thing to a per-entity secret that exists today is the per-wake claim and write token pair: random UUIDs minted at wake time, scoped to one entity's stream and one claim epoch. The protocol spec says such tokens SHOULD be signed; the shipped implementation does not sign them. That per-wake capability is the seed the design in section 5 grows. primary

§What clawpatrol is, and what it actually verifies

Clawpatrol is denoland/clawpatrol, Deno Land's MIT-licensed "security firewall for agents": a single self-hosted Go binary that terminates agent egress. It is young and fast-moving: first commit 2026-04-28, roughly 900 stars, 24 releases between mid-May and late June, pre-1.0 with a written security model that its own issue tracker admits the implementation still trails. primary

Its architecture is worth describing precisely because section 5 borrows most of it. Agent machines join the gateway over WireGuard or Tailscale at layer 3, so there is no HTTPS_PROXY variable and no CONNECT: the gateway sees every flow's original destination, peeks TLS SNI, and man-in-the-middles matched hosts with a per-gateway CA installed in the agent's trust store at onboarding. Beyond HTTPS, it natively intercepts Postgres, ClickHouse, Kubernetes, and SSH. Credentials live gateway-side in SQLite; agents receive shape-valid placeholders (GH_TOKEN=ghp_clawpatrol_placeholder_do_not_use) and the gateway swaps the real secret into the protocol's auth slot at egress, including stripping and re-signing AWS SigV4 requests and completing SSH and Postgres handshakes itself. Response-side auth artifacts (Set-Cookie, WWW-Authenticate) are stripped so the agent cannot harvest session tokens from what comes back. Policy is HCL rules with CEL (Common Expression Language) conditions over per-protocol wire facts, including parsed JSON request bodies up to 1 MiB, with first-match priority, fail-closed evaluation errors (though the no-match default is allow, and the docs recommend a low-priority deny catch-all), a built-in LLM approver that judges the request against an operator-written policy prompt with a deny-when-ambiguous system prompt, and human approval over Slack, the dashboard, or a webhook that times out closed. Its security model is honest about containment: interception is best-effort, and the guarantee is only that "a flow that escapes interception is therefore uncredentialed — an anonymous client holding only placeholders…" Tokens and policy share one chokepoint, so escaping the proxy costs the agent its credentials. That coupling is exactly the property you asked for. primary

Now the identity question. Your suspicion was half right, and the refinement matters. Clawpatrol does verify an identity, and refuses to trust anything the agent claims: "The originating registration is identified from the channel the request arrived on... not from anything the agent can claim" (security-model.md). In remote modes that channel identity is cryptographic, a WireGuard peer key or a persistent Tailscale node minted at human-approved onboarding and mapped to a credential profile. In local mode it is UNIX-user channel separation, not cryptography. But the subject is always a device. The schema comments say the owner concept is "intentionally absent"; rule conditions expose only protocol facts (http.*, sql.*, k8s.*, ssh.*) and no caller-identity variable exists; identity can select which rules apply, via profiles and per-device blocks, but can never be tested inside a condition. And the granularity has moved coarser, not finer: per-run ephemeral WireGuard peers were added and then removed when both transports were unified into one per-host daemon, so today every process on a device, and every entity inside every process, is one indistinguishable peer. The open roadmap items (community RFC #709 for Kubernetes-attested dynamic peers, maintainer PR #753 for OIDC ephemeral enrollment) are both enrollment-time and workload-grade, not per-entity and not per-request. Per-entity policy is not expressible in clawpatrol today, and nothing public suggests it will be soon. One more practical gap for your use case: there is no Microsoft Graph or Entra OAuth credential plugin, so Graph would ride a generic static bearer with no refresh handling, or a custom plugin. primary

§The prior art in one map

Everything the target architecture needs exists somewhere, shipped or drafted. What does not exist, anywhere we could find in public documentation, is the combination at entity granularity. The consistent pattern across every serious system is two layers: a strongly attested workload identity for the process or pod, and a cheap, short-lived credential minted per finer-grained subject on top of it. No system we found issues certificates per entity at million-entity scale; every system we examined switches to short-lived signed tokens at that layer. inferred

SPIFFE / SPIRE Workload identity with no bootstrap secret: the platform attests the process and issues X.509 or JWT SVIDs. The identity subject is the workload. Static registration per entity is the wrong tool: the official sizing guidance tops out at 10,000 workloads and a 700k-entry performance test reported timeouts (since mitigated, with the mitigations still opt-in). The incubating SPIFFE Broker API is the project's own answer for finer-grained subjects: a trusted broker fetches SVIDs on behalf of control-plane objects. shipped core, incubating broker
IETF WIMSE + transaction tokens The standards track is converging on exactly this shape. The WIMSE architecture defines an Identity Proxy that may inspect, replace, or augment workload identity and carry added context as a transaction token. Transaction tokens (draft-08, WG last call ended 2026-04-10) are short-lived, purpose-scoped JWTs minted by one logical service per trust domain, with a self-signed path for internally-initiated work such as cron. That is a per-wake credential in all but name. None of it is an RFC yet. draft
Proof-of-possession per request DPoP (RFC 9449) and HTTP Message Signatures (RFC 9421) let a caller sign each request against a held key so a verifier gets per-request provenance. Biscuit tokens add offline attenuation with public-key verification: a holder can mint a strictly narrower token per task without an issuer round trip. These are the upgrade path once a bearer wake token is not enough. shipped RFCs
Cloud IMDS pattern All three clouds vend short-lived tokens from a link-local endpoint to workloads whose identity the platform attests. It is the canonical "ambient identity, no stored secret" shape, and its granularity limit is the VM, which is precisely the gap an entity layer must close. shipped
Secretless brokers CyberArk's Secretless Broker proved connection-level credential injection where the app never sees the secret. Vault Agent, notably, is not this: its template mode hands the app real secrets. Clawpatrol is the modern agent-flavored version with placeholders and protocol-aware injection. shipped
Envoy ext_authz / ext_proc The enforcement chassis. ext_authz sends the buffered request body to your gRPC policy server and lets an allow verdict inject or overwrite request headers, including Authorization, with an explicit fail-open or fail-closed switch. ext_proc adds streaming inspection and mutation of request and response bodies. Istio's docs supply the enforcement caveat: an egress gateway with no network-level default-deny is advisory. shipped
AI gateways Proof the three capabilities compose in one proxy: Cloudflare AI Gateway vaults provider keys, inspects both directions, and runs Llama Guard in the blocking path at a documented ~500ms with a fail-closed mode for blocking categories and no streaming support. LiteLLM adds ~2-8ms p95 proxy overhead with judge hooks that dominate latency. Kong ships regex and embedding classifiers in-path. These gate model traffic, not arbitrary egress, and none knows who the caller is beyond an API key. shipped
MCP and tool-call gateways agentgateway (Linux Foundation) authorizes individual MCP tool calls with CEL over JWT claims, the closest shipped thing to per-caller, per-call policy. The MCP authorization spec itself identifies client software and users, not agent instances, and its newest revision concedes its client-identity mechanism cannot prevent impersonation without additional attestation. shipped gateway, spec caveats
Microsoft Entra Agent ID Microsoft's productization of agent-as-directory-object: credential-less agent identities minted from a credential-holding blueprint, with an on-behalf-of exchange whose tokens carry the user as subject and the agent as actor. The core is documented GA, but the pieces this design would lean on (blueprint wizard, fmi_path exchange, agent Conditional Access) are preview-gated, the exchange parameter is proprietary, and third-party platforms using app-only Graph calls cap at 250 identities per blueprint. Treat it as the direction of travel, not a dependency. preview-gated
Google Agent Identity + Agent Gateway The closest shipped instance of agent-holds-no-token: per-agent SPIFFE X.509 identity, DPoP-bound tokens, and end-user credentials encrypted by an auth manager and decrypted only at the gateway. But "per-agent" means per deployed reasoning-engine resource, it works only on Google-hosted surfaces (the agent platform runtime and Gemini Enterprise), and the entire auth-manager component, the piece that provides the no-token property, is preview. Agent Substrate's SessionIdentity design (see the Substrate page) is the same two-layer pattern as a published design with an aspirational disclaimer. preview
Auth0 / Okta for agents Auth0's Token Vault (GA) brokers third-party tokens but returns the raw token to the agent at call time, which fails the no-tokens goal. Its CIBA async-authorization flow is good prior art for the human approval leg. Okta's Cross App Access is beta and rate-limited. Cisco's AGNTCY issues W3C verifiable credentials per agent at alpha maturity. shipped with caveats

Two conclusions fall out of the map. First, the egress-proxy shape you want is not exotic: the WIMSE architecture names it, clawpatrol and Google's gateway implement variants of it, and OWASP's agentic top-10 lists identity and privilege abuse as a first-class threat it addresses. Second, the entity-granularity layer is genuinely yours to build. Every attestation in the map stops at the process, pod, device, or deployed-agent resource. An Electric entity is finer than all of those, and the only party that can honestly attest which entity is acting is the system that woke it. That is chronicle. inferred

§The design: the wake carries the identity

Start from what already exists. Every webhook wake chronicle delivers is Ed25519-signed over the exact body plus a timestamp, verifiable against a JWKS chronicle publishes, and that signed body already binds the subscription id, a monotonic generation, a random wake id, the linked stream paths (which in the Electric integration means the entity), and the exact offset window. Generation fencing makes the triple (subscription, generation, wake id) unique and non-reusable on chronicle's side: claims, acks, and callbacks are rejected unless all fence components match, and a lease takeover rotates the fence. In other words, chronicle already produces a cryptographically verifiable statement: entity E was legitimately woken at generation G for offsets A to T at time t. What it lacks to function as a credential a third party can accept is small: no audience, no explicit expiry, no replay tracking at the verifier, and the raw signed body embeds a live callback bearer token you must not forward. The pull-wake path has no asymmetric artifact at all today; its tokens are HMAC that only chronicle can verify. primary

So the chronicle-side work is one additive extension, legal as a pure superset under §11.1's allowance for additional response fields, with §12.1 explicitly inviting authentication extensions: an optional wake_token field on the wake notification and on the claim response. It is a compact signed token over the existing JWKS keys carrying issuer, the entity stream path as subject, the egress gateway as audience, an expiry on the order of the lease TTL, and the generation and wake id as the replay key. The conformance suite reads both target shapes field by field (its strict deep-equal binds on the ack response, which is why chronicle's earlier in-band token-refresh field shipped as optional), so the extension is conformance-safe; chronicle has shipped exactly this pattern before. Two operational prerequisites come first, and they are prerequisites, not niceties: the Ed25519 private key currently lives base64-encoded in the shared data-plane Redis, where anything with Redis read access holds the signing capability, and no key-rotation code path exists even though the schema models one. Move the key to a KMS or dedicated secret and implement rotation before this key gates anyone's email. primary

The identity is then two layers, matching the pattern every system in section 4 converged on. The workload layer authenticates the runtime host to the gateway: mTLS client certificates, a WireGuard peer, or a SPIFFE SVID, whichever fits the deployment; this is device-grade and cheap. The entity layer rides each request: the runtime attaches the current wake token to every outbound call it makes on behalf of that entity, in a request header. The gateway verifies the workload channel, then verifies the wake token against chronicle's JWKS (cacheable, five-minute TTL), checks expiry, and checks a replay cache keyed on (subscription, generation, wake id). Only then does the request have an identity: this specific entity, in this specific wake. Policy can finally be per-entity because the policy engine finally knows the entity. inferred

Honesty about the chain: it is only as strong as its first link, and the first link today is the unauthenticated Electric-Principal header. Chronicle attests that a subscription was woken; the binding from subscription to entity is Electric's convention, established when the agents-server creates a per-entity dispatch subscription. A spoofed or compromised agents-server could mint subscriptions for arbitrary entities. So the design requires hardening entity and subscription creation first: implement authenticateRequest with real verification, disable the dev-principal fallback in production, and restrict who can create entities and subscriptions. Without that, per-entity egress identity is theater. inferred

The gateway chassis. Three options, in order of how much you build. First, run clawpatrol unchanged: you get vaulting, rules, the LLM judge, and human approval today, at device granularity, which is a real improvement over env vars and is the right tool for workstation agents immediately. Its limits for the fleet are structural: policy cannot see caller identity, there is no Graph OAuth plugin, and it is a workstation-first project nine weeks old. Second, extend clawpatrol: teach it to accept the wake token as a trusted request fact and expose identity in CEL. Upstream's own plugin discussions point this direction, but you would be tracking a fast-moving pre-1.0 codebase with a coarsening identity model. Third, build the gateway on Envoy: ext_authz with body buffering gives verdict-plus-header-injection in one shipped filter, fail-closed by default, and the custom gRPC policy server is where the chronicle-specific logic (JWKS verify, replay cache, CEL or Cedar rules, judge calls, token broker) lives in a few hundred lines of Go you own. For a server-side fleet we recommend the third, with clawpatrol kept as the model you are consciously reimplementing at a different trust boundary, and as the workstation tool. The judge and approval semantics to copy are its: deny-when-ambiguous prompts, approvals that time out closed, and replayable policy tests in CI. inferred

How requests reach the gateway. The CONNECT problem has three shipped resolutions: MITM with a distributed CA (clawpatrol's choice; breaks pinned clients, requires trust-store management), a TLS-terminating explicit proxy the client knowingly speaks plaintext-to-proxy with, or base-URL substitution where the agent calls the gateway as the API host (every shipped AI gateway's choice; zero CA distribution). Because you control the tool layer in an Electric runtime, base-URL substitution is the cheap and reliable start: tools and MCP transports point at the gateway, and the deny-all network policy makes the bypass path fail rather than leak. Transparent MITM is the later hardening for tools you do not control. inferred

🔗 Chronicle note

The division of labor keeps chronicle small. Chronicle's only new job is to attest wakes it already performs and sign tokens with keys it already publishes; the extension is optional fields, additive, and conformance-safe. Chronicle should decline the rest: it has no scopes, no consent screens, no audiences, and the protocol's own text says callback tokens "are not service JWTs." The gateway owns verification, custody, exchange, policy, and audit. If the gateway is down, wakes still deliver and handlers still run; what stops is egress, which is exactly the fail-closed you want from a security boundary.

§The worked example: send mail as me, hold nothing

Microsoft Graph is the sharpest test because Microsoft documents every constraint. The wiring below is the standard on-behalf-of (OBO) pattern; each step cites the mechanism that makes it work.

  1. Register the gateway's broker as one confidential client. The user consents once, to the broker, for delegated Mail.Send plus offline_access. The consent prompt is the standard Entra "Send mail as you" screen, and scopes can be added incrementally later without re-consenting what was already granted. Delegated Mail.Send is confined to what that user can already send; there is no tenant-wide blast radius to scope down.
  2. The broker keeps the refresh token; nothing else does. The response to the user's sign-in includes a refresh token bound to (user, broker client). Default lifetime is 90 days sliding; every use returns a replacement and the old one is not auto-revoked, so the broker must rotate-and-delete on each use. Store it encrypted under KMS keys, per tenant.
  3. A wake arrives; the entity asks for egress. The handler calls POST /v1.0/me/sendMail against the gateway with placeholder auth and its wake token. The gateway verifies workload channel, wake token, expiry, and replay, then runs policy: recipient and domain rules in CEL, size and rate limits, then the LLM judge over the parsed body with a deny-when-ambiguous prompt, then human approval if the rule says so.
  4. On allow, the broker mints the real credential. It redeems the stored refresh token for a roughly one-hour delegated Graph token scoped to Mail.Send and injects Authorization: Bearer on the forwarded request. Graph returns 202. The OBO documentation's own warning matches the design: never send middle-tier tokens anywhere but their intended audience, which here means tokens terminate at the gateway. The broker can itself authenticate to Entra without a stored secret via workload identity federation (an external JWT such as a SPIFFE JWT-SVID, matched by a federated identity credential), with two caveats: classic federated credentials cap at 20 per app, so per-entity federation is out, and the flexible claims-matching variant is preview. A certificate credential in KMS is the boring default.
  5. Revocation runs on two clocks, and the fast one is yours. The gateway is the instant kill: flip the entity's policy to deny and the next request dies at the verdict, with no Microsoft latency involved. The Entra kill is slower and coarser: disabling the broker's service principal or revoking the user's refresh tokens propagates to Graph within about 15 minutes under Continuous Access Evaluation (declare the cp1 client capability and honor claims challenges), and a plain bearer token otherwise lives out its hour. One documented wrinkle: revoking the consent grant itself is not in CAE's critical-event list, so treat SP disable and refresh-token revocation as the hard levers. If you ever use app-only Mail.Send (send as anyone), scope it with Exchange RBAC for Applications; its predecessor, Application Access Policies, is officially legacy.
  6. Audit every verdict. Log (entity, wake id, generation, request digest, matched rule, judge verdict, approver, Graph message id) per call. This is the record that makes "which entities can act as me, and what did they do" a query instead of a forensic project, and it is the record Entra cannot give you, since its audit logs show the broker's service principal, not your entities.

The user experience this buys: one consent screen ever, approvals in Slack only when a rule asks for them, per-entity revocation that takes effect on the next request, and an agent that can be prompt-injected into asking for anything but can only ever send what the policy layer, which inspects the request up to its configured body limits, allows. Size caps are themselves policy: reject what you cannot inspect. What it does not buy is protection from an approved-channel exfiltration: an email the policy allows can still carry data an injected agent chose to put there. That is a policy-content problem (recipient allowlists, judge prompts tuned for exfiltration shapes, volume anomaly limits), not an identity problem, and no identity design solves it. inferred

§What it costs, and what stays open

Latency. The rule tier is cheap: sub-millisecond policy evaluation is documented for Cedar and LiteLLM measures single-digit-millisecond proxy overhead at its p95. The judge tier is not: Cloudflare's ~500ms is the only published number for a model verdict in a blocking path, nobody publishes per-verdict cost, and Envoy's ext_proc streaming overhead is unmeasured in public sources. Design accordingly: rules always run, the judge runs on the calls a rule escalates, and the end-to-end p50/p99 gets measured in the first spike, not estimated. An OBO exchange adds an Entra round trip on token-cache miss; per-wake exchange rates will meet Entra throttling at fleet scale, so cache tokens for their lifetime keyed by (user, scope), not per wake. gap

Model traffic. The highest-volume egress an agent makes is to its model provider, it is latency-sensitive, and streaming responses break buffered judges (Cloudflare's guardrails do not support streaming). The pragmatic split: model calls go through the gateway for credential injection and rules (so model keys leave the agent process too) but skip the judge tier, while tool calls get the full treatment. Judging model traffic is its own project with its own products. inferred

Enforcement. Istio's egress documentation states the general truth: a gateway nothing forces traffic through is advisory. The design stands on deny-all egress at the sandbox or network layer with the gateway as the only route, and on clawpatrol's trust story, that an escaped flow holds only placeholders. Electric's default sandbox is unrestricted and its Docker allowlist mode is documented as not a boundary, so this is a deployment posture you must set, not a default you inherit. primary

The gateway concentrates the most valuable secrets. It holds refresh tokens for every user, the wake trust root, and, if you MITM, a CA key. That concentration is the price of the no-tokens-with-agent property; pay it deliberately: KMS-held keys, per-tenant encryption of vaulted tokens, no plaintext export path, its own audit stream, and an HA story before it gates anything that matters. Compare the alternative being replaced: the same secrets scattered as environment variables across every runtime host, with no policy and no audit. Concentration plus custody beats scatter. inferred

Human approval versus the lease clock. A Slack approval can take an hour; a wake lease defaults to 30 seconds and the wake token's expiry rides the lease. Do not hold the request open. On escalation, the gateway should deny-with-pending, record the approval request, and deliver the outcome as a new message to the entity's inbox, waking it to retry through the normal path with a fresh wake token. That is the CIBA shape from Auth0's async authorization, and it composes with chronicle's fencing instead of fighting it. inferred

The judge sees everything. Sending email bodies to a third-party model API for adjudication is itself sensitive egress. Decide its data-handling posture explicitly: a local classifier, a provider with a no-retention contract, or judge prompts that receive redacted bodies. And the judge can be evaded by encoding and chunking; treat it as one tier, backed by rules the attacker cannot argue with. inferred

Local development. The stack must degrade gracefully to a laptop: a permissive gateway mode with shadow-logged verdicts, a dev signing key chronicle already mints on boot, base-URL substitution so no CA ever enters a dev trust store, and a test tenant for Graph consent. Clawpatrol's replayable policy tests (clawpatrol test against recorded fixtures) are the CI pattern to copy for rules and judge prompts alike. inferred

§Actions this design produces

  1. Harden the first link. Implement authenticateRequest with real verification in the agents-server deployment, disable the dev-principal fallback outside development, and restrict entity and subscription creation. Every downstream identity claim inherits this link's strength.
  2. Fix key custody before keys gate egress. Move chronicle's Ed25519 signing key out of the shared data-plane Redis into a KMS or dedicated secret, and implement the rotation path the schema already models (active and retiring statuses exist; no code mints or retires a key today).
  3. Ship the wake-token superset behind a flag. Optional wake_token on the wake notification and claim response: audience, expiry, entity path, generation and wake id as the replay key, signed with the existing JWKS keys. Additive and conformance-safe. Propose it upstream as a §11 extension in the same message as the still-unfiled claim-granularity issue from the Substrate page's action list.
  4. Spike the gateway. Envoy ext_authz plus a small Go policy server: JWKS verification, replay cache, CEL rules, header injection, deny by default. Measure added p50/p99 with rules only, then with the judge tier. Run it in shadow mode against real traffic before it enforces anything.
  5. Wire the Graph broker. One confidential client, delegated Mail.Send + offline_access, cp1 declared, refresh tokens rotated on use and stored under KMS, tokens cached by (user, scope). Write the revocation runbook: policy kill at the gateway, SP disable and refresh-token revocation at Entra.
  6. Use clawpatrol where it fits today. Workstation and local-dev agents get it unchanged for vaulting, rules, and the judge. Watch its dynamic-peer RFC (#709) and OIDC enrollment PR (#753); if identity facts ever land in its rule conditions, the extend-clawpatrol option for the fleet reopens.
  7. Define the audit record now. (entity, wake id, generation, request digest, matched rule, judge verdict, approver, upstream result id), emitted per decision, kept tamper-evident. Retrofitting audit after an incident is the expensive order.
