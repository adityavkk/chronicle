Inside the runtime

@electric-ax/agents-runtime is the half that lives in your app. Its whole job is to make one function call — handler(ctx, wake) — feel like the entity has always been alive. This part traces a single wake through the machinery: webhook in, events out. (The runtime package ships readable declarations and bundles; the sibling agents-server ships full TypeScript source — file references below name the actual modules.)

1The webhook arrives

createRuntimeHandler({ baseUrl, serveEndpoint, registry }) produces the webhook host. It exposes a few adapters over one core: handleWebhookRequest(request) (fetch-native), onEnter(req, res) (Node http), and drainWakes() (graceful shutdown: wait for in-flight wakes). At startup, registerTypes() POSTs each defined type — description, creation/inbox/state schemas, permission grants, and crucially the serveEndpoint — to the server's /_electric/entity-types API.

The wake notification body tells the runtime everything it needs to be stateless:

  • who: the entity (type, URL, status, tags, spawn args, sandbox profile) and the acting principal,
  • what: the trigger (message_received, child finished, observed change, cron, timeout) plus the streams and offsets covering the new events,
  • how to respond: a callback URL and a claim token — the short-lived credential this wake must present to write to the entity's stream.

Payloads are Ed25519-signed by the server (webhook-signature header, verified against the server's JWKS at /__ds/jwks.json), so a public serve endpoint can't be fed forged wakes.

2Materialize: log → collections

Before your code runs, the runtime rebuilds the entity's world. createEntityStreamDB(streamUrl, customState) (in entity-stream-db) is StreamDB from Part 2 with the entity schema pre-merged: your declared collections plus the 20 built-ins (runs, steps, texts, textDeltas, toolCalls, reasoning, inbox, wakes, manifests, …). Each stream event is validated against the entity state schema (real Zod schemas — e.g. a text_delta event must carry {text_id, run_id, delta}) and applied to its collection. Two bookkeeping fields get stamped on every row:

  • _seq — global monotonic insertion order across all collections;
  • _timeline_order — a lexicographic stream:<offset>:<subOffset> token, so "the timeline" is just an ORDER BY, stable across replays.

Two details make this cheap in practice. Reads are offset-resumable — a warm runtime that has seen this entity before only reads the delta. And writes go out through a shared idempotent producer (writeEvent/flushWrites), so retried webhooks can't double-append.

The manifests collection deserves a note: it's the entity's resource table — one row per durable attachment of the entity to the world (kind: child | source | shared-state | schedule | effect | attachment | context | goal). When you ctx.spawn(), a child manifest row is what makes the relationship durable; when you observe(), a source row records it plus a replayWatermarks row tracking how far you've consumed it. "What is this entity connected to?" is a query, not tribal knowledge.

3Build the HandlerContext

createHandlerContext assembles the ctx object — and it's worth seeing it as three layers wired to different backends:

Local, synchronous — the DB
ctx.db.collections (reads), ctx.state.<coll> proxies (get/toArray/insert/update/delete), ctx.db.actions.<coll>_*, custom ctx.actions. Writes append change events via the producer — nothing talks to the server synchronously.
Remote, async — coordination
spawn / fork / forkSelf / observe / unobserve / send / mkdb / setTag — each is an HTTP call to the server's control plane, authenticated as this entity, recorded as a manifest row.
Wake-scoped — the session
ctx.wake (normalized), ctx.firstWake, ctx.signal (AbortSignal), ctx.sandbox, ctx.attachments, ctx.electricTools, goal and context-entry APIs, recordRun() / replyText() / sleep().

The raw WakeEvent ({source, type, fromOffset, toOffset, eventCount, payload}) is normalized into the two-case ctx.wake your handler switches on. Then the runtime simply calls your handler(ctx, wake) and awaits it.

4The model runner — agent.run() mechanically

The LLM loop is built on pi (@mariozechner/pi-agent-core + pi-ai) — a provider-agnostic agent core (Anthropic by default when model is a string; OpenAI, DeepSeek, Moonshot and others detectable). The runtime's contribution is the adapter on each side of that loop:

  1. Input adapter — timelineToMessages(db). Walks the materialized collections (inbox, runs, texts + assembled deltas, tool calls with results, reasoning) in _timeline_order and emits standard LLM history: user, assistant (text + toolCall blocks), toolResult messages. Attachments are hydrated into content blocks. The prompt is a projection of the log.
  2. The loop. pi streams a completion; tool calls are executed (each AgentTool.execute(id, args), sandbox-backed where relevant), results are appended to history, and the loop continues until the model stops or a tool returns terminate: true. Oversized tool results are truncated at 10k tokens with a visible placeholder. Timeouts, retries, and a ModelProviderError taxonomy (timeout / unreachable / auth / rate-limited) wrap the provider call.
  3. Output adapter — the outbound bridge. Every streaming event maps to a typed stream append, live: message_start → steps row; text_delta → texts + textDeltas; thinking → reasoning(+Deltas); tool call lifecycle → toolCalls (started → args_complete → executing → completed/failed, with args, result, duration); errors → errors; run brackets → runs. Per-step token usage (input / cached / output, context window) lands in steps.
✓ Why this shape is the payoff

Persistence, UI streaming, observability, and child-completion signaling are one write path. The runs row flipping to completed is the durable record, is what the UI renders, is the event that triggers a parent's runFinished wake. Nothing to keep in sync, because there's only one thing.

(One honest caveat from the reference docs: AgentRunResult.writes/toolCalls/usage returned by run() are currently placeholders — read outcomes from the collections, which are authoritative.)

5Context management: budgets and compaction

Long-lived entities accumulate long logs, so the runtime manages the projection into finite context windows:

  • ctx.useContext() replaces the default whole-timeline projection with a budgeted composition: named sources with token budgets and cache tiers (pinned / stable / slow-changing / volatile), plus auto-registered tools (loadTimelineRange, loadSourceRange, loadContextHistory) so the model can page in history on demand rather than carrying it all.
  • Durable context entries — ctx.insertContext / removeContext / setGoal / markGoalComplete write contextInserted/contextRemoved events, versioning the working context in the log itself.
  • Compaction thresholds — usage notices from 25% of the window; background compaction (checkpoint summarization) starts at 85%; a synchronous hard ceiling at 90%. Budget accounting counts uncachedInput + output, so provider-cached warm turns aren't double-counted.

6Sandboxes: where tool side-effects live

ctx.sandbox isolates what the LLM does (bash, file reads/writes/edits, fetch_url) from what your handler does. Three adapters: unrestricted (host FS — the trusted single-tenant dev default, explicitly not a boundary), docker (workdir /work in a digest-pinned container; cpu/memory/pid limits; optional gVisor runtime; network policy allow-all / deny-all / allowlist), and remote (e2b microVMs). Selection is per-spawn via profiles, with orthogonal knobs for scope (per-entity vs per-wake), persistence across idles, and ownership; sandboxes are lazily materialized, reused across an entity's queued wakes, and reaped/reattached by key. Write paths are containment-checked on every adapter.

This maps to the serverless-agents blog's "execution ladder": agent logic runs in the cheapest possible compute (your function), and full computers are summoned only for the tool calls that need one.

7Signals: interrupting a durable thing

Because entities aren't processes, "kill -9" needs a protocol. POST /_electric/entities/:type/:id/signal delivers POSIX-flavored signals; the runtime surfaces them mid-wake: SIGINT trips ctx.signal (the AbortSignal threaded into LLM calls, fetches, subprocesses) and aborts the current handler invocation; SIGHUP/SIGTERM/SIGUSR are delivered to ctx.onSignal(…) handlers; SIGSTOP/SIGCONT pause and resume wake processing (messages still queue); SIGKILL unregisters wakes and closes the entity's streams. Signals are themselves events — the signals collection records each delivery, outcome, and state transition.

8Done → idle → (maybe never again)

When the handler returns, the runtime flushes pending stream writes, then calls the wake's callback URL with done — releasing the claim and letting the server flip the entity to idle. The Node process (or lambda) that hosted the wake holds nothing the system needs: warm caches are an optimization, the log is the truth. The entity might be woken again in a millisecond, a month, or never — and the cost of "never" is a few kilobytes of storage.

What decides that next wake — and everything else on the other side of the webhook — is the server.
