Interaction journeys — every hop, drawn

Six sequence diagrams for the journeys everything else in this site describes in prose — with every system on the page: the browser, the agents server's authn/authz gate, the Postgres registry, the durable streams backend, the ephemeral handler invocation, and the model provider. Read them after FAQ 12 (who you actually talk to) and alongside Part 5 (what each hop is made of). Same conventions throughout: solid arrows are requests, dashed are async delivery — webhooks, streams, SSE.

§Messaging an agent — from send to streamed answer

The canonical happy path — the journey every other one specializes. A user messages an agent and watches the answer stream in: the message enters through the server's front door, never the streams backend directly (FAQ 12), where it is authenticated, authorized, and schema-validated before becoming an exactly-once append on the entity's log (Part 5 §4, FAQ 3). That single append does everything downstream: it projects into the registry, matches a wake registration, and becomes an Ed25519-signed webhook to your handler (Part 5 §5) — whose LLM loop appends token deltas back onto the same log as the run happens (Part 4 §4). The UI, meanwhile, is not waiting on a response body: it tails the log over observe()/SSE the entire time, so persisting the answer and streaming it to the screen are the same write (Part 1 §5).

  • The server is the front door. authenticateRequest establishes the principal, authorizeRequest applies external policy (cached with expiry), and inboxSchemas validate the payload before anything touches the log — clients never write to the streams backend directly (FAQ 12, Part 6 Q5).
  • Two semantics, one contract. Steps 6–7 are exactly-once (idempotent-producer dedupe on producerId/epoch/seq); steps 12–14 are at-least-once (retries, lease-expiry re-dispatch). The claim plus its claim-scoped write token (step 20) is what makes the second safe against the first (FAQ 3, Part 5 §6).
  • The par block is the payoff. The UI's SSE tail (steps 10–11) is live before the handler even wakes; every token delta appended in steps 20–21 arrives on that same offset-resumable connection. No push channel, no post-hoc save — the run's writes are simultaneously the durable record, the UI's feed, and the model's future context (Part 4 §4).
  • Kept deliberately generic: the wiki describes the EntityProjector as a background worker while wake evaluation runs inline in the append path — step 8 shows both as one registry hop rather than inventing their exact interleaving.

§Spawning and joining sub-agents — delegation

Delegation is the coordination move the rest of Part 3 builds toward: a parent wakes, fans work out to child entities, and joins their results — with no process anywhere blocked on the answer. This journey follows one fan-out end to end: the spawn-once guard against redelivered wakes (Q&A #3), ctx.spawn minting each child as a full public entity (FAQ 11) while registering a runFinished observation on the way in, and the parent's gate-on-durable-state join — the hybrid control-flow idiom of Part 3 §6. Watch what the parent never does: await. It spawns, it sleeps, and each child's completion arrives later as a fresh wake carrying finished_child in its payload (Part 3 §5).

  • The guard exists because delivery is at-least-once. Deterministic child IDs plus the manifests check (Q&A #3) make a redelivered wake find the existing child and send rather than spawn a duplicate — spawn-idempotency lives in durable state, not in memory.
  • Children are not lightweight tasks. Each spawn creates a full entity — its own streams, URL, authz surface, and lifecycle (FAQ 11) — so results reach the parent not as return values but as finished_child wakes feeding its own durable state.
  • The par block is concurrency with no coordinator running. Between arrows 5 and 15 the parent is rows and log entries; when both children finish near-simultaneously, claims (Part 5 §6) serialize the finishes into two orderly wakes (FAQ 2) — which is what makes the have-all-children-reported gate race-free without locks.
  • Token economics of the gate. Of the parent's three wakes only the last runs a model call — the middle one is a pure durable-state check that sleeps for free, the same shape as the judge's five-wakes-two-LLM-runs table in Part 3 §6.

§Forking an entity — branching a timeline

Everywhere else in this wiki the log is the entity's memory; fork() treats it as a branch point. Because an entity's whole state is its history, copying the log at a point copies the agent — ctx.fork(url, id) / ctx.forkSelf(id) branch a new entity from an existing one's history, and streams fork without rewriting (Part 3 §5). The recurring triggers: retry from a known-good point or what-if exploration — replay any entity, branch its timeline, explore the alternative (Q&A #1); recovering a wedged agent — "recovery by branching rather than surgery" (FAQ 5); and the fork-and-retire schema migration, where you point traffic at the fork and TTL the ancestor (FAQ 7, FAQ 4). The fork call itself is one gated control-plane request; the structure worth diagramming sits before it (why you branch) and after it (two live timelines diverging).

  • The alt block is the whole case for forks: wedge recovery, what-if retry, and big-bang migration all reduce to the same single call, because branching the log is branching the agent — there is no separate export/import of "state" (FAQ 5).
  • fork is an ordinary entity-level permission verb alongside read / write / signal (Q&A #5), served by the entities-router with every other gated route (Part 5 §3); when a handler calls ctx.fork() it is an authenticated control-plane HTTP call recorded as a manifest row (Part 4).
  • The wiki does not document the server's internal fork mechanics — the fork hop (arrows 5–8) stays generic by design: one gated request, the shared-history stream, its registry row, the new URL. The only visible trace is the append guard, which rejects writes to stopped or fork-locked entities (Part 5 §4).
  • The fork is a full entity — its own registry row, grants, offsets, lifecycle — which is exactly why migration rollback is trivial: "keep using the original" until the ancestor's TTL fires (FAQ 7).

§Watching an agent live — observe, disconnect, resume

An agent's session is not a response you await — it is a log you watch. This journey follows a browser tab attaching to a live agent with observe(entity(url)): an authorized catch-up read through the agents server's sync surface (FAQ 12), incremental materialization into TanStack DB collections via the state protocol (Part 2 §7–8), then a live SSE tail — until the network drops mid-run, and the tab resumes at the cost of exactly one request. The punchline is what is absent: no reconnection protocol, no server-side session, no consumer group — the only recovery state is the Stream-Next-Offset the consumer already holds (Part 2 §3).

  • The disconnect is a non-event. Consumer position is client-held data, not server-side session state (Part 2 §3) — the tab recovers exactly the way a crashed handler or a second browser tab would: present the last offset, catch up, go live.
  • Catch-up and live are one request shape (Part 2 §4): messages 1 and 7 differ only by live=sse, so the UI never stitches "load history" onto "subscribe" or handles the gap between them — the protocol does it.
  • Resumability is what makes fan-out a caching problem: reads at a given offset always return the same bytes, hence ETags + conditional GET and Stream-Cursor against stale long-poll loops (Part 2 §6); only volatile reads (offset=now, HEAD) are no-store.
  • Same verb, two consumers: an entity observes another entity with the same observe(entity(url)) plus opts.wake — invoked when matching events land rather than holding a socket (Part 3 §5, §7). One drawn simplification: the wiki describes the server's SSE surface only as a pass-through to the streams backend (Part 5 §3), so the internal delivery hop (messages 11–12) is kept generic rather than inventing mechanics.

§A handler crashes mid-wake — recovery and fencing

This journey plays the first row of FAQ 5's failure table as a film: a handler dies mid-wake — process crash or lambda timeout — after streaming part of its work into the log. Nothing that follows is a special mode. The partial work was durable the moment it was appended, through the exactly-once producer path (Part 2 §5); the claim's lease is the only failure detector (Part 5 §6); and the re-dispatched invocation simply does what every invocation does — re-materialize, re-run, guard (FAQ 5). The one genuinely new event is the zombie limping back to append, and that is answered with a 403, not a data race.

  • The crash is detected by silence, not by a signal. Nothing supervises invocation A's process — the only failure detector is the claim's lease expiring and the dispatch-recovery loop reclaiming it (Part 5 §6). A hung lambda and a dead one look identical, and are handled identically.
  • Steps 7–8 are why nothing is lost. The partial tokens and the tool result became durable as they were appended — exactly-once via the idempotent producer, so even a retried batch from the dying run couldn't double-append (Part 2 §5).
  • Step 12 plus the guard note are why nothing is redone. Invocation B gets no clean slate — it materializes a world that already contains A's work, and the same guard-on-durable-state idiom every wake uses (FAQ 3) skips what's done. What "continue the run" means at step 13 is ordinary handler logic — the wiki specifies the contract (at-least-once delivery, re-entrant handlers), not a resumption mechanism.
  • The zombie is rejected twice over. Its write token was superseded at reclaim — only the current claim holder may append (Part 5 §4) — and its producer epoch is stale, fenced with a 403 (Part 2 §5). One-active-wake is enforced at the data layer, not by convention.

§Intervening in a running agent — steer, queue, signals

An entity is single-threaded by construction — the log orders all writers, claims guarantee at most one active wake, and wakes coalesce (FAQ 2) — so input that arrives mid-run never interrupts by accident. Whether it interrupts on purpose is the sender's choice: send modes decide if a message waits its turn (queued, the default) or is injected into the loop already in flight (steer — "actually, stop and do X"), while the signal API (Part 4 §7) gives operators POSIX-flavored control — abort, quarantine, kill — over a thing that isn't a process. This journey follows /assistant/a1 through a long agent.run() loop as each kind of intervention lands, ending with the recovery move for an agent that is wedged rather than crashed: fork() the pre-wedged history and retire the original (FAQ 5).

  • "Queued" is not a separate queue. The message is an ordinary validated append (Part 5 §4); the queuing behavior emerges from claims (at most one active wake per entity) plus coalescing — five messages landing mid-run become one re-invocation whose window (arrows 4–9) already contains all five.
  • Steer shares the whole append pipeline. The send itself (arrows 10–11) goes through the same authn/validation/idempotent-producer path as any send; the wiki specifies the semantics — injection into the currently running loop — but is silent on the wire mechanics of delivery into a live invocation, so arrow 12 is deliberately generic.
  • SIGINT aborts through ctx.signal — the AbortSignal threaded into LLM calls, fetches, and subprocesses (Part 4 §7). Because every append before the abort was already durable, an abort loses nothing written so far.
  • fork() is the escape hatch beyond signals: the entity's whole state is its log, so branching the pre-wedge history is branching the whole agent — recovery by branching rather than surgery (FAQ 5).
