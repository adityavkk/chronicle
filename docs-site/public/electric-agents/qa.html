Question 1
What attributes does an electric agent have that differentiate it from an actor with an LLM loop inside it?
TL;DR
An actor is compute that owns hidden state; an electric agent is state that summons compute. Concretely, an electric agent ≈ a virtual actor + event sourcing + durable pub/sub + time-travel, collapsed into one HTTP-addressable primitive — and that collapse, not any single feature, is the differentiator.

The comparison is apt — the surface vocabulary is nearly identical: identity, spawn, send, mailbox-ish inbox, supervision-ish parents. If you built "an actor with an LLM loop inside" (Akka/Erlang style, or a Cloudflare Durable Object, or an Orleans grain), you'd have something that demos the same. The differences are structural:

DimensionActor + LLM loopElectric agent (entity)
Where state lives Private, in-memory, behind the actor. Persistence (event sourcing, grain storage) is an add-on you implement per actor. Externalized by construction. The entity's only memory is its durable stream. There is no private state to lose, snapshot, or forget to persist — the LLM tokens themselves land in the log as they stream.
Relationship to compute Bound to a process/runtime node. Even "virtual actors" (Orleans) activate somewhere and pin state to that activation; the runtime that hosts actors must itself be deployed and kept alive. No residency at all. Between wakes an agent is rows and log entries. Any stateless function anywhere that can speak HTTP to the server can host the next wake. Redeploys, crashes, and region moves are non-events.
Introspection Opaque. To know what an actor is doing you must define messages for asking, or bolt on telemetry. Its history is gone unless you logged it. Transparent by default. Any authorized party — a parent, a monitor entity, a dashboard, you with curl — can observe() the agent's stream and materialize its full timeline: every token, tool call, state transition, forever. No API had to be designed for this.
Messaging semantics Mailbox: typically at-most-once, consumed-once, unordered across senders unless you work for it. A message processed is a message gone. Log: durable, totally ordered, multi-consumer. The same inbox event is simultaneously the delivery, the audit record, and part of the LLM's future context. Exactly-once appends via producer fencing.
Waiting An actor awaiting five children holds resources (or you hand-roll persistent timers/reminders). Waiting is free and declarative: wake conditions (runFinished, collection changes, cron, timeouts) are data in the server. A judge "waiting" for rebuttals is zero compute.
History operations None inherent. Replaying or branching an actor's past is a research project. Native: replay any entity from offset zero; fork() an agent — its whole history — at a point and explore an alternative timeline; audit by reading.
Reach Actor refs are meaningful inside the actor system. Browsers, CLIs, other stacks need gateways. The address is a URL and the protocol is HTTP. A browser tab is a first-class peer of the agent — same stream, same offsets, CDN-cacheable fan-out.

Two of these deserve emphasis because they specifically matter for LLM agents:

  • The context problem is the persistence problem. An LLM agent's "state" is largely its conversation history — which is exactly what must be rebuilt after any interruption, streamed to users, audited later, and fed back as context. In the actor model those are four different mechanisms (state, transport, logging, prompt assembly). Here they are one log with four readers. timelineToMessages(db) — the prompt is literally a query over the same data the UI renders (Part 4 §4).
  • Dynamic topology without interface design. The serverless-agents post's Kleppmann-inspired point ("turning the agent inside out"): actor coordination requires predefined message protocols between parties. Electric agents coordinate by observing each other's externalized state — the walkthrough's manager doesn't ask the judge for status via a message type someone designed; it reads judge.db.collections.debate.get('current').phase. New observers join without anyone's code changing.
⚖ To be fair to actors

Mature actor systems can assemble most single rows of that table: Orleans gives activation-on-demand, Akka gives event sourcing, Durable Objects give a persistent mailbox. What none of them give is the unification — one primitive that is simultaneously the state store, the transport, the subscription, the audit log, and the UI feed, addressable from a browser. The cost side of the trade: latency (every hop is HTTP + log append, not an in-memory enqueue — fine for LLM-paced work, wrong for microsecond actor workloads) and losing in-process locality. Electric Agents bets that agent workloads are I/O-bound and observation-hungry, so the trade is worth it.

Question 2
Why not just use a shared KV store to share data between agents instead of these stream entities?
TL;DR
Because a KV store answers only "what is the value now?" — and almost everything agents need from shared data is something else: what changed, in what order, since when, who should react, and what happened before. A stream answers all of those, and gives you the KV view for free as its last-write-wins projection. The reverse is not true: a KV store upgraded to answer them becomes a stream.

Walk through what shared agent state actually has to do, using the debate blackboard as the running example:

  1. Notify, don't get polled. The judge must react when a debater writes an argument. With KV, someone polls (GET argument-a in a loop — compute while waiting, latency floor, rate limits). With streams, wake conditions are declarative server-side data: wake: { on: 'change', collections: ['arguments'] } — zero compute until the change arrives. The moment you add a "changefeed" to your KV store to fix this, you have started building the log.
  2. Order concurrent writers. Two debaters finish near-simultaneously; the judge's logic ("when both arguments are in, advance the phase") needs a consistent view of the sequence, and its own phase transition must not race with itself on redelivered wakes. A KV store gives per-key last-write-wins with no cross-key ordering; you end up bolting on versions, CAS loops, or locks. A stream is a total order — every consumer sees the same history in the same sequence, and idempotent producers + write tokens fence duplicate/zombie writers at the door (Parts 2 §5, 5 §6).
  3. Resume after dying. Every participant here is ephemeral compute. A KV consumer that restarts knows only "current values" — it can't tell what it already processed. A stream consumer holds one offset and resumes exactly; the runtime's replayWatermarks collection is precisely this, per observed source.
  4. Carry the in-between. Agent data isn't only end states — it's streams of tokens, sequences of tool calls, progressions of phases. KV overwrites destroy the middle (write token-by-token and each write obliterates the last; write-at-end and you've lost streaming). The log is the middle: transport and storage in one write (Part 1 §2).
  5. Remember. Why did the judge rule this way? What did debater B's first draft say? Who set phase='done' and when? KV: gone, overwritten. Log: GET ?offset=-1. Audit, debugging, evals, and fork() (branch the whole debate and re-run it differently) all fall out of retained history.
  6. Fan out cheaply. A thousand dashboards watching one agent would hammer a KV store with polls. Offset-immutable stream reads collapse in CDNs — "10,000 viewers at the same offset become one upstream request" (Part 2 §6).

And here is the kicker that makes the question dissolve: the KV store is still there. The state protocol's materialization rule — apply change events in order, last write wins per (type, key) — means ctx.state.debate.get('current') is a KV read. It's just a KV whose value is derived from, and always consistent with, an ordered, subscribable, replayable history. You write board.findings.insert(…) and read board.findings.get(key) exactly as you would with Redis — the stream underneath is what makes the other five requirements free rather than five more systems.

⚠ When KV genuinely is enough

Ephemeral, unordered, single-writer, nobody-reacts data — a rate-limit counter, a cache of embeddings — doesn't need a log, and nothing stops an agent's tools from using Redis for it. The framework's claim is narrower than "streams beat KV": it's that coordination state between agents — the state that drives wakes, gates, and UIs — is exactly the state that needs ordering, history, and subscriptions.

Question 3
What role is TanStack DB playing here? Show me examples. And why not just fold over the events?
TL;DR
A fold gives you state; TanStack DB gives you a database over the fold — incremental live queries, reactive subscriptions, typed collections, and an optimistic write path with confirmation. The fold is still in there (it's literally the sync layer), but folding is the easy 20%. TanStack DB is the other 80% you'd otherwise hand-roll: query maintenance, not state maintenance.

The role, precisely

TanStack DB is an embedded, reactive client database built on differential dataflow (its engine is d2ts — also an ElectricSQL project). In this stack it appears in three places doing one job — materializing streams into something programmable:

  • In the handler: ctx.db.collections.* / ctx.state.* — the entity's log as typed collections (Part 4 §2).
  • In the browser: client.observe(entity(url)) → the same collections, live over SSE, driving useChat and any custom UI.
  • Between entities: shared StreamDBs (mkdb/observe(db(…))) and observed handles — one entity querying another's state.

Same schema, same query language, same reactivity model in all three. That uniformity is itself part of the answer.

Examples

1. A gate in a handler — point read of materialized state (the walkthrough's manager, deciding whether the judge's debate is actually finished):

const judge = await ctx.observe(entity(finishedChild.url))
const debate = judge.db.collections.debate.get('current')
if (debate?.phase !== 'done') return ctx.sleep()   // not yet — costs nothing

2. A real query — "did I already spawn this child?" (from the runtime's own query skill; the manifests collection is the entity's durable resource table):

import { manifestChildKey } from '@electric-ax/agents-runtime'
import { eq, queryOnce } from '@durable-streams/state/db'

const child = await queryOnce((q) =>
  q.from({ manifests: ctx.db.collections.manifests })
   .where(({ manifests }) => eq(manifests.key, manifestChildKey('worker', 'child-1')))
   .findOne()
)
if (child?.kind === 'child') ctx.send(child.entity_url, payload)
else await ctx.spawn('worker', 'child-1', args)

3. A live UI — the chat timeline as an incrementally-maintained join:

const db = await client.observe(entity('/assistant/a1'))   // SSE-tailed

// useChat is sugar over a live query joining runs + inbox + wakes + entities,
// assembling textDeltas into texts, ordered by _timeline_order:
const chat = useChat(db)
chat.runs[0].texts[0].text      // grows token-by-token as delta events arrive
chat.state === 'working'        // drives the streaming cursor

// or roll your own live view — e.g. a tool-call audit panel:
const q = useLiveQuery((q) =>
  q.from({ calls: db.collections.toolCalls })
   .where(({ calls }) => eq(calls.status, 'failed')))

4. The write path — optimistic, log-confirmed (what ctx.state.*.insert and UI actions compile down to):

addFinding: {
  onMutate: (f) => db.collections.findings.insert(f),        // instant, local
  mutationFn: async (f) => {
    const txid = crypto.randomUUID()
    await stream.append(schema.findings.insert({ value: f, headers: { txid } }))
    await db.utils.awaitTxId(txid)   // confirmed when it round-trips the log
  },
}

OK — but why not just fold?

You absolutely can fold — @durable-streams/state ships the fold as MaterializedState: ~a hundred lines, Map<type, Map<key, value>>, apply events in order. If all you needed were example 1, the fold would do. The gap appears at examples 2–4, and it's the gap between state and queries over state:

NeedHand-rolled foldTanStack DB collections
Derived views that stay fresh (timeline join, "failed tool calls", per-run token totals) Recompute the derivation on every event — O(data) per event — or maintain each view incrementally by hand, which means writing a bespoke delta-propagation engine per view (and getting deletes, updates and join re-evaluation right). Differential dataflow maintains registered queries in O(change). The chat UI does not re-scan the log per token; the delta flows through the join.
Reactivity (something changed → exactly the affected subscribers re-render/re-evaluate) You invent a listener/emitter layer, per-key vs per-type granularity, batching so a burst of 200 deltas doesn't cause 200 renders… Native: collections are subscribable; the stream dispatcher commits per batch, so consumers see snapshot-consistent transitions at upToDate boundaries.
Writes A fold is read-only by definition. The write path — optimistic apply, append with txid, reconcile when the authoritative event returns, roll back on failure, dedupe replays (the runtime downgrades re-delivered inserts to updates so reconnects don't crash on duplicate keys) — is a second system you now design. createOptimisticAction + awaitTxId is exactly that system, already correct.
Types & validation A Map<string, unknown>; schema enforcement and key derivation are on you. Standard Schema (Zod/TypeBox) per collection; rows are typed end-to-end from handler to React.
One model everywhere Your server fold and your UI state layer diverge; "what the agent sees" ≠ "what the user sees". Handler, browser, observer entity all materialize the same schema the same way. useChat and timelineToMessages are queries over the same collections.

So the honest formulation: the fold is the sync config; TanStack DB is the database that makes the folded result worth having. The framework folds events into collections (that's the state protocol), then TanStack DB provides what folding alone never gives you — incremental queries, reactive subscriptions, and a principled optimistic write loop — uniformly across agents, UIs, and observers. Given that agent UX is fundamentally "many live views over one fast-moving log", that's not a convenience; it's the load-bearing layer.

Question 4
What does the deployment topology look like? Where do my agent handlers get deployed? Is this a serverless runtime?
TL;DR
Your handlers deploy inside your own app — they're routes behind one webhook endpoint, so they go wherever your app goes: a Node server, a container, or serverless/edge functions. The always-on part is the agents server + its storage (Postgres, Electric, a streams backend), run via Docker in dev, self-hosted or Electric Cloud in prod. It's "serverless-ready" rather than a serverless runtime: the architecture is specifically designed so agent loops can be stateless functions that scale to zero — but a plain long-lived server works identically, and a pull-based "runner" mode exists for compute the server can't reach.

"Is this a serverless runtime?"

Three precise statements instead of one fuzzy yes:

  • The programming model is serverless-shaped. Handlers are stateless, webhook-invoked, and forbidden from blocking across wakes (no "await the child in-process"). All durability lives behind the API. That's exactly the contract FaaS platforms need — the serverless-agents post is explicit that this is the point: agents as data, loops as stateless functions, scale to zero, with the ~5ms/2MB economics of function invocation rather than the ~125ms/128MB of resurrecting a sandbox VM per agent.
  • It is not only serverless. The same code runs in a boring long-lived Node service (the walkthrough's Hono app is one), and the runner model exists precisely for compute that can't accept inbound webhooks. Push vs. pull is a per-entity-type dispatch policy, not an architecture commitment.
  • The platform itself is not serverless. Somebody runs the always-on plane — you (a compose file's worth of containers) or Electric Cloud. "Serverless" here describes your half of the system.
⚠ Serverless fine print

Wakes that run LLM loops are long-lived HTTP handlers — minutes, sometimes. On FaaS that means: configure generous function timeouts, remember interrupted wakes are re-dispatched (claims expire, delivery is at-least-once — your idempotent handler absorbs this), and note the blog's own edge-deployment framing ("deploy your agents as serverless functions") assumes the loop's I/O-bound profile. For very long tool executions, push them into sandboxes or runners rather than holding the function open.

Question 5
How can authn/authz be handled?
TL;DR
Authn is pluggable and yours; authz is built in and layered. Every request acts as a principal (user: / agent: / service: / system:). You establish who that is — via an authenticateRequest hook or a trusted gateway setting the Electric-Principal header. From there the server enforces: creator rights + explicit permission grants on entities and types (8 verbs, propagation, expiry), an optional external policy hook for ABAC, claim-scoped write tokens on the stream plane, signed webhooks on the dispatch plane, row-level scoping on the sync plane, and tenant isolation underneath it all.

Authentication — establishing the principal

Identity is a string key <kind>:<id>, canonicalized to an addressable entity URL (user:sam → /principal/user%3Asam). Three ways it enters a request, in trust order:

  1. An authenticateRequest hook injected into the server: receives the raw request, verifies your real credential (JWT, session cookie, API key), returns the principal. The right place in self-hosted production.
  2. A trusted gateway that terminates auth and sets Electric-Principal before forwarding. Important: the server treats that header as trusted input — it must never be reachable with client-controlled headers, and CORS is wide open by default, so a fronting proxy is part of the production design, not an option.
  3. Dev fallback — system:dev-local when running insecure/dev/embedded; production conditions (external streams, NODE_ENV=production, no ELECTRIC_INSECURE) hard-require a principal (401 otherwise).

Agents are principals too: a wake executes as its entity (agent:/judge/debate-7), so agent-to-agent calls (spawn, send, observe) flow through exactly the same authz as user calls — there is no privileged "inside the framework" path. (Except the explicit one: system:* principals used by internal machinery bypass checks.)

Authorization — five layers

LayerMechanismProtects
1 · Grants Creator gets full rights; everything else is explicit rows: entity-level verbs read · write · delete · signal · fork · schedule · spawn · manage, type-level spawn · manage. Grants target a principal or a whole kind, can propagate (self/descendants, copy_to_children — so a whole agent subtree inherits access), and can carry expires_at. Declared statically on entity types (permissionGrants) or managed at runtime (POST /:type/:id/grants). The UI's view/chat/manage roles are bundles of these. The control plane: who may see, message, spawn, signal, or administer each entity.
2 · Policy hook Optional authorizeRequest callback consulted on decisions — plug in OPA/ABAC/your rules; allow/deny results cached per (tenant, principal, verb, resource) with expiry. Organization-specific rules the grant tables can't express.
3 · Write tokens Raw stream appends require a claim-scoped token (electric-claim-token), minted per wake/spawn, released on done. Collection writes from outside additionally require the collection to be declared externallyWritable with an operations allow-list. The data plane: only the entity's current claim holder can write its log; UIs can't forge agent events.
4 · Signed webhooks Ed25519 signatures on wake payloads, verified by the runtime against the server's JWKS (on by default). The dispatch plane: your public serve endpoint can't be fed forged wakes.
5 · Scoped sync + tenancy The Electric proxy rewrites every shape request: table allow-list, fixed columns, injected where deriving from the caller's grants + tenant. All storage is tenant-keyed; stream paths are tenant-prefixed at the backend boundary. The read plane: live queries only ever see rows the principal could read; tenants can't see each other at all.

A concrete production recipe

// 1. Front the agents server; verify your real auth there.
const server = new ElectricAgentsServer({
  authenticateRequest: async (req) => {
    const claims = await verifyJwt(req.headers.get('authorization'))
    return { key: `user:${claims.sub}` }        // → the acting principal
  },
  authorizeRequest: opaPolicyHook,               // optional ABAC layer
})

// 2. Let entity types declare their own access on registration:
registry.define('support-agent', {
  permissionGrants: [
    { subject_kind: 'principal_kind', subject_value: 'user', permission: 'spawn' },
  ],
  // support tickets: creator (the user) chats; ops team gets visibility via
  // runtime grants with propagation to descendants (the agent's sub-workers)
  …
})

// 3. Users hit YOUR app; your app talks to the agents server as them.
//    Agents talk to each other as themselves. Secrets never enter prompts
//    or spawn args (they're persisted in the log forever) — keep credentials
//    in handler/tool closures, which live only in your deployment.

That last parenthetical is the one cultural rule the docs insist on alongside the mechanisms: the log is durable and observable by design, so anything written to it — prompts, args, messages — should be treated as visible to everyone who can ever read the entity. Capability secrets belong in your app code (tools), not in entity data.
