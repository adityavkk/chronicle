Case Study: Amp's Orbs on Durable Streams

On June 30, 2026, Amp shipped orbs. An orb is a remote machine that runs one agent thread, and you can control it from the same interface as your local agents. This page does three things. It reports what Amp actually documents about orbs and the local to orb handoff, with quotes and links. It compresses the prior art on session portability into one table. It then asks a design question: if you built an orbs-like product on the Electric Agents stack this wiki describes, which primitives would carry the load, where would the mapping strain, and what would you have to build.

⚠ This page is analysis, not documentation of Amp

Amp has not published its internals. Sections 1 and 2 report only what Amp's public pages say, and every claim there links to its source. Everything from section 4 onward is a design exercise on the Electric Agents primitives from Parts 1 to 5 of this wiki. It describes how we would build an orbs-like system, not how Amp built theirs. Where a claim is an inference it carries an inferred label. Where the evidence does not exist it carries a gap label.

§What Amp documents

The launch post defines the product in two sentences: "Orbs are machines where agents can run without supervision. When you create a new thread you get a fresh orb that contains your code, plugins, and tools the agent might need" (Agents in Orbs). The manual adds the isolation boundary: "Each Amp thread started from ampcode.com in an orb gets its own orb." One thread maps to one machine.

The machine is concrete. An orb runs Debian 12 with 32 GB of memory and 16 cores, and Amp says resource customization will come later. It costs $1.66 per hour, or $2.48 per hour for enterprise workspaces, billed by the minute. A paused orb costs nothing. The base image ships authenticated gh and amp, Git and SSH, PostgreSQL 17 and Redis, tmux, ripgrep, Node.js, Python, and more, and the Amp system prompt tells the agent it is inside an orb and that "nearly everything is an apt-get install away" (Putting an Agent in an Orb). The security page says "e2b provides ephemeral compute instances for Amp sandboxes." That line uses the word sandboxes, not orbs. Thorsten Ball's note calls the orb "the sandbox" when describing snapshotting, so reading the e2b line as the orb substrate is well supported, but it is still our reading. inferred

The session object is the thread, and a thread is the same thing as a session. The CLI's stream-json output reports the thread ID, shaped T-<uuid>, as the session_id (streaming JSON post). The security page enumerates what a thread contains: "user messages, LLM responses, snippets of or entire code files used as context for the LLM requests, tool call results, and attachments." The server is the source of truth for it: "Amp Server stores these conversations in its PostgreSQL database in Google Cloud Platform" (security page). The client keeps a local thread history as well.

Two kinds of state are explicitly not in the thread. File edits are workspace state. The Neo rebuild removed rollback because "if the agent wrote and ran code that generated files, we didn't keep track of that without elaborate snapshotting" (Neo, "What's Gone"). Terminal state is environment state. The orb terminal "is running in a tmux session, so your agent can see what you see in the terminal" (manual). The codebase is also excluded: "The Amp Client and Amp Server do not see, store, clone, or index the entire codebase." The orb clones the repo itself with the authenticated GitHub CLI.

§The local to orb handoff, exactly as documented

Amp documents three moves between a laptop and an orb. None of them migrates a live execution environment. Each move transfers a different thing.

MoveSurfaceWhat travelsWhat stays behind
1 · Start a new thread in an orb, from local amp -ox "prompt", the TUI project picker, or ampcode.com Nothing from the laptop. "Each orb starts with a fresh clone of your repository" (manual/orbs), plus project env vars and secrets. Uncommitted local changes, local processes, anything not pushed to the git remote.
2 · Mirror orb changes down to the laptop amp sync <thread-id> File changes only: "mirror an orb thread's changes into your local checkout while the agent keeps working remotely" (manual/orbs). The transport is not documented. gap The orb's processes, its tmux sessions, its PostgreSQL and Redis contents, installed packages. The agent and the thread stay in the orb.
3 · Control any thread from any device Remote control on web, mobile, and the CLI sidebar Control and a live view. "Remote control lets you continue a running Amp CLI thread from ampcode.com" (manual), with live updates, queue, dequeue, and cancel. The execution environment. A local thread keeps executing on the laptop, and an orb thread keeps executing in the orb.
⚠ The move people assume exists is not documented

The phrase "start locally and push to orb" appears in no primary source we could find, and no Amp page describes migrating an existing thread's execution environment between a laptop and an orb, in either direction. What moves in the documented product is control and file diffs. What stays is the environment. What resumes is the server-held thread. gap

The architecture that makes the control handoff cheap is stated plainly. Amp Server, not the client, drives the loop: the client "communicates with and executes tools as requested by Amp Server" (security page). Four weeks before orbs, Amp wrote that "Amp is now a distributed system with durable execution for the agent loop" (Agents, Everywhere). The documented transport is WebSockets: the firewall allowlist names production.ampworkers.com "for secure WebSocket connections used by the Amp Client." Beyond that, the public record only hints. A dev setup script names THREAD_ACTORS_SERVICE_SECRET and THREAD_ACTORS_WEBSOCKET_JWT_SECRET, and the repo has lib/thread-client and lib/thread-protocol directories. Per-thread actor processes reached over authenticated WebSockets would fit those names, but Amp has not said so. inferred

§Prior art: four ways to move a session

We surveyed twelve systems that move, or refuse to move, a running session: tmux, mosh, Jupyter, VS Code Live Share, GitHub Codespaces, Claude Code (teleport and remote control), OpenAI Codex cloud tasks, Devin, Cloudflare Durable Objects, Fly.io suspend, Erlang/OTP, and CRDT systems (Automerge, Yjs). Four strategies cover all of them. The taxonomy is our synthesis of those primary sources, so treat the grouping as analysis. inferred

StrategySystemsWhat movesWhat it keepsWhat it gives up
Re-attach. State stays pinned to one runtime. Clients disconnect and reconnect a view. tmux, mosh, Jupyter frontends, Live Share, Claude Code remote control Only the viewport. Everything: memory, open sockets, GPU state. Nothing moves, so nothing breaks. The host is a single point of failure. When the host process dies, the session dies.
Snapshot the runtime image. Serialize the machine's disk or memory. Fly suspend, Codespaces stop and resume, Devin machine snapshots, Codespaces prebuilds A disk or memory image, mostly in place. The only strategy that preserves live memory. Fly captures CPU registers, memory, and open file handles. The least portable. Fly snapshots die on deploy and on host migration, exclude GPUs, and resume into dead TCP connections and skewed clocks.
Externalize and rehydrate. Durable storage is the session. Compute is disposable and rebuilt from it. Durable Objects, BEAM failover and takeover Nothing. A new instance reloads from storage. Survives instance death by construction. Loses anything not written down. Durable Objects state that in-memory state does not survive eviction.
Log and replay. The session is an ordered record. Any host reconstructs state by reading it. Temporal, Claude Code teleport, Codex diffs, CRDT change histories, notebooks An ordered record of inputs and results. Resume at any offset, cheap fork, many readers, a full audit trail. No live memory, no open sockets, no unrecorded side effects. The log grows and needs compaction. Temporal caps history at 51,200 events or 50 MB.

The convergence across shipping agent products is the useful finding. Claude Code, Codex, and Devin all split the session the same way: the conversation moves as a log, the code moves as git, and the environment never moves. Each product rebuilds the environment from templates and setup scripts. No surveyed system migrates the live agent process. Amp's documented behavior matches this split exactly: the thread lives on the server, the code reaches the orb as a fresh clone, and amp sync brings back file changes rather than a machine.

§Mapping an orb onto Electric Agents primitives

From here on this page is design work, not reporting. The question: which requirements of an orbs-like product does the stack from Parts 1 to 5 already satisfy, and which does it not. The table states each requirement, the primitive that carries it, and an honest status.

RequirementElectric Agents primitiveStatus
Session identity that survives a host move The entity URL /{type}/{id} plus its registry row. Identity, memory, and behavior are decoupled from any running process (Part 1 §1). shipped
Session state that both hosts can read The main log, attachment streams for file artifacts, shared boards via ctx.mkdb(), and the manifests collection as the resource table (Part 1 §2, Part 4 §2). shipped
A cloud host The webhook push target, derived from the type's serveEndpoint (Part 5 §5). shipped
A laptop host behind NAT The runner pull target: register at /_electric/runners, long-poll POST /runners/:id/claim, heartbeat a lease. Part 5 names laptops explicitly. Both targets receive the same notification shape, so handler code does not know which host it is on. shipped
At most one active brain, with zombie fencing Claims serialize execution. Leases detect death. Epochs and claim-scoped write tokens reject a superseded host's late appends with 403 (Part 5 §4, §6). shipped
The handoff lever itself The per-entity dispatch policy. Resolution is explicit per entity, then inherited from the parent, then the type's default (Part 5 §5). The data model holds a per-entity target, but no documented route mutates a live entity's policy. build
Catch-up on the arriving host Offset resume. A woken handler is a stateless consumer catching up from a watermark. A cold host reads the full log. A warm host reads only the delta (Part 2 §3, §4). shipped
Live spectating from the other host, or a phone observe(entity(url)): an authorized catch-up read, then an SSE tail. Consumer position is client-held, so disconnects need no protocol. Offset reads collapse on a CDN (watching journey). shipped
Divergence, e.g. a local experiment off the cloud session fork() branches a full entity from the history at a point (forking journey). There is no merge. Reconvergence means adopting the branch and retiring the ancestor. shipped, no merge
Triggers that survive the move Wake registrations, cron schedules, future sends, and webhook sources are durable server-side data. No process anywhere holds a timer (Part 3 §8). shipped
The warm workspace (checkout, build cache) Deliberately not state. Sandboxes are leased per wake. Durable artifacts go to attachment streams. The cache rule from the anatomy section governs the rest. Rehydration of a warm volume keyed to a log position is named by FAQ 13 as something you build. build
A model call in flight at handoff time It cannot migrate. FAQ 10: you cannot retarget a 30-second run mid-flight. You hand off at a turn boundary for zero loss, or abort with SIGINT and re-enter on the new host, paying the interrupted step's tokens again. partial
Credentials on each host Keys never enter the log by design. LLM keys live in the host runtime, tool secrets live in handler closures and OAuth bridges (Q&A 4, 5). Authority travels as grants and claim-scoped write tokens. Key material does not travel at all. shipped as posture, parity is yours

Where the mapping is exact: identity, state, dual hosting, fencing, catch-up, spectating, fork, and durable triggers. Notice that every failure-recovery mechanism in the crash journey, which is lease expiry, re-dispatch, re-materialize, and guard, is also the handoff mechanism. A handoff is a deliberate, quiesced run of the path the system already exercises on every crash. That is why the safety half of the orb costs no new code.

Where it strains, you build. In rough dependency order:

  1. A per-entity dispatch re-point API. The resolution chain admits an explicit per-entity target, but no documented route mutates a live entity's policy. Re-registering the type's serveEndpoint is the wrong lever, because registration is per type and would move every instance. The conflict semantics of two runtimes registering one type with different endpoints are also undocumented.
  2. The move choreography. Quiesce, either by waiting for the done callback or by signal, then flip the dispatch target, then nudge a wake on the new host. The rails exist. The verb and its UX do not.
  3. Warm workspace rehydration. A volume cache keyed to a log position, on both hosts, with the repo ref and patch series in state of record. Without it every handoff pays checkout and build warm-up again.
  4. A mid-run handoff policy. Default to turn-boundary handoff. For forced moves, abort and re-enter with per-step checkpoint state to bound the tokens you pay twice. A streaming completion cannot be migrated on these primitives, or on any surveyed system.
  5. Runner failover. The wiki does not say what happens to an entity whose standing target is a dead runner. gap An orb needs a rule such as: after N missed heartbeats, dispatch falls back to the type's cloud webhook.
  6. A host capability parity check. Credentials cannot travel, so nothing verifies the target host holds the LLM keys, tools, and sandbox profiles the session needs before you re-point it. Build a host manifest handshake.
  7. Subtree handoff. Dispatch policy inherits from the parent, but whether inheritance is evaluated at spawn time or at dispatch time is undocumented, and there are no linked lifecycles (FAQ 9). Moving a session with children is explicit iteration. gap
  8. Merge after divergence. fork() gives branches. Grafting a local experiment back into the mainline is unbuilt. The documented idiom is fork and retire.
  9. Offline operation. Out of scope. One always-on plane mediates every read and write (FAQ 12). A disconnected laptop can neither append nor be woken. True local-first would need a second plane and cross-plane sync, which is a different project.

§Amp on Electric: the proposed topology

The design decisions, stated once. A thread is an entity, /thread/T-42, and its main log holds the conversation, tool results, run boundaries, and state changes. The orb is not the session. It is a disposable host: a handler runtime plus a leased sandbox that holds a fresh clone, reachable as a webhook target or as a registered runner. The laptop is a registered runner that long-polls for claims, which works behind NAT with outbound-only traffic. Workspace truth travels through the git remote and through attachment streams, never through the control plane, which matches what Amp documents about its own client and server not storing the codebase. Each host holds its own credentials. The dispatch policy on the entity decides which host the next wake reaches, and flipping that policy is the handoff.

🔗 Chronicle note

The durable streams box is the substrate Chronicle implements (Part 2). Nothing on this page asks anything new of it. The orb design leans on properties the protocol already has: offset-resumable reads for catch-up, idempotent producers and epoch fencing for the two-hosts race, and fork without rewriting for divergence.

The Amp features map onto this without new nouns. Starting a thread in an orb is spawning the entity with a dispatch policy that targets an orb host, then letting the host clone and run the setup hook. amp sync is a git fetch of the orb's pushed branch plus an observe() tail. Remote control is observe() plus queued sends, which coalesce into the next wake. The 24-hour setup snapshot is a creation-time template for new sandboxes, which the platform does not ship and does not preclude. The limitation to state plainly: this topology has one always-on plane, so the laptop participates only while it can reach the server. Amp has the same shape, since a thread lives on Amp Server.

§Journey: laptop to orb, pushing a session away

The developer has been driving /thread/T-42 from the laptop and wants it to keep running after the lid closes. This is the move Amp does not document for existing threads, built from the primitives in Part 5. The safety half is free, because it is the crash journey entered on purpose. The product half is steps 2, 5, and 7, which are the choreography, the re-point API, and host provisioning from the build list.

  • Step 2 is the whole product decision. Waiting for the done callback makes the handoff lossless, because at a turn boundary the log is the entire session (anatomy). If the developer will not wait, SIGINT aborts the current wake, everything appended before the abort is already durable, and the orb re-enters against that partial work. The interrupted model step's tokens are paid again.
  • Step 4 is not optional. The log holds truth, not the working tree. An uncommitted local change that never reaches the git remote or an attachment stream does not exist for the orb. Amp has the same rule: the orb sees a fresh clone.
  • Step 11 is the cost of a cold host. The orb reads the full log and rebuilds the checkout. Truth is never lost. Time is always spent. The rehydrating volume cache from the build list is what would shrink this.
  • Steps 12 and 13 are why the race is safe. Claims allow one active wake, and the laptop's stale epoch and retired write token are rejected at the data layer, not by convention (Part 5 §6). A laptop that limps back after the lid opens cannot corrupt the thread.

§Journey: orb to laptop, pulling a session home

The reverse move. The thread has been running in the orb overnight, and the developer wants to iterate on it locally. The laptop is a warm host here, because it held the thread before and kept its watermarks, so catch-up is a delta read rather than a full replay. The workspace comes down the same way Amp's amp sync brings changes down, through git, except that here the dispatch target moves too and the agent itself continues on the laptop.

  • Spectating precedes the move. Before the developer pulls the session home, the laptop is an ordinary observe() consumer with a client-held offset. A queued send from the spectator lands on the log and coalesces into the next wake (FAQ 2). Most of Amp's remote-control surface is this step alone, with no host move at all.
  • Step 9 is the pull model. No inbound connection reaches the laptop. The runner long-polls and heartbeats a lease, which is why a laptop behind NAT can be a first-class host (Part 5 §3).
  • Step 10 is the warm-host payoff. The laptop kept watermarks from when it last held the thread, so it replays only the overnight delta. The same move to a fresh machine would be the cold path from the previous journey.
  • Step 14 is the orb's whole teardown. Because nothing on the orb was state of record, the teardown is discard, not migration. What the orb's tmux session, databases, and installed packages held is gone, exactly as Amp documents for amp sync. If the runner were to die instead of being disabled, the failover rule from the build list has to decide where the next wake goes. gap

§What the log-backed orb wins, and what it cannot carry

The log and replay strategy from section 3 is the most portable representation of a session, and it is also the most partial one. Both halves show up in the journeys above.

Wins
  • Resume anywhere. Any host with credentials materializes the session from an offset. Cold hosts pay a full read, warm hosts pay a delta.
  • Spectate from anything. Many readers can watch one writer. Offsets are client-held, and reads at an offset are cacheable, so fan-out collapses on a CDN. Late joiners replay the same log.
  • Fork. Branch the history at a point and the branch is a full session. No export, no import. Neither re-attach nor snapshots offer this cheaply.
  • Audit. The session record and the debugging record are the same bytes, including every intervention and every handoff.
  • Handoff is crash recovery on purpose. One mechanism, exercised on every failure, so the rare path is the tested path.
Cannot carry
  • Warm sandbox state. The checkout, the build cache, the running Postgres in the orb. Every move pays warm-up time again unless you build the keyed volume cache.
  • In-flight model calls. A streaming completion dies with its host. Hand off at turn boundaries, or abort and pay the step's tokens twice.
  • Credentials. By design they never enter the log, so each host is provisioned separately and the two hosts can lawfully have different capabilities. Nothing checks parity before a move.
  • Open connections. Tunnels and sockets die across the move, the same reason Amp's resume hook exists to restart tunnels.
  • An offline laptop. One plane mediates everything. No connectivity, no session.
💡 The cache rule, applied to orbs

The anatomy section states the rule this whole page keeps applying: a derived store is legitimate exactly insofar as it stays working state, where deleting it costs time, not truth. An orb is a clean instance of the rule. Its disk is legitimate while everything on it rehydrates from the log, the git remote, and the attachment streams, which is why the teardown in the second journey is a discard. The moment an orb's disk holds truth the log cannot reconstruct, e.g. a hand-edited database row that no event records, the session has a second source of record, and handoff, fork, and audit silently break for exactly that state. FAQ 13 concedes the honest cost: for coding agents with large warm checkouts, rebuilding per move is expensive, and the rehydrating volume cache is something you build, not something the platform ships.
