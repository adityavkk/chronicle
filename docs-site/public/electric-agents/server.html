Inside the agent server

@electric-ax/agents-server ships its full TypeScript source in the npm package, so this part is grounded in the actual modules (src/server.ts, src/routing/*, src/wake-registry.ts, …). It is the always-on piece: one Node process that fronts the streams, owns the registry, and decides who wakes when.

1What the server is (and isn't)

The server is the entity control plane. It is not where agent code runs — no LLM loop, no handlers (except a mock chat agent for tests). Its responsibilities: store or proxy durable streams, validate and authorize every read and write, project stream events into a queryable registry, evaluate wake conditions, dispatch wakes to runtimes, run schedules, and serve the observability UI plus live sync.

Bootstrap (server.ts, entrypoint-lib.ts): run Postgres migrations → start the runtime workers (wake registry, scheduler, projector, outbox drainer, bridges) → serve HTTP on :4437. Streams storage is either embedded (an LMDB-backed Durable Streams server with webhooks enabled — the dev default) or an external Durable Streams server via DURABLE_STREAMS_URL.

🔗 Chronicle note

That DURABLE_STREAMS_URL seam is exactly where a protocol-conformant server like Chronicle sits: the agents server treats the streams backend as a black box speaking the Durable Streams protocol — create, append, read, subscriptions, producer semantics. (The one extension the dispatch pipeline leans on is the backend's subscription webhook support — the webhooks: true flag in the embedded reference server — which is how "stream has pending events" becomes a callback.)

2The two data planes

The most clarifying fact about the server: it manages two different kinds of truth.

plane 1 Durable Streams — the event log

Every entity event: inbox, runs, tokens, tool calls, state changes, tags. Append-only, replayable, streamed to UIs and handlers. This is the source of truth for what happened.

Backed by LMDB / files / any conformant server.

plane 2 Postgres — the control-plane registry

Queryable current state: entities (status, parent, tags), entity_types, permission grants, runners, wake registrations, consumer claims, schedules, subscription webhooks, outboxes. This is the source of truth for what exists and who may do what.

Drizzle ORM; migrations on boot.

The planes are stitched together in both directions. Stream events are projected into Postgres rows (an EntityProjector keeps entities.status etc. current), and Postgres tables are streamed back out via Electric sync — the server tails its own wake_registrations and entities tables through Electric ShapeStreams to keep in-memory caches and membership streams live. Postgres for queryable now; streams for replayable history; Electric to make the Postgres side reactive too.

3The HTTP surface

Routing is layered (itty-router): an OSS wrapper (UI, mock agent) → a global router → either the internal control plane (/_electric/*) or the Durable Streams catch-all (every other path is a stream). Per-request middleware builds a TenantContext (principal, managers, stream client, signer) — request handling itself is stateless.

4Life of an append — where everything meets

The densest code path is POST to an entity stream (routing/stream-append.ts). Every write to an entity's log — from a runtime mid-wake, a UI sending a message via collection write, anything — passes through:

  1. Resolve & guard. Map the stream path to its entity; reject if stopped or fork-locked.
  2. Authenticate the writer. Validate the write token (electric-claim-token) — minted when a wake was claimed or an entity spawned, released on done. Only the current claim holder may write. This is how "one active wake at a time" is enforced at the data layer, not by convention.
  3. Validate the event. Against the entity type's schemas (inbox types, state collections, externallyWritable allow-lists).
  4. Forward to the backend, tenant-prefixing the path (tenant-stream-paths.ts).
  5. Evaluate consequences. evaluateWakePayload — does this event match anyone's wake registration? checkRunFinished — did a run just complete (parents with runFinished wakes care)? Sync any manifest-declared wakes, sources, and schedules the event implies.

Step 5 is the heart of the reactive machinery: appends are what cause wakes.

5Wake dispatch: one abstraction, push and pull

The WakeRegistry (wake-registry.ts) holds every wake registration (conditions: runFinished or {on:'change', collections, ops}, plus debounceMs / timeoutMs / oneShot) in Postgres, mirrored in memory and kept live across nodes via an Electric shape on the table itself. When an event matches, the entity has pending work — and its dispatch policy decides how compute finds out. Exactly one target, two kinds:

Webhook target — push

{ type: 'webhook', url } — derived automatically from the type's serveEndpoint. The entity's main stream joins a streams-backend subscription whose callback is /_electric/subscription-webhooks/:id; on pending events the server marks the entity running, enriches the notification (entity, streams+offsets, claim, principal), signs it, and POSTs it to your app.

Fits: serverless / scale-to-zero. Compute exists only while handling.

Runner target — pull

{ type: 'runner', runnerId } — the entity's stream joins a pull-wake subscription tied to the runner's own wake stream. A registered runner long-polls POST /runners/:id/claim, receives the same notification shape, heartbeats a liveness lease while working.

Fits: long-lived workers, private networks where the server can't reach in, the built-in Horton/worker agents, sandboxed fleets.

Policy resolution: explicit per-entity → inherited from parent → the type's default. Both models converge on the same notification and the same callback protocol, so a handler never knows which way it was delivered.

6Claims, leases, and at-least-once made safe

Delivery is at-least-once end to end; three mechanisms make that safe:

  • Claims serialize execution. consumer_claims + entity_dispatch_state (active consumer, epoch, outstanding wake, pending source streams) ensure one active wake per entity; competing claims get benign 409s. Claims carry lease expiries; a dispatch-recovery loop reclaims stale ones, and epochs fence zombies — a done from a superseded consumer can't clobber a newer claim's state.
  • Write tokens scope mutation. Only the claim holder can append (§4), so a timed-out handler that limps back to life can't corrupt the log after its successor started.
  • Idempotency everywhere. Stream appends ride idempotent producers; control-plane upserts are onConflictDoNothing/Update; wake notifications track delivery_status (queued/delivered/failed/superseded) and claim_status. Re-delivery is an expected event, not an error path — which is also why your handlers must be re-entrant (Part 3 §3).

7Case study: the tag outbox

A small module that teaches the server's whole philosophy. Entity tags live in Postgres (queryable) and on the entity's stream (replayable, observable). Updating both atomically across two systems is the classic dual-write problem — solved the classic way, a transactional outbox (tag-stream-outbox-drainer.ts): the tag mutation and an outbox row commit in one Postgres transaction; a drainer polls every 500ms, claims rows with a worker lease, and appends each as a tag change event to the entity's main stream. Each row gets its own producer identity (tag-outbox-<rowId>, epoch 0, seq 0), so retries dedupe into exactly-once appends; ten failures dead-letters the row.

Pattern to notice: Postgres transactions where atomicity is needed, streams as the fan-out, idempotent producers as the bridge. The wake pipeline, the scheduler (cron ticks deduped by unique constraint, claim-based firing), and the bridges all rhyme with it.

8The Electric proxy and pg-sync — where "Electric" earns the name

Two features close the loop with ElectricSQL's Postgres sync engine:

  • The Electric proxy (electric-proxy-router.ts): UIs need live lists — "all entities of type judge that I can see", updating as things spawn and die. That's a Postgres query, synced. The proxy forwards GET /_electric/electric/v1/shape to Electric, but rewrites it defensively: one table per request from an allow-list, fixed column lists, client where clauses checked for SQL breakout, and an enforced scoping clause ANDed in — tenant + the requesting principal's readable-entities filter derived from the grants tables. Row-level security applied at the proxy, so the browser can hold a live, permission-correct view of the registry.
  • pg-sync (pg-sync-router.ts, bridge manager): the reverse — register any external Postgres table (URL, table, columns, where) as an observation source. The bridge tails it via an Electric shape and re-publishes changes into a durable stream entities can observe(pgSync(…)). Your production database becomes a wake source: "wake me when a row lands in orders."

9Multi-tenancy, scale-out, production posture

  • Tenancy: every Postgres table is keyed by tenant_id; every backend stream path is tenant-prefixed at the proxy boundary. One standalone server = one tenant; the embeddable AgentsHost runs many tenants in one process with shared background workers — the shape of Electric Cloud's hosted offering.
  • Scale-out: server nodes are stateless per request; Postgres is the coordination point (claims, leases, unique constraints), the streams backend is shared, and in-memory caches stay coherent by subscribing to their own tables via Electric shapes. Schedulers and drainers use claim columns + instance IDs so N nodes don't double-fire.
  • Production auth posture: the Electric-Principal header is trusted input — the server expects an authenticateRequest hook (verify the JWT/session, return the principal) and an optional authorizeRequest policy hook (external ABAC, cached with expiry) to be wired in, or a gateway in front. Dev fallback (system:dev-local) only engages when insecure/dev conditions hold. Outbound webhooks are Ed25519-signed; inbound streams-backend webhooks are verified against JWKS. More in Q&A #5.
