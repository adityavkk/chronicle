A guided tour of the agent runtime & agent server

Electric Agents, explained from the nouns up

Electric Agents is a durable runtime for long-lived, collaborative agents built by the ElectricSQL team. Instead of an agent being a process that must stay alive, an agent is an entity: an addressable, append-only stream of events plus a handler function that is woken when something it cares about happens. This site walks that idea from first concepts down to the implementation, in order.

§The mental-model shift

Most agent frameworks model an agent as a process: an object in memory running an LLM loop, holding conversation state, alive for as long as the agent "exists". That model fights the web's architecture — processes die, redeploys wipe memory, serverless functions time out, and two replicas can't share a heap.

Electric Agents inverts it. The framework's own phrase for this is "turning the agent inside out":

Process-centric agent
  • State lives in the process heap
  • Identity = a running object / actor
  • Messaging = RPC into the process
  • Crash / redeploy ⇒ amnesia
  • Must stay resident to "exist"
Electric agent (data-centric)
  • State lives in a durable stream (append-only log)
  • Identity = a URL: /{type}/{id}
  • Messaging = append an event to a stream
  • Crash / redeploy ⇒ replay the log, carry on
  • Sleeps between wakes ⇒ scales to zero

The agent is the data. The compute — your handler function and its LLM loop — is stateless, disposable, and only runs for the duration of a wake. On every wake the runtime rebuilds the agent's world from its stream, runs your handler, appends whatever happened back onto the stream, and lets the compute die. That one idea explains almost every design decision in the stack.

⚛ The actor lineage — and what agents actually change

George Guimarães's essay "Your Agent Orchestrator Is Just a Bad Clone of Elixir" makes the sharpest version of an argument you will keep meeting: the actor model Erlang shipped in 1986 — isolated state, message passing, supervision, fault recovery — is the agent model AI is rediscovering, and today's frameworks are rebuilding it in runtimes that can't deliver it. This stack is best read as the next step in that lineage, not a departure from it. Each generation relaxed one assumption:

  • Erlang bound existence to a running process — and virtual actors already cut that cord. In classic actor runtimes a million idle actors really do hold heaps and a scheduler; but Orleans's virtual actors (2011) made actors "purely logical entities that always exist, virtually" — activated on demand, deactivated under pressure, always addressable, state persisted between activations. Virtual existence is a solved problem in actor-land; it is not what's new here.
  • What agents change is who the log is for. Actor systems already event-source when they need durability — Akka Persistence and Orleans JournaledGrains keep a log too. But theirs is a recovery mechanism: private to the actor, replayed by the actor, one consumer, one access pattern. Here the log is the interface: the same append-only, offset-addressed record of everything the agent said, saw, and did is the write path, the read path, the LLM's context (a projection of it), the UI's live feed, the parent's monitor, the audit trail — and fork() branches it: "copy this agent's timeline at event N and let both continue" has no equivalent when the log is a persistence detail. Recovery falls out for free: re-entry into the log rather than restart into cleanliness, which also matches how agents actually fail — the process is usually healthy; the output is what went wrong.
  • And agents change where identity lives: the web, not a cluster. A grain is always addressable inside its cluster; an entity's address is a URL — messaging is an HTTP append, and a handler runs on anything that can receive a webhook. Though not every agent should be externalized: a flock of ephemeral sub-agents has no business holding public addresses, and neither tradition has formalized that internal/external split yet (FAQ 11).

Same discipline — single-threaded, message-driven, isolated — extended one more step: process actors → virtual actors → logged, web-addressed agents. The open threads this lineage still owes us: declarative supervision (FAQ 9) and the internal/external agent distinction (FAQ 11); the full argument and line-for-line mapping live in FAQ 8–10.

§The nouns at a glance

Eight nouns carry the whole system. Part 1 treats each one properly; here is the map.

Entity
The unit of existence. An addressable identity (/{type}/{id}) that owns an append-only event stream and has a handler. Agents, workers, judges — all entities.
Stream
A durable, append-only log over plain HTTP. Each entity has one main stream (/{type}/{id}/main) carrying every event of its life: messages, LLM steps, state changes.
Wake
The unit of execution. "Something happened that you care about" — an inbox message, a child finishing, a state change, a timer. Each wake invokes the handler once.
Handler
Your code: async handler(ctx, wake). Deterministic control flow that decides what this wake means — run the LLM, spawn children, update state, or go back to sleep.
Agent (the LLM loop)
An optional behavior inside a wake: ctx.useAgent({...}) + await ctx.agent.run(). Context is assembled from the stream; every step is appended back to it.
Collection (state)
Typed, queryable state materialized from the stream via TanStack DB. Built-ins (inbox, runs, steps…) plus your own declared collections with insert/update/delete actions.
Runtime
@electric-ax/agents-runtime — the library in your app. Registers entity types, receives wake webhooks, materializes streams into ctx, runs handlers.
Server
@electric-ax/agents-server — the always-on control plane. Stores streams, watches them, decides who to wake, enforces permissions, serves the UI and live sync.

Read it as a loop: a message is appended to an entity's stream → the server's wake machinery notices → it POSTs a webhook to your app → the runtime materializes the stream into typed state and runs your handler → the handler's effects (LLM steps, replies, spawns, state updates) are appended back → which may wake other entities. Nothing in the loop requires your code to be resident between wakes.
