A guided tour of the agent runtime & agent server

Electric Agents, explained from the nouns up

Electric Agents is a durable runtime for long-lived, collaborative agents built by the ElectricSQL team. Instead of an agent being a process that must stay alive, an agent is an entity: an addressable, append-only stream of events plus a handler function that is woken when something it cares about happens. This site walks that idea from first concepts down to the implementation, in order.

§The mental-model shift

Most agent frameworks model an agent as a process: an object in memory running an LLM loop, holding conversation state, alive for as long as the agent "exists". That model fights the web's architecture — processes die, redeploys wipe memory, serverless functions time out, and two replicas can't share a heap.

Electric Agents inverts it. The framework's own phrase for this is "turning the agent inside out":

Process-centric agent
  • State lives in the process heap
  • Identity = a running object / actor
  • Messaging = RPC into the process
  • Crash / redeploy ⇒ amnesia
  • Must stay resident to "exist"
Electric agent (data-centric)
  • State lives in a durable stream (append-only log)
  • Identity = a URL: /{type}/{id}
  • Messaging = append an event to a stream
  • Crash / redeploy ⇒ replay the log, carry on
  • Sleeps between wakes ⇒ scales to zero

The agent is the data. The compute — your handler function and its LLM loop — is stateless, disposable, and only runs for the duration of a wake. On every wake the runtime rebuilds the agent's world from its stream, runs your handler, appends whatever happened back onto the stream, and lets the compute die. That one idea explains almost every design decision in the stack.

⚛ The actor lineage — and what agents actually change

George Guimarães's essay "Your Agent Orchestrator Is Just a Bad Clone of Elixir" makes the sharpest version of an argument you will keep meeting: the actor model Erlang shipped in 1986 — isolated state, message passing, supervision, fault recovery — is the agent model AI is rediscovering, and today's frameworks are rebuilding it in runtimes that can't deliver it. This stack is best read as the next step in that lineage, not a departure from it. Each generation relaxed one assumption:

  • Erlang bound existence to a running process — and virtual actors already cut that cord. In classic actor runtimes a million idle actors really do hold heaps and a scheduler; but Orleans's virtual actors (2011) made actors "purely logical entities that always exist, virtually" — activated on demand, deactivated under pressure, always addressable, state persisted between activations. Virtual existence is a solved problem in actor-land; it is not what's new here.
  • What agents change is who the log is for. Actor systems already event-source when they need durability — Akka Persistence and Orleans JournaledGrains keep a log too. But theirs is a recovery mechanism: private to the actor, replayed by the actor, one consumer, one access pattern. Here the log is the interface: the same append-only, offset-addressed record of everything the agent said, saw, and did is the write path, the read path, the LLM's context (a projection of it), the UI's live feed, the parent's monitor, the audit trail — and fork() branches it: "copy this agent's timeline at event N and let both continue" has no equivalent when the log is a persistence detail. Recovery falls out for free: re-entry into the log rather than restart into cleanliness, which also matches how agents actually fail — the process is usually healthy; the output is what went wrong.
  • And agents change where identity lives: the web, not a cluster. A grain is always addressable inside its cluster; an entity's address is a URL — messaging is an HTTP append, and a handler runs on anything that can receive a webhook. Though not every agent should be externalized: a flock of ephemeral sub-agents has no business holding public addresses, and neither tradition has formalized that internal/external split yet (FAQ 11).

Same discipline — single-threaded, message-driven, isolated — extended one more step: process actors → virtual actors → logged, web-addressed agents. The open threads this lineage still owes us: declarative supervision (FAQ 9) and the internal/external agent distinction (FAQ 11); the full argument and line-for-line mapping live in FAQ 8–10.

§An agent's anatomy — properties, not slogans

"The agent is the data" is Electric's framing, and as pedagogy it earns its keep: one sentence, one inversion, and half the stack's design decisions follow. But it is an identity claim, and identity claims end arguments. This site's preferred framing — worth stating separately, because it is doing different work — is a design claim: an agent is whatever satisfies four sets of required properties. Design claims stay useful when the implementation varies: they let you evaluate what Electric chose, what the actor lineage chose, and what a coding agent with a persistent volume chooses differently — by checking properties, not allegiance.

OrganWhat it isThe properties that matter
The log The agent's own memory and identity — the state of record. In Electric: the entity's streams (Part 2). Append-only (audit, replay, fork points, cacheable reads) · totally ordered (races become boring — FAQ 2) · offset-addressable (resume without coordination) · multi-consumer with an open set of readers — UIs, sub-agents, memory systems, evals; you don't know today who reads tomorrow · forkable (branch a timeline at an offset — FAQ 4, FAQ 5) · appends cheap enough to carry individual token deltas, so the log doubles as the live feed · named, permissioned, lifecycle-managed (TTL — FAQ 4)
The brain Harness + model. The harness is the fixed, pre-determined control flow — context construction, guardrails, gates — authored before the agent ever runs (Part 3 §6); the model adds the dynamic, runtime decision-making that can't be pre-determined. In Electric: your handler + ctx.agent.run(). Holds no state of record — stateless across turns, richly stateful within one (the context window is state, but state reconstructible by projecting the log) · killable at any instant with zero loss (FAQ 5) · its context is a budgeted projection of the log, not the log (Part 4 §4, FAQ 4)
The hands The action space — tools, sandboxes, side effects. In Electric: ctx.sandbox + tool sources (Part 3). Leased per wake, not owned · blast-radius-tiered (host → docker → microVM, per-spawn — FAQ 13) · capability-scoped — tools allowlisted by the host, every action executed as a principal, credentials never ambient (FAQ 13) · journaled — tool calls and results land on the log · the one place exactly-once honestly ends (FAQ 3), so external effects carry idempotency keys derived from durable identifiers
The nervous system The binding between log and brain — something must notice the log moved and summon compute. In Electric: the agents server (Part 5). Watches the log, evaluates wake conditions, dispatches · at-most-one active brain per agent (claims, leases) with zombie fencing (epochs, write tokens — FAQ 5) · at-least-once delivery with coalescing (FAQ 2) · gates every read and write behind authn/authz (FAQ 12)

Two of those terms carry weight and deserve definitions. A turn is one wake-to-sleep execution: the nervous system summons the brain, the brain rebuilds its world from the log, harness and model act, everything that happened lands back on the log as it happens, and the compute dies. A session is the agent's whole recorded lifetime — the log across all of its turns (Anthropic's Managed Agents literally names its log "the session"). Stateless across turns then has a precise meaning: at a turn boundary, nothing exists anywhere in the system but the log. And the harness/model split is Part 3 §6's hybrid-control-flow idiom stated as anatomy: the branches you could write before the agent ran belong to the harness; the judgment you couldn't belongs to the model.

State of record deserves its own definition, because the whole anatomy hangs on it. It is the copy that settles disagreements — and three tests identify it, any one sufficing: losing it loses truth, not time; someone who is not you may later demand it (an audit, a parent's join, a billing dispute); and a fork() must carry it for the branch to be the same agent. Everything failing all three is working state — reconstructible from the state of record at some cost in time: the context window, a materialized collection, a warm checkout. The discipline in one line: the brain and hands may hold arbitrary working state; only the log holds state of record.

The log is the agent's own state — but agents also touch state they don't own, and the framing has to say where each kind lives:

  • Own — the entity's streams: private by default, permissioned, everything above.
  • Shared — blackboards: stream-backed DBs no single agent owns (ctx.mkdb() / observe(db(…)), Part 3 §4), materialized by every participant. Same log properties, joint ownership — the coordination patterns favor these over conversational ping-pong between entities (Part 3 §7).
  • Observed — other agents' logs, read-only (observe(entity(url))): coordination as observation (FAQ 1).
  • External — the world's systems of record (repos, databases, SaaS), reached through the hands. Not derived from the log: the log records what the agent did to them — the effect journal — not what they contain.
  • Derived — projections and caches over the log: TanStack DB collections (Part 2 §8), a file-system view over streams, a sandbox's warm disk. The rule that keeps this tier honest: a derived store is legitimate exactly insofar as it stays working state — deleting it costs time, not truth. A coding agent's checkout on a persistent volume is fine while it rehydrates from a log position (repo ref + patch series); the moment the volume holds truth the log can't reconstruct, a second source of record exists — and forkability and audit are silently lost for exactly that state. Electric enforces this rule structurally: sandboxes are leased per wake (scratch disks only), and durable file-like artifacts go to attachment streams under the entity instead of volumes (FAQ 13).
⚖ Convergence check: Anthropic cut the same joints

Anthropic's "Scaling Managed Agents: Decoupling the brain from the hands" arrived at this anatomy from the opposite direction — not web architecture but the ops pain of running an agent fleet: "We virtualized the components of an agent: a session (the append-only log of everything that happened), a harness (the loop that calls Claude and routes Claude's tool calls to the relevant infrastructure), and a sandbox (an execution environment where Claude can run code and edit files)." Their coupled first design — session, harness, and sandbox in one container — produced a pet: lose the container, lose the session. The fix was this page's anatomy: decouple the brain from the hands and the session log, so that "nothing in the harness needs to survive a crash" — a dead harness is rebooted with wake(sessionId) and resumes from the log; the session becomes a context object the brain queries by positional slices (getEvents()) rather than something it must carry; and credentials live where the sandbox can never reach them. Log, stateless brain, leased hands, a wake verb. When two teams starting from opposite ends — Electric from the web's architecture, Anthropic from operating a fleet — cut the agent at the same joints, the joints are probably real.

Read the rest of this site as the property lists made concrete: Part 2 is the log's properties as a wire protocol, Part 3 is the brain's idioms, Part 5 is the nervous system, and the journeys are all six organs moving at once. The actor callout above is this same framing applied to history.

§The nouns at a glance

Eight nouns carry the whole system. Part 1 treats each one properly; here is the map.

Entity
The unit of existence. An addressable identity (/{type}/{id}) that owns an append-only event stream and has a handler. Agents, workers, judges — all entities.
Stream
A durable, append-only log over plain HTTP. Each entity has one main stream (/{type}/{id}/main) carrying every event of its life: messages, LLM steps, state changes.
Wake
The unit of execution. "Something happened that you care about" — an inbox message, a child finishing, a state change, a timer. Each wake invokes the handler once.
Handler
Your code: async handler(ctx, wake). Deterministic control flow that decides what this wake means — run the LLM, spawn children, update state, or go back to sleep.
Agent (the LLM loop)
An optional behavior inside a wake: ctx.useAgent({...}) + await ctx.agent.run(). Context is assembled from the stream; every step is appended back to it.
Collection (state)
Typed, queryable state materialized from the stream via TanStack DB. Built-ins (inbox, runs, steps…) plus your own declared collections with insert/update/delete actions.
Runtime
@electric-ax/agents-runtime — the library in your app. Registers entity types, receives wake webhooks, materializes streams into ctx, runs handlers.
Server
@electric-ax/agents-server — the always-on control plane. Stores streams, watches them, decides who to wake, enforces permissions, serves the UI and live sync.

Read it as a loop: a message is appended to an entity's stream → the server's wake machinery notices → it POSTs a webhook to your app → the runtime materializes the stream into typed state and runs your handler → the handler's effects (LLM steps, replies, spawns, state updates) are appended back → which may wake other entities. Nothing in the loop requires your code to be resident between wakes.
