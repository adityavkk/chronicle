FAQ 1
Isn't this just Temporal (or LangGraph) for agents? How does it differ from durable-execution engines?
TL;DR
Temporal makes code durable by replaying it deterministically; Electric Agents makes state durable and lets code be ordinary. That inversion removes Temporal's determinism constraints, makes the session observable data rather than engine-internal history, and treats streaming and UIs as first-class — at the cost of Temporal's "write it like a normal function" linear control flow. LangGraph sits a level below both: an in-process orchestration library, not a durability substrate.

Temporal (and Restate, Azure Durable Functions, etc.) achieves durability by event-sourcing the execution: every side effect a workflow performs is recorded, and on failure the engine re-runs your workflow function from the top, replaying recorded results until it catches up. That gives you an amazing property — durable code that reads like linear code (const a = await activity1(); const b = await activity2(a)) — but the price is strict: workflow code must be deterministic (no bare randomness, clocks, or I/O outside activities), the event history is an engine-internal format, and versioning running workflows is notoriously delicate because old histories must replay against new code.

Electric Agents takes the other fork. Nothing is ever replayed through your code:

  • The unit of resumption is the wake, not the statement. On every wake the runtime rebuilds the world by materializing data (Part 4 §2), not by re-executing your handler's past. Your handler can be as non-deterministic as it likes — it contains an LLM, after all, the least deterministic component in software. There is no versioning trap: new code simply handles the next wake against the same state.
  • The history is a public data structure. Temporal's event history exists to drive replay; you inspect it through Temporal's UI. An entity's log is the product: the same events feed the LLM's context, the user's live UI, observer entities, and audits (Q&A #1). Streaming tokens to a browser through a workflow engine is possible but foreign to the model; here it's the default write path.
  • Coordination is observation, not orchestration. A Temporal workflow coordinates children it started, through signals and futures it holds. Electric entities coordinate by watching each other's state (observe()), so topologies can form dynamically without a parent workflow owning the whole graph.

What you give up: Temporal's linear "durable function" ergonomics. An Electric handler is a state machine you re-enter (guard on ctx.state, act, sleep — Part 3 §6); a five-step sequence is five wakes with explicit gates, not five awaits in a row. For deterministic back-office sagas — payments, provisioning — Temporal's model is genuinely better. For agent sessions — streaming, observable, human-in-the-loop, LLM-driven — the data-first inversion pays for itself. (LangGraph, for contrast, is a graph library inside one process whose checkpointer bolts persistence onto an in-memory model — it answers "how do I structure a loop?", not "how does the loop survive, scale to zero, and get observed?")

FAQ 2
What happens when things race — two messages arrive at once, or a wake fires while the entity is already running?
TL;DR
An entity is single-threaded by construction: the append-only log serializes all inputs, and the server's claim system guarantees at most one active wake per entity. Events that arrive mid-wake don't interrupt — they queue and coalesce into the next wake. So handlers never need locks; the concurrency model is "one reducer, ordered input, at-least-once invocation."

Three mechanisms stack to make races boring:

  1. The log orders writers. Two users messaging the same entity simultaneously both append to /{type}/{id}/main; the streams backend serializes them into a total order (Part 2). There is no "same time" by the time anything reads.
  2. Claims serialize execution. The server's entity_dispatch_state tracks one active consumer, epoch, and outstanding wake per entity (Part 5 §6). A second wake condition firing while a handler is running doesn't spawn a second handler — the pending events wait; competing claims get benign 409s; a lease-expired claim is fenced by epoch so a zombie can't act after its successor starts.
  3. Wakes coalesce. A wake covers a window (fromOffset → toOffset, eventCount), so five messages that arrived during a run become one re-invocation whose materialized inbox already contains all five. debounceMs on wake registrations lets you widen the coalescing deliberately for chatty observed sources.

The remaining knob is what a message means when it lands mid-run, and that's the sender's choice via send modes: queued (default shape — wait your turn), steer (inject into the currently running agent's loop — "actually, stop and do X"), and paused delivery for entities under SIGSTOP. Cross-entity races (two children finishing "at once") reduce to the same story: two wakes, delivered one at a time, each seeing durable state — which is exactly why the judge's "have both arguments arrived?" gate in Part 3 §6 is race-free without any locking.

FAQ 3
What are the delivery semantics, end to end? Where exactly is it exactly-once, and what must my handler guarantee?
TL;DR
Appends are exactly-once; invocations are at-least-once; the contract that joins them is handler idempotency. Writes dedupe via idempotent producers, so retries never double-append. Wake delivery can repeat, so your handler must be safe to re-run — which the guard-on-durable-state idiom gives you for free.
HopSemanticsMechanism
Client/handler → stream (append)Exactly-once Idempotent producer headers: server dedupes on (producerId, epoch, seq); retried batches return 204; stale epochs are fenced with 403 (Part 2 §5). The runtime routes all entity writes through one.
Server → handler (wake)At-least-once Webhook delivery retries; expired claims re-dispatch; wake_notifications tracks queued/delivered/failed/superseded (Part 5 §6). Duplicates and re-deliveries are expected events.
Handler executionAt-most-one live at a time Claims + write tokens: only the current claim holder can append, so a re-delivered or zombie invocation can't corrupt the log even if it runs (Part 5 §4, §6).
State materializationDeterministic replay Apply-in-order, last-write-wins; re-delivered inserts are downgraded to updates by the dispatcher, so reconnects don't trip duplicate keys (Part 2 §8).

So the whole burden that lands on you is one rule: a wake handler must be re-entrant. Concretely:

  • Guard effects on durable state, not on "this is the first time I've run" intuition: if (ctx.state.debate.get('current')) return ctx.sleep(). Spawn-once = deterministic child IDs + a manifest/state check before spawning (the manifestChildKey query in Q&A #3).
  • External side effects (Stripe charge, email) are where at-least-once actually bites — same as every queue system. Put your own idempotency key, derived from durable identifiers (entity URL + state key), on the outbound call, or bracket it with recordRun() state so a re-run sees it happened.
  • State writes themselves are safe to repeat by construction — they flow through the exactly-once append path.

Note the philosophical alignment with Kafka: the framework doesn't pretend to give you exactly-once processing (nothing distributed honestly can, once arbitrary side effects are involved); it gives you exactly-once logging plus fencing, which is the strongest buildable foundation, and makes the remaining idempotency your handler's visible, testable responsibility.

FAQ 4
The log grows forever but the context window doesn't. How does a long-lived entity not drown in its own history — in the LLM, and on disk?
TL;DR
Three different growth problems, three different answers. LLM context: budgeted projection + automatic compaction (background summarization at 85% of the window, hard ceiling at 90%). Materialized state: last-write-wins keeps collections proportional to live keys, not events. Storage: honestly, the base protocol never compacts — logs are append-only until TTL'd, deleted, or forked; the bet is that kilobytes are cheap and history is valuable.
  • The context window (the real constraint). The prompt is a projection of the log, not the log (Part 4 §4) — so the fix lives in the projection. By default the runtime tracks usage (uncachedInput + output, so provider caching isn't double-counted), warns the model from 25%, starts background compaction — checkpoint summaries written back to the stream — at 85%, and forces synchronous compaction at a 90% hard ceiling. Beyond the defaults, ctx.useContext() makes the projection explicit: named sources with token budgets and cache tiers (pinned / stable / slow-changing / volatile), plus auto-registered tools (loadTimelineRange, loadSourceRange) so the model pages history in on demand instead of carrying it. The log stays complete; the window carries a working set.
  • Materialized collections. A million state:debate update events still materialize to one row per key — last-write-wins means memory tracks the entity's live state size, not its age. The bulky built-ins (textDeltas) matter for warm runtimes, which is why reads are offset-resumable: a warm consumer only ever applies the delta.
  • Storage. The base protocol deliberately has no log compaction (Part 2): reclamation is Stream-TTL/expiry, explicit DELETE, and fork() — branch a fresh entity from a point and let the ancestor age out — plus advisory snapshot-start/end and reset control events at the state layer for consumers that want to re-baseline. This is a real trade: an entity that streams tokens for a year accumulates a year of tokens. The design bet is that agent history is audit trail, training data, and debuggability — worth its kilobytes — and that lifecycle policy (TTL per stream, fork + retire) belongs to you, not to a compactor that silently rewrites the past.
FAQ 5
What's the failure model? My handler crashes mid-wake, the LLM times out, the agents server restarts — what actually happens?
TL;DR
Every failure reduces to the same recovery: the claim lease expires, the wake re-dispatches, the handler re-runs against durable state, and fencing guarantees the dead attempt can't write after its successor starts. Work completed before the crash isn't lost (it was appended as it happened) and isn't redone (guards see it). The server itself is stateless per request, so its restarts are only a dispatch pause.
FailureWhat happensWhy it's safe
Handler crashes mid-wake (or the lambda times out) No done callback arrives; the claim's lease expires; the dispatch-recovery loop reclaims it and re-dispatches the wake to a fresh invocation. Everything the dead run appended (tokens, tool calls, state) is already durable; the re-run's guards see it. The dead run's write token is superseded — if the "crashed" process limps back, its appends are rejected.
LLM call fails (timeout / rate limit / 5xx) The model runner retries within the wake (modelMaxRetries, modelTimeoutMs); classified ModelProviderErrors land as errors events and end the run as failed. The failed run is visible data — parents woken on runFinished see run_status: 'failed' and can retry, reroute, or escalate as ordinary handler logic.
Agents server restarts In-flight webhook deliveries get 503s (graceful shutdown refuses new dispatch); on boot it reloads wake registrations, claims, and schedules from Postgres and resumes evaluating from the streams. All coordination state is in Postgres + streams, none in process memory (Part 5 §2, §9). Undelivered wakes are still queued rows; nothing depends on the process that died.
Streams backend down Appends fail → handlers error → wakes retry later. Readers resume from their offsets when it returns. Offsets make every consumer recovery-free (Part 2 §3); idempotent producers make every retried append dedupe.
A stuck or runaway agent (not crashed — wrong) Operator intervention is a first-class API: SIGINT aborts the current wake through ctx.signal; SIGSTOP quarantines (messages queue); SIGKILL closes the streams. All recorded as signals events. Because the entity's whole state is its log, you can also fork() the pre-wedged history into a fresh entity and retire the stuck one — recovery by branching rather than surgery.

The deeper point: there is no separate "recovery mode." Re-materialize, re-run, guard — the failure path is the normal path (every wake already works that way), which is why it's trustworthy. Systems with a distinct recovery codepath fail in recovery; this one recovers the same way it runs.

FAQ 6
What does this architecture cost in latency and money versus an in-process agent loop — and when is it the wrong choice?
TL;DR
The overhead sits at coordination boundaries (wake dispatch, cross-entity hops — tens of ms of HTTP + append), not inside the LLM loop (which runs in-process once woken, exactly like any harness). Since agent turns are seconds and LLM tokens are ~all of the money, the tax is noise for agent-paced work — and the architecture actively saves money by making waiting free and no-op wakes token-free. It's the wrong tool when you need sub-millisecond loops, single-machine shared memory, or when your whole product is one ephemeral chat box.

Where the latency actually goes. A wake costs: webhook dispatch (network hop) + catch-up read (offset-resumable — small for warm entities) + handler start. Call it tens of milliseconds. Inside ctx.agent.run(), the tool loop is ordinary in-process code; stream appends are pipelined writes that don't block token generation. So a 30-second research turn pays the same LLM 30 seconds it would anywhere, plus ~1% overhead at the edges. The places to watch are chatty cross-entity designs — every send → wake → reply cycle is a full coordination round-trip, which is why the patterns (Part 3 §7) favor batching state into blackboards and gates over conversational ping-pong between entities.

Where the money goes — and doesn't. Tokens dominate agent economics, and the hybrid-control-flow idiom is directly a cost optimization: the walkthrough's judge handles five wakes with only two LLM runs — the gate wakes are pure JavaScript, ~free (Part 3 §6). Waiting costs zero compute (Q&A #1); idle entities cost kilobytes; read fan-out (dashboards, observers) is CDN-cacheable rather than compute. The standing costs are the always-on plane — the agents server, Postgres, streams storage — which is a fixed ops cost amortized over every agent, versus per-agent sandbox-hours in the resident-agent model (the 5ms/2MB-vs-125ms/128MB comparison from the serverless-agents post).

When it's honestly the wrong choice:

  • Tight loops. Agents reacting to each other at sub-millisecond cadence (trading, game AI, robotics control) — the per-hop coordination cost is the workload. Use actors or shared memory.
  • Single ephemeral sessions. A stateless "ask one question" chat with no history, no coordination, no observers — a plain streaming HTTP response is simpler; you'd be running a control plane for nothing.
  • Huge artifacts through the log. The log wants events, not gigabytes; that's what the attachments streams and sandboxes are for — pass references, keep blobs out of the timeline.
FAQ 7
How do I evolve an entity type — change its state schema or handler logic — when instances with old-format history are still alive?
TL;DR
Code evolves freely — handlers aren't replayed, so new code just serves the next wake (the advantage over durable-execution engines, FAQ 1). Data evolves like an event-sourced system: events are forever, so grow schemas additively, re-register types on deploy, and reach for the escape hatches — reset to re-baseline a stream, fork() to migrate an entity onto new history — when additive isn't enough.
  • Handler logic: trivially. There's no recorded execution to stay compatible with. Deploy new code, registerTypes() re-registers on startup, and every subsequent wake — including for entities spawned months ago — runs the new handler against materialized state. Your only obligation is the one you already have: handle the state shapes that exist.
  • Schemas: additively, by default. Old events in the log were validated by old schemas and will be materialized again; a new schema that rejects them breaks your own history. So evolve like protobuf: add optional fields, tolerate absence in the handler (debate.rebuttals ?? {}), never repurpose a field. Type registration supports amendment (PATCH /_electric/entity-types/:name/schemas) for adding inbox message types and state collections to a live type; adding a whole new collection is clean — old entities simply have zero rows in it.
  • Breaking changes: use the escape hatches. The state protocol ships reset (consumers clear and rematerialize from a given offset — the designed hook for "the stream's schema changed") and snapshot markers to delimit a re-baseline written in the new format. At the entity level, the idiomatic big-bang migration is a fork-and-retire: fork() the entity, write a migration wake that reads old-shape state and writes new-shape state, point traffic at the fork, TTL the ancestor. History is preserved, the migration itself is an audited event, and rollback is "keep using the original."
  • Contracts with others. inboxSchemas and creationSchema are validated server-side at send/spawn time, so they version like any public API: additive within a type name, or introduce reviewer-v2 alongside reviewer when semantics genuinely break — dispatchers make the cutover a routing decision rather than a migration.
FAQ 8
The "agents are actors" argument: Erlang solved all of this in 1986 — supervision trees, mailboxes, let-it-crash. Is Electric Agents just relearning BEAM lessons?
TL;DR
The argument, made sharpest by George Guimarães: the actor model Erlang shipped in 1986 is the agent model AI is rediscovering — and today's frameworks are rebuilding it without the runtime that made it work. He's substantially right, and the cleanest way to see this architecture is as an actor with a durable mailbox. But the two traditions attack opposite halves of the problem: OTP nailed process-level fault tolerance and concedes durability to a persistence layer; Electric Agents nailed durability and leaves supervision policy to you (FAQ 9). Each one's headline feature is the other's confessed gap.

The primary source is Guimarães's "Your Agent Orchestrator Is Just a Bad Clone of Elixir" (expanding an earlier note; see also the Hacker News thread and his follow-up conceding the fair criticisms). The thesis in one line: "the actor model that Erlang introduced in 1986 is the agent model that AI is rediscovering in 2026." His case:

  • Agent sessions are telecom calls. Long-lived, stateful, concurrent conversations that must fail independently — the exact workload the BEAM was designed for, which is why its answers (2KB isolated processes, preemptive scheduling, per-process GC, supervision) fit so uncannily.
  • The frameworks are converging on actors without naming the destination. Langroid's README cites the actor model outright; AutoGen was rebuilt in v0.4 as an "event-driven actor framework." But it's actors on single-threaded asyncio: no preemption, no per-agent GC, no supervision hierarchy, no real fault isolation — "you're rebuilding telecom infrastructure in a language that wasn't designed for it."
  • The last mile is runtime-level. His estimate: ~70% of the actor model can be rebuilt in Python or TypeScript with enough engineering; the remaining 30% (preemptive scheduling, per-process GC, hot code swapping, true isolation) needs the VM. Akka and Orleans are his evidence for how much engineering "approximate the BEAM" costs (FAQ 10 takes this head-on).
  • And the concession that matters here: after HN pushback he agreed that supervision restores a clean state, not your state — "if the whole cluster goes down or you redeploy, that in-memory state evaporates… you still need a persistence layer," i.e. an append-only event log. Process-level fault tolerance and execution-level durability are different problems.

Read this architecture against that vocabulary and the correspondence is almost line-for-line:

Virtual actor (Orleans grain) — "always exists, virtually"; activated on demand; a state snapshot persisted between activationsSame virtual existence — but what persists is the log, not a snapshot: public, multi-reader, offset-addressed, forkable
Event-sourced actor (Akka Persistence, Orleans JournaledGrain) — a log kept for recovery: private, replayed by its own actor, one consumer The log as the interface: the write path, the read path, the context projection, the UI feed, the monitor, and the fork point are all the same log

One refinement the one-line thesis needs — and the reason "departure from actors" would overstate it: Orleans's virtual actors already decoupled existence from residency ("actors are purely logical entities that always exist, virtually… always addressable" — Orleans docs), with activation on demand and state persisted between activations. So sleeping cheaply is not the novelty. Read this stack as the next relaxation in the same lineage. And since event-sourced actors exist too, the honest statement of the differentiator is not "log vs. snapshot" but who the log is for: event-sourcing as a private recovery mechanism versus event-sourcing as the public product — one log serving writes, reads, context, UIs, monitors, audits, and fork() — plus the addressing move from cluster to web (FAQ 11 for where that one gets complicated, FAQ 12 for how it's mediated).

The deep difference is what a failure costs. OTP restarts in microseconds into a clean state — which for an agent means the conversation, the tool results, and the tokens you paid for are gone (the sharpest HN critique of let-it-crash for agents: "clean state = lost conversation context"). Electric re-enters in tens of milliseconds into durable state — everything the dead run appended is still there, and guards keep it from being redone (FAQ 5). Where OTP treats the process as the unit of truth and forgets, this treats the log as the unit of truth and remembers. That ordering of priorities — durability first, supervision policy second — is the whole design bet, and Guimarães's essay is the strongest case for why the second half still deserves to be stolen deliberately rather than rediscovered accidentally.

FAQ 9
OTP's killer feature is the supervision tree: declarative restart strategies, restart budgets, escalation, linked lifecycles. What's the equivalent here — and what's honestly missing?
TL;DR
There is a built-in flat supervisor — lease expiry + wake re-dispatch restarts every crashed handler against durable state (FAQ 5) — and observe() makes supervisor entities an ordinary pattern to write. What there isn't is OTP's declarative layer: restart strategies (one_for_one / one_for_all / rest_for_one), restart-intensity budgets with automatic escalation, and linked lifecycles for entity teams. Today those are handler code you write, not policy the platform enforces.

What exists, mapped onto the supervisor's three jobs:

  • Restart the worker. Automatic and universal: a crashed or timed-out wake's claim lease expires, the recovery loop re-dispatches, fencing stops the corpse from writing (FAQ 5). This is OTP's restart-the-child, with one upgrade — the child comes back remembering, because its state was never in the process.
  • Notice the failure. Failed runs are data, not exceptions: run_status: 'failed' and errors events wake any parent observing runFinished. That's a monitor, and it composes across machines for free.
  • Intervene. The operator layer — SIGINT / SIGSTOP / SIGKILL, plus fork()-and-retire recovery (FAQ 5) — covers the "human in the supervision tree" case OTP handles with :observer and prayers.

The gaps, called out plainly:

  • No declarative restart policy. A parent that wants "restart this child up to three times with backoff, then escalate to me" writes that as guard-state logic in its own handler. OTP expresses it in one tuple.
  • No restart-intensity circuit breaker. Nothing documented bounds the lease-expire → re-dispatch loop, so a poison wake — a handler that crashes deterministically on the same input — keeps being re-offered (burning invocations, and tokens if the crash is late) until an operator SIGSTOPs the entity or ships a fix. OTP's max_restarts/max_seconds escalates automatically: the supervisor itself dies upward. There is no automatic "give up and tell my parent" here yet.
  • No linked lifecycles. Killing a debate's judge does not kill the debaters — there is no one_for_all for an entity team, and no subtree kill. Tearing down a topology is explicit iteration (or per-stream TTL), and a child orphaned by its parent's demise just sleeps forever, costing kilobytes.
  • Semantic supervision exists nowhere — including OTP, as Guimarães's follow-up concedes: restarting fixes crashed processes, not bad LLM output, so a supervisor that inspects why (garbage response vs. rate limit vs. real crash) and chooses different strategies is application logic in every runtime today. The natural home for it here is a supervisor entity: it observes children's errors/runFinished, keeps restart budgets in its own durable state, and every decision it takes is an audited event. The primitives are arguably better than OTP's (a BEAM supervisor's restart counters die with it; a supervisor entity's survive) — but the packaged, declarative library on top of them is not written yet.

So: supervision here is a pattern, not yet a feature. If you build one, the shape falls out of the existing idioms — spawn with deterministic child IDs (Q&A #3), observe runFinished, hold the restart budget in durable state, escalate by messaging your parent — a supervision tree where every node remembers. The missing piece is exactly the thing OTP proved valuable: making that policy declarative so teams stop hand-rolling it.

FAQ 10
The strongest form of the BEAM argument: the last 30% — preemptive scheduling, per-process GC, hot code reload, true isolation — needs runtime support you can't bolt on. Does Electric Agents have an answer, or is it stuck in the 70%?
TL;DR
It sidesteps rather than solves: isolation and inter-agent fairness are delegated to process/invocation boundaries (coarser than BEAM processes, with FAQ 6's latency tax, but real); hot reload's outcome falls out of the no-replay design; distribution is URLs + offsets instead of transparent pids. What is genuinely unanswered: BEAM-style fairness inside one runtime process — a CPU-hogging handler blocks its event loop, and no architecture choice here changes that.
  • Isolation. The BEAM isolates with per-process heaps inside one VM; here each wake is its own invocation (its own process or sandbox), and — the stronger property — state isn't in process memory at all. One agent's crash, leak, or bloat can't corrupt another's state because the state of record is the log (Part 2), not a heap. The grain is coarser and each hop costs tens of milliseconds instead of a microsecond message send (FAQ 6); that's the price of isolation you didn't have to build.
  • Preemptive scheduling & per-process GC. The honest gap. BEAM preempts every ~4,000 reductions and collects garbage per-process; Node and Python are cooperative, so within a single runtime process a CPU-heavy handler (giant JSON parse, embedding math) starves its neighbors. The mitigation is architectural, not runtime: fairness between entities comes from one-invocation-per-wake dispatch, and CPU-heavy work belongs in the model call, a tool, or a sandbox. If you do heavy compute inside a shared handler process, you will starve it — the runtime will not save you.
  • Hot code reload. The BEAM swaps bytecode under live processes because a phone switch can't stop. Here the same outcome for agents comes free from no-replay (FAQ 1, FAQ 7): deploy, and every subsequent wake — including for entities spawned months ago — runs new code against old state; in-flight runs finish on the code they started with. What you can't do is retarget a 30-second run mid-flight; the idiom for that is steering it with a message (FAQ 2), not swapping its code.
  • Distribution. Distributed Erlang gives transparent pids inside a cluster you operate — with cluster membership, netsplits, and cookies as your problem. Here location transparency is the entity URL: streams are plain HTTP (CDN-shaped reads, Part 2), and a handler can run on anything that can receive a webhook. Coarser and slower than a pid send, but it's internet-grade rather than cluster-grade — no membership protocol to babysit.

Scoreboard, honestly kept: mailbox durability, crash recovery, and code evolution — answered, and for agent-paced workloads (seconds per turn, tokens as the real cost) arguably answered better, because recovery preserves context instead of discarding it. Declarative supervision (FAQ 9) and intra-process fairness — not answered: the first is buildable as a pattern and should eventually be a library; the second is a real limit you design around by keeping handlers I/O-shaped. Which lands on Guimarães's own closing point: runtimes shape systems. This one just picked the append-only log, rather than the VM, as the component that never lies.

FAQ 11
Not every agent seems to need a public address: one agent may spawn a flock of ephemeral sub-agents, while another is a standing contract with the outside world. Do actor systems distinguish internal from external agents? Does Electric?
TL;DR
Actor systems have addressability scopes but no first-class internal/external distinction. Electric makes the opposite simplification: every entity is externalized — a URL with durable streams — and the only "internal agents" are whatever lives inside a single wake's in-process loop. The middle tier — logged but unaddressed, agentic but private, lifecycle-bound to a parent — is unformalized in both traditions. This answer is partly an editorial flag: that tier is worth formalizing, and nobody has.

What actors have: scopes, not semantics. Forty years of actor systems produced a rich toolbox for "reachable by whom, under what name?" — worth knowing, because each mechanism was built to solve a specific problem:

System & mechanismScope modelWhat it solves
Erlang/OTP — anonymous pids by default; register/2 local names; the global cluster registry; pg process groups Reachability as capability: an unregistered pid can only be messaged by whoever was handed it. Registration is opt-in publication, at node or cluster scope. Decoupling names from lifecycles: a supervisor restart yields a new pid but the registered name repoints, so senders survive their target's death — the naming layer is part of the fault-tolerance story.
Akka — hierarchical actor paths (akka://sys/user/parent/child); Receptionist discovery; Cluster Sharding of entity IDs The address is the supervision tree — a path names a position in the hierarchy, not a process. Sharding adds logical entity IDs routed to whichever node currently hosts them. Location transparency plus placement: senders hold stable logical addresses while the runtime moves, rebalances, and passivates the actors behind them.
Orleans — no registration at all: grain identity = (type, key), resolved by the runtime's grain directory Universal in-cluster addressability: every possible identity "always exists, virtually" and can be messaged at any time; the directory maps identity to a live activation, creating one if needed. Eliminating discovery and lifecycle races by construction — there is no "is it started yet?", no registration ceremony, no dangling refs.
Cloudflare Durable Objects — IDs, not URLs: a DO is reachable only through Worker code you deploy in front of it Mandatory mediation: the platform gives objects identity but no public surface; every access flows through your code, which is therefore your authn/authz layer. Making exposure a policy decision rather than a topology accident — the closest existing answer to "everything is addressable, but who may actually reach it?"

Notice what all four have in common: they are operational scopes — capability, hierarchy, directory, mediation — not modeling concepts. Nothing in any actor contract says this actor is an internal implementation detail; that one is a public commitment. The distinction the agent world needs is semantic, and it isn't in the toolbox.

What Electric has: externalization by construction. Identity is a URL (/{type}/{id}); a spawn()ed child is a full entity with streams, an authz surface, and a lifecycle, identical in kind to its parent. That default buys the properties this wiki keeps advertising — any agent can be observed, audited, streamed to a UI, signaled by an operator, fork()ed — precisely because nothing is hidden inside a process. But it also bills every ephemeral helper the full contract: an address you must authorize, storage you must TTL, an orphan you must remember to end (FAQ 9's linked-lifecycle gap). At the other extreme, the tool loop inside ctx.agent.run() is fully internal — no address, no log of its own beyond what the handler chooses to append. Between "full public entity" and "invisible in-process loop" there is nothing — structurally. What there is instead is policy: a URL here is identity, not exposure. Every read and write passes through the agent server's authn/authz gate (FAQ 12), so "private sub-agent" is expressible today as an authorization rule — only the parent's principal may send to or observe the child. That is real access control, in the Durable Objects spirit of mandatory mediation; what it isn't is a packaged semantics with defaults, which is where the rest of this answer goes.

The unformalized middle tier. A researcher entity that fans out twelve extraction sub-agents wants them logged (debuggability, audit, fork-to-retry) but not addressed: no inbound contract, invisible to the public routing surface, reachable only through the parent, and torn down with it. A formalization would probably be a spawn-time property, not a new noun: visibility (private streams, capability-scoped to the parent rather than the public surface), lifecycle linkage (die/TTL with the parent — the same missing "process group" concept as FAQ 9's one_for_all, which suggests one mechanism solves both), and contract exclusion (no inboxSchemas obligations to version). Until something like that exists, the working rule: externalize an agent iff someone who is not its parent must message, observe, or audit it — and before minting a URL at all, check whether the "sub-agent" is really just handler code (the hybrid control-flow idiom, Part 3 §6).

Worth saying plainly: this is the one question in this appendix answered by neither the source material nor the shipped system. OTP never needed the distinction (all pids are cheap and die with the app), Orleans made everything uniformly cluster-addressable, and Electric made everything uniformly web-addressable. Agents — which spawn agents, which spawn agents — are the first workload where the internal/external split is doing real architectural work, and it's this explainer's nomination for the next concept the actor lineage owes us.

FAQ 12
The durable stream gives an agent its URL — but is that how you actually talk to it? Do clients write directly into the stream, or go through the agent server?
TL;DR
Through the server. The stream gives the agent its identity and its persistence; the agent server is the front door. It stores or proxies the durable streams and validates and authorizes every read and write (Part 5) — sends, spawns, observe feeds, and appends all pass through its HTTP surface under a principal. Clients never need to reach the streams backend directly, and production designs put a fronting proxy in front of even the server.

Why the front door exists. The server manages two kinds of truth (Part 5 §2): the durable streams — the append-only log of what happened — and the Postgres control-plane registry — entities, wake registrations, claims, schedules. A bare streams backend can serialize appends and serve offsets, but it cannot validate an inbox message against inboxSchemas, evaluate wake conditions, enforce claims and write tokens, or decide who may do any of this. The entity URL therefore names a resource the server serves; the stream behind it is an internal tier.

Life of a send. A request arrives carrying a principal — the server expects an authenticateRequest hook (verify the JWT/session, return the principal) and an optional authorizeRequest policy hook (external ABAC, cached with expiry), or a gateway wired in front (Q&A #5). The payload is validated against the entity's declared schemas, appended to the inbox stream through the runtime's idempotent producer (the exactly-once hop of FAQ 3), projected into the registry, and evaluated against wake registrations — which is what turns a write into a running agent. ctx.send(entityUrl, payload) from another entity rides exactly the same path: agents are principals too, so agent-to-agent messages clear the same authorization gate as user traffic.

Reads are the same story. A browser tab observing an agent (observe(), the live UI in Part 3) tails the log through the server's sync surface — SSE, offset-resumable, CDN-cacheable fan-out. The "browser is a first-class peer of the agent" property (Q&A #1) is a property of this mediated surface: peer means same log and same offsets, not unmediated storage access.

The trust boundary, stated plainly. The streams backend (chronicle, or any conformant server) sits behind the agent server, which stores or proxies it; inbound streams-backend webhooks are verified against JWKS, outbound webhooks are Ed25519-signed. The server treats its principal header as trusted input and ships with CORS wide open — so it must never be reachable with client-controlled headers, and a fronting proxy is part of the production design, not an option (Part 5 §9, Q&A #5). Dev mode falls back to a system:dev-local principal; production conditions hard-require a real one (401 otherwise).

This closes the loop on FAQ 11: actor systems scope reachability topologically — you cannot message what you cannot name or route to. Here everything is nameable, and reachability is policy at a mediated surface: what a principal may do to a name. That is the web's own answer to addressing — universal names, gated access — which is fitting for agents whose addresses are URLs in the first place.
