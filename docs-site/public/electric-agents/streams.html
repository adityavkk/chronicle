Durable Streams — the substrate

Everything in Electric Agents — messages, LLM tokens, state, coordination — is ultimately an append to, or a read from, a durable stream. This part explains the protocol itself, then the state protocol layered on it that turns a byte log into a typed, syncable database. Once you have these two layers, the agent framework is "merely" a disciplined way of using them.

1Why the stack starts with a log

The Electric team's blog post "Durable streams: the data primitive for the agent loop" (April 2026) makes the case: agent sessions are long-lived, streaming, multi-consumer, interruption-prone workloads. A plain HTTP response can't survive a disconnect. A websocket can't be resumed or cached. A database row loses the history and the ordering. A queue delivers once and forgets. What the agent loop actually needs is a primitive that is simultaneously:

  • a transport — you can stream tokens through it in real time,
  • a store — everything streamed is durably kept, in order,
  • a subscription — any number of consumers can tail it live,
  • a checkpoint — any consumer can resume from any point, statelessly.

That primitive is an append-only log addressed as an HTTP resource. It's Kafka's core idea with the operational model of a web server: no client libraries required, no partitions to manage, no consumer-group protocol — just URLs, methods, and headers.

2The wire protocol in one table

A stream is a URL, e.g. /judge/debate-7/main. The full lifecycle is five HTTP methods:

RequestMeaningNotes
PUT /pathCreate the stream201 new / 200 idempotent re-create. Sets Content-Type for life; optional Stream-TTL or Stream-Expires-At; optional initial body.
POST /pathAppend a batchOne request = one batch. 204 plain / 200 producer append. Stream-Closed: true closes (EOF).
GET /path?offset=…Read from an offsetoffset=-1 start · now tail · or a returned offset. Optional live=long-poll|sse.
HEAD /pathMetadataStream-Next-Offset, content type, closed flag, TTL — without the body.
DELETE /pathDelete410 Gone afterwards.

Every read response carries Stream-Next-Offset (where to resume), possibly Stream-Up-To-Date (you've reached the head) and Stream-Closed (no more will ever come). Streams are hierarchical paths, so namespacing — per tenant, per entity — is just URL structure.

3Offsets: durable consumption without a coordinator

Offsets are opaque tokens — the spec is emphatic: "clients MUST NOT interpret the format". (Internally they're <read-seq>_<byte-offset>, but that's the server's business.) The contract is a loop: 

const res = await stream({ url, offset: savedOffset, live: true })
res.subscribeJson(async (batch) => {
  for (const item of batch.items) process(item)
  saveOffset(batch.offset)          // ← the only consumer state that exists
})

This is what "durable" means operationally: consumer position is client-held data, not server-side session state. A crashed handler, a redeployed app, a laptop waking from sleep, a second browser tab — all recover identically: present your last offset, catch up, go live. Kafka needs a consumer-group coordinator for this; here it's a query parameter.

💡 Where the agent framework leans on this

The runtime's wake webhook includes the streams and offsets to read from; the entity's own replayWatermarks collection records how far each observed source has been consumed. A woken handler is just another stateless consumer catching up from a watermark.

4Three read modes, one request shape

Catch-up
No live param. Returns what exists from your offset; Stream-Up-To-Date when you've reached the head. Plain, cacheable GET.
Long-poll
live=long-poll. If you're at the head, the server holds the request (default ≤30s); new data returns immediately, else 204 + fresh cursor and you re-poll. CDN-collapsible.
SSE
live=sse. text/event-stream with data frames per message and control frames carrying {streamNextOffset, streamCursor, upToDate}. What the agents UI uses.

The crucial property: catch-up and live are the same request. A consumer never has to stitch "load history" and "subscribe to updates" together (and handle the gap between them) — the protocol does it.

5Writers: ordering guards and exactly-once

Two write disciplines, matching two levels of paranoia:

  • Stream-Seq — a monotonic, lexicographic sequence string per writer ("writer-1-000001"). Appending with a lower seq than the last → 409 Conflict. A cheap ordering guard for cooperative writers.
  • Idempotent producers — Kafka's exactly-once design, verbatim, over HTTP headers: Producer-Id / Producer-Epoch / Producer-Seq. The server dedupes on the (producerId, epoch, seq) triple: retried batches return 204 harmlessly; a stale epoch is rejected 403 (zombie fencing — a crashed-and-replaced producer can't corrupt the log); a sequence gap is 409 with the expected/received seqs.
const producer = new IdempotentProducer(stream, 'judge-writer', { autoClaim: true })
producer.append(event)     // fire-and-forget; batched (~5ms linger), retried, deduped
await producer.flush()

The agents layer builds directly on this: every runtime append of entity events goes through an idempotent producer, and the server's tag outbox drainer (Part 5) gives each outbox row its own producer identity so at-least-once retries become exactly-once appends.

6The CDN trick (inherited from Electric sync)

Because a read at a given offset always returns the same bytes, offset-parameterized GETs are immutable and cacheable. This is the same insight that lets ElectricSQL serve Postgres sync through CDNs, applied to streams: "10,000 viewers at the same offset become one upstream request." Two refinements make it safe:

  • ETags + conditional GET on historical reads (304 Not Modified).
  • Stream-Cursor — a time-bucketed, monotonically advancing token echoed on long-polls, so cached 204s can't trap a client in a stale-response loop.

Volatile responses (HEAD, offset=now) are marked Cache-Control: no-store. The upshot for agents: fan-out — many users, dashboards, and observer entities watching one agent — is a caching problem, not a broker-scaling problem.

7The state protocol: giving events a schema

Raw streams carry bytes. @durable-streams/state defines a small event vocabulary that makes a JSON stream mean state changes. Two message families: 

// Change message — a mutation of one keyed row of one type
{
  "type": "user",                      // routes to a collection
  "key": "user:123",                   // primary key
  "value": { "name": "Alice", … },     // required for insert/update
  "old_value": { … },                  // optional (audit / conflict detection)
  "headers": { "operation": "insert",  // insert | update | delete (+upsert in impl)
               "txid": "…", "timestamp": "…" }
}

// Control message — stream management, no data
{ "headers": { "control": "snapshot-start" | "snapshot-end" | "reset", "offset": "…" } }

Materialization is deliberately boring: "apply change messages sequentially in stream order", last write wins per (type, key). reset tells consumers to clear and rebuild (schema migrations); snapshot markers delimit point-in-time dumps. That's the whole spec — simple enough that any client on any platform can implement it, strong enough to carry a database.

This is the format of every event on an entity's main stream. An LLM token is {type:'text_delta', key:'…', value:{delta:'…'}}; your judge's phase change is {type:'state:debate', key:'current', headers:{operation:'update'}}. One vocabulary, one log, everything replayable.

8StreamDB: the log, presented as a database

createStreamDB (from @durable-streams/state/db) binds a schema to a stream URL and gives back TanStack DB collections — one per declared type — plus lifecycle and write helpers:

  1. Declare: createStateSchema({ users: { schema: userSchema, type: 'user', primaryKey: 'id' } }). Any Standard Schema validator works (Zod, TypeBox, Valibot…).
  2. Preload: db.preload() consumes the stream from the beginning; writes are buffered and committed per batch, and the promise resolves at the first Stream-Up-To-Date — you get a snapshot-consistent database, then it stays live on the same subscription.
  3. Read: db.collections.users.get('123'), or differential-dataflow live queries — joins, filters, groupBy that update incrementally per event.
  4. Write: actions built on createOptimisticAction — apply the change to the local collection instantly (onMutate), append the change event with a txid, then await db.utils.awaitTxId(txid): the write is confirmed when it comes back through the stream. The log stays the single source of truth; the UI never waits for it to feel fast.
The write loop: optimistic, but log-authoritative
sequenceDiagram

The agents runtime wraps exactly this machinery for every entity (createEntityStreamDB = StreamDB with the 20 built-in collections merged with your state block), and ctx.mkdb() / observe(db(…)) expose it directly for shared blackboard state between entities.

§Recap

  • A durable stream is an append-only log as an HTTP resource: PUT/POST/GET/HEAD/DELETE, offsets in, Stream-Next-Offset out.
  • Consumer state is one offset, held by the consumer — resumability without coordination.
  • Catch-up and live tail are one request; long-poll and SSE are the live modes; offset-immutability makes it all CDN-friendly.
  • Idempotent producers (id/epoch/seq + fencing) give exactly-once appends over at-least-once HTTP.
  • The state protocol (insert/update/delete change events + control messages) turns a JSON stream into replayable state; StreamDB materializes it into TanStack DB collections with live queries and optimistic, txid-confirmed writes.
  • Electric Agents = this substrate + an entity discipline on top. Which is Part 3.
