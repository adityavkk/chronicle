Evaluation

Agent Substrate, evaluated against the log

In May 2026 Google published Agent Substrate, a Kubernetes runtime that suspends an idle agent by checkpointing its running sandbox and resumes it on any warm pod. It is the opposite bet from the one this wiki describes. Electric Agents makes the log durable and treats compute as disposable. Substrate makes the compute state durable and does not have a log at all. This page reports what Substrate actually is, tests the two lifecycle models against each other, extracts the ideas worth taking, and answers the question that motivated the comparison. Can chronicle extend the Durable Streams stack with these ideas, or does it need a fork? The answer is extend, and the evidence is in section 7.

Electric Agents is pre-1.0 but validated end to end, including against chronicle. Agent Substrate's only release tag is v0.0.0, its README says it is "not ready for production use", and its own architecture doc opens with "Much of this architecture is aspirational, and is not yet implemented!" (architecture.md). Every Substrate capability on this page should be read with that status attached. Claims from sources carry a primary label, our readings carry inferred, and missing evidence carries gap.

§The verdict up front

Three questions drove this evaluation. Here are the answers, with the evidence in the sections that follow.

QuestionAnswerWhere
Extend Durable Streams, or fork it? Extend. The protocol's own extensibility section requires extensions to be pure supersets and the conformance suite tolerates them. Everything chronicle needs is additive, and the one capability the base protocol lacks is already built in chronicle as an additive change, with mechanical follow-ups documented. The honest fork pressure is governance, not licensing or mechanics, and it only binds if chronicle ever needs to change base wire semantics. It does not. §7
What is Agent Substrate uniquely good at? Keeping the volatile state of a running sandbox alive across idleness. RAM, the process tree, terminal sessions, and the writable filesystem survive suspend and resume, and a warm pool plus golden snapshots make wakes cheap. That is the heart of the list the orbs page concluded a log cannot carry. Substrate has no log, no schedules, and no fork, so it solves the log's blind spot and nothing else. §4, §5
Is a hybrid coherent? Yes, and the two halves do not overlap. A suspended Substrate actor can only be woken by an inbound HTTP request or an explicit RPC. Electric ships seven wake sources and owns none of the compute. The natural joint is a durable-streams control plane whose wakes drive a checkpointing sandbox tier. Google's own stack already has this shape, since its log runtime AX deploys on top of Substrate. The integration work is real and Substrate is not mature enough to adopt today, so the near-term move is to borrow its ideas, not its machinery. §6

One placement note. This evaluation lives as a page of the existing wiki rather than a new site or subdomain, because every argument on it leans on machinery the wiki already explains, from the anatomy properties to the orbs build list to FAQ 13. A separate site would have to restate all of that or link back here anyway. The cost of this choice is that the site's title says Electric Agents while this page evaluates a Google project, and that the shared top navigation is hand-edited in every page.

§What Agent Substrate is, per its own documents

Agent Substrate is an Apache-2.0 project in its own GitHub org, announced by Google Cloud in the same post that took GKE Agent Sandbox to general availability (GCP blog). The README states the core idea in one sentence: it "maps a larger set of 'actors'... onto a smaller set of ready 'workers' (Kubernetes Pods), relying on the fact that agent-like applications tend to be idle most of the time to achieve heavy multiplexing" (README). It is not an agent SDK and it does not run an agent loop. It manages standard OCI containers at the sandbox level and hosts any harness, with demos multiplexing Claude Code sessions. primary

NounWhat it is
Actor One suspendable instance, the unit of lifecycle. "It is the unit that is suspended and resumed" (glossary).
ActorTemplate The immutable class definition, a Kubernetes CRD. Creating one boots a temporary golden pod, waits for readiness, and snapshots it once. Every actor of that template then starts from the shared golden snapshot, so expensive init such as model loading runs once per template version rather than once per actor.
WorkerPool / Worker A CRD declaring warm pod capacity, and the record of one such pod. A worker hosts at most one actor at a time. "Many Actors are multiplexed across a pool over time" (glossary).
Snapshot The durable artifact. Full scope captures process memory plus the rootfs writable layer. Data scope captures only declared volumes, and the actor cold-boots on resume. Snapshots stream zstd-compressed to GCS or S3.

The suspend mechanism is checkpoint and restore of the running sandbox, not anything Kubernetes-native. The default sandbox class checkpoints a gVisor process tree with runsc, which today requires a build flag to work around a bug in networking resumption. A second class snapshots a Kata Containers micro-VM on Cloud Hypervisor and restores it with demand paging (architecture.md). The wake path is traffic itself. An Envoy router intercepts requests to <actor-id>.actors.resources.substrate.ate.dev, holds the request, asks the control plane where the actor is, triggers a resume if it is suspended, and then forwards the held request to the worker's pod IP. primary

The control plane is split in a way worth noticing. Slow-changing configuration stays in Kubernetes CRDs. High-frequency actor and worker records live in Redis or Valkey behind a stateless gRPC server called ateapi, explicitly because "achieving 100ms resumption requires low-latency state lookups and atomic worker assignments that bypass the eventual consistency and variable latency of standard Kubernetes API servers" (architecture.md). Every lifecycle transition is a step workflow guarded by a per-actor Redis lock with a 30 second TTL (learn.agentsubstrate.dev). Substrate also distinguishes Pause, a short-term checkpoint kept on the node with resume prioritized to that node, from Suspend, a checkpoint uploaded to object storage that can resume anywhere. primary

The numbers attached to all this are targets, not measurements. The stated north stars are 100ms p95 activation, one billion registered actors per cluster, and 1000 wakes per second. The public demo shows about 250 stateful sessions multiplexed onto 8 pods with sub-second activation. No benchmark under load has been published by anyone, and the roadmap lists representative-workload benchmarking as future work. gap The layer below is further along. GKE Agent Sandbox is GA and documents 300 sandbox allocations per second per cluster with 90% completing in 200ms (GCP blog). primary

Kubernetes is required and GKE is not. The quickstart runs on a local kind cluster with Valkey and an S3-compatible store. The practical catch is that pod certificates, which Substrate requires for its internal mTLS, sit behind Kubernetes feature gates that default off as of 1.36 and that some managed services do not expose (cloudnativedeepdive). Governance is a draft document, the README says it is not an officially supported Google product, and the strongest external signal is that Solo.io abandoned open-sourcing its own equivalent system, with measured 50ms and 200ms resumes on Bubblewrap and Firecracker, to contribute to Substrate instead (Solo.io). primary

§Two answers to one question

Both systems start from the same observation. An agent is idle most of the time, so an agent must not cost a machine while idle. They differ in what they choose as the state of record, and every other difference follows from that choice.

The framing that motivated this page was that Substrate connects the compute lifecycle to the agent lifecycle, while Electric defines a standalone agent lifecycle and matches compute to it. The evidence supports the second half and refines the first. Substrate does not bind the agent to a pod. It binds the agent to a machine image, the checkpoint of its RAM and disk, and then deliberately decouples that image from any particular pod. Its docs call this out by name: "Decoupling the Actor Lifecycle from Pods", with resumes landing "possibly on a different worker" each time (architecture.md). So both systems treat compute as fungible. The real difference is what survives idleness. In Electric, the log survives and the machine does not. In Substrate, the machine survives, frozen, and there is no log. inferred

Electric AgentsAgent Substrate

Identity The stream path /{type}/{id}. No separate entity id exists. The actor id, minted by the control plane, delivered to the workload as a bind-mounted file so the golden snapshot does not freeze it into every clone.
What a wake costs A handler invocation plus a catch-up read from the last offset. A cold host replays the full log. A snapshot restore onto a warm pod. Target 100ms p95, demonstrated sub-second, unmeasured under load. gap
Wake sources Seven: inbox message, child completion, observed entity change, shared state change, schedules, webhook sources, and Postgres sync (waking-entities). Two: an inbound HTTP request held at the gateway, or an explicit ResumeActor RPC. No timers, no cron, no queues. primary
What survives suspend Everything written to streams. Nothing in process memory, by design: "no process, no memory, no running handler" between wakes. Process memory, the process tree, terminal sessions, and files. Open external TCP connections still die, as they do everywhere.
What a crash loses Nothing durable. Replay reconstructs state. In-flight model calls are re-entered at a turn boundary. Work since the last checkpoint. Between checkpoints the running machine is the only copy. inferred
Fork / audit / spectate Native. Fork at an offset, replay for audit, many readers per log. None. Forking and cloning are roadmap items. A snapshot is opaque bytes.

The orbs page's prior-art taxonomy places both cleanly. Electric is the log-and-replay strategy. Substrate is the strategy that taxonomy calls "snapshot the runtime image", industrialized. It is the same family as Fly suspend and Codespaces stop, but the snapshot is portable across a pool instead of pinned to one machine. The taxonomy's costs transfer unchanged. Logs cannot carry live memory. Snapshots cannot fork, cannot be audited, and resume into dead TCP connections. inferred

§What the snapshot carries that the log cannot

The orbs case study ended with an honest list of what a log-backed session cannot carry: warm sandbox state, in-flight model calls, credentials, open connections, and an offline laptop. Substrate's entire reason to exist is the first item and the running processes inside it. Item by item:

The log's blind spot (after orbs §8)Does Substrate solve it?
Warm sandbox state. The checkout, the build cache, the running database. Every host move pays warm-up again unless you build a keyed volume cache. Yes, natively. The snapshot is the warm state. The README claims "persistent working memory (volatile RAM) and filesystem state preserved perfectly across hibernation cycles", and markets exactly the coding agent case: environments that "preserve terminal and filesystem state across sessions". The orbs build-list item "warm workspace rehydration" is this, shipped as the core primitive. primary
Running processes. A tmux session, a REPL, a dev server, a browser. The log records none of it, so a move discards it. Yes, with caveats. gVisor checkpoints the process tree, so processes resume where they stopped. The caveats are real: external TCP connections are terminated on restore, the gVisor path today needs a build carrying a bug workaround, and GKE's own pod snapshot docs require the restore target to match machine series, gVisor kernel version, and GPU driver version (pod-snapshots). primary
In-flight model calls. A streaming completion dies with its host. No. A checkpoint taken mid-call resumes into a dead socket like everyone else. Turn boundaries remain the honest handoff point in both architectures. inferred
Credentials and open connections. No, and one wrinkle is worse. Environment variables, secrets included, are resolved when the golden snapshot is taken and frozen into it. primary The practical consequence, that rotating a secret means rebuilding the template or restarting actors, is our reading of that mechanism. inferred Electric's posture, where keys live in host runtimes and never enter the log, has no Substrate equivalent yet.

Two more capabilities have no counterpart in the log world at all. Golden snapshots amortize cold init across a fleet: boot one pod per template version, snapshot it after readiness, and every subsequent actor starts from that image instead of re-running setup. And the pause tier keeps short-idle checkpoints on the node they were taken on, resuming locally without an object-storage round trip. Both are placement economics, and placement economics is the discipline the Electric stack does not practice, because it owns no compute.

The costs are stated nowhere and should be assumed until measured. A full-fidelity snapshot of a coding agent is potentially gigabytes of RAM per suspend cycle flowing to object storage, many times a day, versus a log whose increments are kilobytes. Nobody, including Google, has published that comparison. gap And Substrate's own roadmap carries an unresolved question with quiet consequences: a gVisor upgrade can invalidate memory snapshots, so checkpointed memory is best treated as a cache over some other state of record, not as the state of record itself. Substrate does not say what that other state of record should be. A log is a reasonable answer. inferred

§What Substrate lacks, and why the stacks are complements

Read from the other direction, the gaps are just as sharp. Substrate has no durable messaging of any kind. It has no stream, no inbox, no queue, and no event log. Input is a synchronous HTTP request or a lifecycle RPC, and if nothing calls a suspended actor, it sleeps forever. There are no schedules, no observed-state triggers, and no self-sends. There is no fork, no replay, no audit trail, and no way for a second consumer to watch what an actor is doing except to ask it over HTTP. Multi-agent coordination, the thing Part 3 of this wiki spends most of its pages on, has no primitive here. primary

Google's own stack concedes this by construction. Agent Executor, the runtime Google recommends deploying on top of Substrate, is an event-log system: single-writer sessions, durable execution state, client catch-up by last seen sequence number (google/ax). Semantically that is the Electric Agents shape. Substantively it is not a seam chronicle can plug into: AX's log is an embedded SQLite file behind a Go interface, not a networked log service, so substituting a Durable Streams server for it would be unsupported surgery rather than configuration. The ecosystems do not interoperate today. The lesson is that when the company that built the compute layer needed agent semantics, it reached for a log. primary

One fairness note, because Electric's marketing invites a misreading. Electric's essay against this architecture, "Managed agents don't belong in sandboxes. They belong in functions" (serverless agents), is a position about where the agent loop runs. It is not a rejection of sandboxes. In June 2026 Electric shipped persistent Docker and E2B sandboxes that reattach by key, and its runners already give entities long-lived hosts. The genuine disagreement between the stacks is narrow: Electric keeps the loop in a stateless function and delegates stateful tools to sandboxes it does not manage, while Substrate makes the stateful machine itself the thing that sleeps and wakes. Everything else is layering. primary

What remains genuinely unshipped on the Electric side is the fleet half of compute: worker pools, ordered dispatch fallback, and live handoff are deferred in the runners RFC, and v1 dispatch policy is exactly one target, immutable after spawn (RFC #4299). That deferred list is precisely where Substrate is strongest, which is what makes the hybrid interesting rather than redundant. primary

§The borrow list: Substrate ideas on durable-streams rails

The two systems join along a clean line because each one's wake story is the other's gap. Electric has seven wake sources and no compute. Substrate has compute and two wake sources. A durable-streams control plane that drives a checkpointing sandbox tier uses each side for the thing it owns. The table ranks the ideas by what they cost to adopt.

Substrate ideaOn the Electric / chronicle stackStatus
Low-latency placement state outside the config plane. Actor and worker records in Redis with per-actor TTL locks, because the config store is too slow for the hot path. Already the shape of chronicle's subscription control plane: claims, leases, and generation fences in Redis, with the same lesson learned from the other direction during the horizontal-scale work. have
Hold the request while the target wakes. The Envoy gateway parks an inbound request, resumes the actor, then forwards. Chronicle already parks readers in long-polls and holds subscription deliveries through claim and ack. The pattern extends to holding a wake until a sandbox reports ready. have, partial
Golden snapshots. Run setup once per template version, snapshot after readiness, start every instance from the image. The same move as Amp's 24-hour setup snapshot in the orbs case study. Adopt it in whatever provisions sandboxes for entities: a base image keyed to the entity type, cut after .agents/setup, refreshed per template version. build
Two-tier pause and suspend. Short-idle snapshots stay on the node and resume locally. Long-idle snapshots go to object storage and resume anywhere. This is the missing design for the orbs build-list item "warm workspace rehydration", with the tier decision keyed to how long an entity has been idle. A lease-holding runner keeps its workspace on short idle and archives it on long idle. build
Identity by bind mount, not env var. Anything frozen into a base image must not include instance identity or secrets. A posture rule for any golden-image scheme above. Amp's resume hook and Electric's credentials-never-in-the-log rule already point the same way. note
A checkpointing sandbox tier as the entity's hands. Entities keep their log, loop, and wake sources. The sandbox an entity leases is a Substrate-class actor whose warm state survives wakes. Integration is mechanical on the Electric side: a named sandbox profile whose factory resolves to the pool, or a runner fronting it. A chronicle wake becomes a ResumeActor call. But Substrate today has no fork, unimplemented snapshot GC, restores pinned to matching kernel versions, and no measured latency under load, so this tier is a spike to prototype, not a dependency to take. wait

🔗 Chronicle note

The hybrid asks chronicle for nothing new. The wake that resumes a sandbox is an ordinary §6 to §7 subscription delivery, signed and fenced exactly as today, pointed at an adapter instead of directly at a handler. Chronicle's claim, lease, and generation machinery already provides what Substrate's ateapi built from scratch on Redis: single-holder wakes with fencing against stale holders. What the hybrid adds is entirely on the compute side, and the log's cache rule from the anatomy section governs it cleanly. A snapshot is legitimate exactly while deleting it costs time, not truth. Substrate's own unresolved snapshot-invalidation question says the same thing from the other side.

§Extend or fork, mechanically

The question splits across three layers, and the answer is the same at each one, for different reasons.

The Durable Streams protocol invites supersets. The spec's extensibility section is explicit: "Extensions SHOULD be pure supersets of the base protocol... Implementations MAY extend the protocol with additional query parameters, headers, or response fields... Extensions MUST NOT break base protocol semantics" (PROTOCOL.md §11). Authentication is explicitly out of scope, which makes it a sanctioned extension point, and URL structure outside the reserved __ds prefix is implementation-defined. The conformance suite enforces the same posture from the outside. It is a black-box runner pointed at a base URL, it contains no test that rejects supersets, and it actively requires servers to ignore unknown query parameters. Chronicle passes it at 332 of 332 with subscriptions enabled. A fork would forfeit that claim and the ten client SDKs that talk to any conforming server by URL alone. primary

Chronicle's own history is the proof. The one agent-scale capability the base protocol lacks, claim granularity finer than one lease per subscription, is the thing that collapsed the load test at 12 replicas while every tier sat under 12% CPU. Chronicle built it as a pure superset: sharded claims exist in the store layer, shard zero is byte-identical to the unsharded path, and a client can get the benefit today with no chronicle change at all by registering sharded subscription ids. Mechanical follow-ups remain documented, since the recovery sweep and subscription deletion do not yet cover the extra shards, but the safety half is complete and gated. No fork was needed for the hardest extension the project has yet required. The upstream invitation goes the same direction. The protocol authors wrote that they want "a spec with many implementations, not a single codebase", named Go among the languages and Redis among the storage backends they want, and offered to link third-party implementations from the main repo (announcement). AnyCable's independent read-only Go implementation is already linked from the upstream README, so the precedent exists. primary

The agents layer is extended at wire contracts, not by patching its code. Electric's runtime swaps its Durable Streams backend by environment variable, which is how chronicle became its backend with configuration only. Its sanctioned extension points are the entity-type registration call, the wake notification shape, dispatch policies, sandbox profiles, and tools. Forking the TypeScript itself would mean re-tracking a codebase that went from 0.4.0 to 0.6.3 in ten days with publicly removed APIs. The wire contracts are the stable surface. The package internals are not. primary

Capability chronicle may wantPath without a fork
Finer claim granularity on the wire (a shard field on claim/ack) Ship as a §11 superset now. Propose upstream as an optional extension in parallel. The client-side sharded-id convention already works with zero protocol change.
The agents runtime registering finer subscriptions (the client half of the fence-storm fix) A configuration-level change in Electric's runtime. The tracking issue drafted in chronicle's design doc was never filed upstream, so this is an open action, not a blocked one.
Sandbox-tier wakes (the hybrid's adapter) An ordinary webhook subscription target. No protocol change of any kind.
Auth, quotas, tenancy Explicitly out of protocol scope, so implementation-defined by design.

The honest fork pressure is governance, and it should be stated rather than waved at. The spec is a draft authored and copyrighted by ElectricSQL. The repo has no governance document, no contributing guide, and no CLA, and roughly 98% of commits come from Electric staff and their coding agents. There is no process by which anyone outside Electric can force a spec change, and the promised third-party server registry page currently returns a 404. Chronicle appears nowhere upstream. If chronicle ever needed a change to base wire semantics, it would land at Electric's discretion or not at all, and that is the scenario in which a fork becomes a real conversation. Nothing on chronicle's roadmap is in that category. Everything it needs is additive, and everything additive is sanctioned. primary

💡 The verdict, restated once

Extend. The protocol sanctions supersets, the conformance suite tolerates them, the licenses are permissive throughout, the upstream authors invite exactly this implementation, and chronicle's hardest extension to date was already delivered additively. Keep the fork triggers written down and check them on each upstream release: a base wire-semantics change chronicle cannot absorb, a license change, or upstream rejection of superset conformance claims. None has occurred. The cost of this position is real but bounded: chronicle tracks a spec it does not control, on Electric's timetable, with a §6 to §7 subscription layer that upstream's own servers implement unevenly. That last point cuts both ways, since full subscription coverage is chronicle's differentiator.

§Actions this evaluation produces

  1. File the claim-granularity issue upstream. The fence-storm finding and the client-half fix drafted in chronicle's design docs have zero upstream visibility today. Searches for chronicle in both Electric repos return nothing. Until that issue exists, no extend-vs-fork judgment about upstream receptiveness has actually been tested.
  2. Ask for the README link. Chronicle passes the full conformance suite including subscriptions. The upstream blog offered to link implementations, and AnyCable got its link for a read-only server. This is a Discord message and a small PR.
  3. Propose the shard field as a spec extension. A short PROTOCOL.md §11 superset proposal, an optional integer on claim and ack. Acceptance is nice. Rejection costs nothing, since the superset and the client-side convention both work regardless.
  4. Adopt the free ideas now. Golden images per entity type and two-tier idle for runner workspaces need no new dependencies and directly shrink the orbs build list.
  5. Prototype the Substrate tier as a spike, behind the adapter. One entity type whose sandbox profile resolves to a checkpointing pool, woken by an ordinary chronicle webhook. Measure activation latency and snapshot cost yourself, because nobody has published either. Treat snapshots as cache, since a runtime upgrade can invalidate them. Do not take Substrate as a dependency before it has garbage collection, a ratified governance doc, and measured latencies.
  6. Watch AX for a networked log seam. If Agent Executor ever accepts a pluggable event-log backend, a Durable Streams server becomes a candidate implementation of it, and the two ecosystems would meet at a real interface instead of an analogy.
