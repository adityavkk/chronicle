How to Do Things

The developer surface, in the order you'd actually use it. Sections 0–2 get one agent chatting; 3–5 add the coordination primitives; 6 is the design idiom that makes multi-agent systems reliable; 7–9 round out the toolkit. Code follows the official walkthrough and quickstart, condensed.

0Wire up an app

Dev infrastructure is one command — it runs Postgres, Electric, and the agents server (with an embedded Durable Streams server and web UI) in Docker on port 4437: 

pnpx electric-ax@latest agents start     # clean runtime, define your own types
# or: agents quickstart                  # includes built-in horton + worker agents

Your app needs four things — a registry, a runtime handler, a webhook route, and a one-time type registration:

src/index.ts — any TS framework (Hono shown)
import { createEntityRegistry, createRuntimeHandler } from '@electric-ax/agents-runtime'

const registry = createEntityRegistry()
// … registry.define(…) — next section …

const runtime = createRuntimeHandler({
  baseUrl: 'http://localhost:4437',                    // the agents server
  serveEndpoint: 'http://localhost:3000/electric-agents', // ← where IT calls YOU
  registry,
})

app.post('/electric-agents', (c) => runtime.handleWebhookRequest(c.req.raw))

serve({ fetch: app.fetch, port: 3000 }, () => {
  runtime.registerTypes().catch(console.error)         // announce types + webhook URL
})

That's the entire integration seam. Everything else in this part happens inside registry.define().

1Define an entity type

registry.define('assistant', {
  description: 'A general-purpose AI assistant',

  // optional contracts, validated by the server on spawn / send:
  creationSchema: z.object({ systemPrompt: z.string().optional() }),
  inboxSchemas: { 'pr-opened': z.object({ diff: z.string() }) },

  async handler(ctx) {
    ctx.useAgent({
      systemPrompt: ctx.args.systemPrompt ?? 'You are a helpful assistant.',
      model: 'claude-sonnet-4-6',
      tools: [],
    })
    await ctx.agent.run()
  },
})

Spawn instances from anywhere — the web UI, the CLI (electric-ax agents spawn assistant a1), the HTTP API (PUT /_electric/entities/assistant/a1), or another entity (ctx.spawn). Message it and the handler wakes.

2Give it an LLM — and real tools

useAgent + agent.run() is the whole LLM story (§5 of Part 1). Tools are plain objects: a TypeBox/Zod parameter schema and an execute function. The convention worth internalizing: tools that change the world should also record what they did in durable state — that's what makes them auditable and makes control flow possible later. 

function createSpawnAssistantTool(ctx) {
  return {
    name: 'spawn_assistant',
    description: 'Spawn an assistant sub-agent to perform a task.',
    parameters: Type.Object({ task: Type.String() }),
    execute: async (_id, { task }) => {
      const { entityUrl } = await ctx.spawn('assistant', genId(), {},
        { initialMessage: task, wake: { on: 'runFinished', includeResponse: true } })
      return {
        content: [{ type: 'text', text: `Assistant dispatched at ${entityUrl}.` }],
        details: { entityUrl },
        terminate: true,      // end this run after the tool call — child will wake us
      }
    },
  }
}
💡 Why spawn inside a tool call, not in handler code?

The walkthrough demonstrates this beautifully: spawn imperatively in the handler and the LLM later has no idea the child exists — the spawn never entered its context. Spawn via a tool call and it's on the timeline, so the model can reason about it ("who reversed this message? — I spawned an assistant to do it"). Rule of thumb: actions the LLM should know about must happen as tool calls; actions it must not screw up should happen in handler code.

3Route on wakes

Every handler's first job is a small dispatch on what woke it:

async handler(ctx, wake) {
  if (wake.type === 'inbox') {
    // a message: from a user, another entity, or a webhook source
    // wake.payload — validated against inboxSchemas if declared
  } else {                        // wake.type === 'wake'
    const p = wake.payload
    if (p?.finished_child) { /* a spawned child completed/failed — p.finished_child.response */ }
    if (p?.changes?.length) { /* observed collections changed — [{collection, kind, key}] */ }
    if (p?.timeout)         { /* a wake registration's timeoutMs elapsed with no event */ }
    // cron ticks arrive here too; scheduled future_sends arrive as 'inbox'
  }
}

Handlers end three ways: await ctx.agent.run() (the LLM's reply is the outcome), ctx.replyText('…') (a synthetic reply without an LLM), or ctx.sleep() (this wake needs nothing — extremely common, and free). Not reacting is a first-class outcome.

4Keep durable state

Declare collections on the type; get typed reads and log-backed writes on ctx.state:

registry.define('judge', {
  state: {
    debate: { schema: passthrough<Debate>(), primaryKey: 'key' },
  },
  async handler(ctx, wake) {
    ctx.state.debate.insert({ key: 'current', phase: 'arguing', arguments: {} })
    ctx.state.debate.update('current', d => { d.phase = 'critiquing' })  // Immer-style draft
    const debate = ctx.state.debate.get('current')
    ctx.state.debate.delete('current')
  },
})

Remember what these writes are (Part 2 §7): change events appended to the entity's stream. Which buys you:

  • Durability — state survives crashes, redeploys, months of sleep;
  • History — every state the entity has ever been in is in the log;
  • Observability — any other entity or UI can watch this state live, with no API on your part.

For state shared between entities, one entity creates a standalone stream-backed DB and others attach to it — the blackboard: 

if (ctx.firstWake) ctx.mkdb('board-1', boardSchema)        // create (throws if exists)
const board = await ctx.observe(db('board-1', boardSchema)) // attach — any entity, any wake
board.findings.insert({ key: 'f-1', domain: 'security', finding: 'XSS found' })

5Spawn, send, observe

The complete inter-entity vocabulary is three verbs (plus fork):

VerbSignatureSemantics
spawn ctx.spawn(type, id, args?, opts?) Create a child entity. opts.initialMessage seeds its inbox; opts.wake registers when to wake me about it — { on: 'runFinished', includeResponse: true } or { on: 'change', collections?, ops?, debounceMs? }. Returns an EntityHandle (url, status, its db).
send ctx.send(entityUrl, payload, opts?) Append a message to any entity's inbox by URL. opts.afterMs delays delivery (durable timer). Fire-and-forget; delivery modes (immediate/queued/steer) are the receiver's policy.
observe ctx.observe(entity(url) | db(id, schema) | …, opts?) Attach to a stream you didn't create: another entity, a shared DB, a webhook source, or a synced Postgres table. Returns a handle whose .db.collections you can query; opts.wake subscribes you to its changes.
fork ctx.fork(url, id) / ctx.forkSelf(id) Branch a new entity from an existing one's history at a point — cheap what-if copies of a whole agent (streams fork without rewriting).
⚠ The one thing you can't do

There is deliberately no "spawn and await the result in the same wake". You spawn, you return (sleep), and the child's completion arrives as a new wake with finished_child in the payload. This is the price — and the point — of scale-to-zero: no compute anywhere is blocked waiting. Any "wait for N children" logic is durable state + a gate (next section).

observe deserves emphasis. Because every entity's state is a readable stream, agents don't need to define APIs for each other. A parent doesn't ask the judge "are you done?" — it reads the judge's debate collection directly: 

const judge = await ctx.observe(entity(finishedChild.url))
const debate = judge.db.collections.debate.get('current')
if (debate?.phase !== 'done') return ctx.sleep()

6Hybrid control flow — the design idiom

The walkthrough's arc: a judge agent coordinating a two-phase debate by prompt alone ("wait for both arguments… don't hallucinate…") works, mostly. Then it doesn't — the model responds to partial results or invents the debate. The fix isn't a better prompt; it's moving the control flow into durable state and keeping the LLM for the judgment calls:

Over a full debate the judge is woken five times and runs the LLM twice:

The debate cannot finish early, the model cannot hallucinate the results, and three of five wakes cost no tokens at all. In the official framing: let the LLM interpret, decide and be creative when it needs to; use durable state to make the control flow deterministic when you can. Everything else in this part is machinery for expressing that split well.

7The seven coordination patterns

The runtime ships a design skill (skills/designing-entities) cataloguing seven topologies, with trigger phrases for choosing. Compressed:

1 · Single agent
One entity, one LLM loop, tools, optional state. No spawn/observe/send at all. The default until a coordination signal appears.
2 · Manager–worker
Parent spawns a fixed, named set of specialists in parallel, gates on all finished_child wakes arriving, then synthesizes. "Give me economic, political and social takes."
3 · Dispatcher
Classify each incoming request (LLM decides), route to the right specialist type, spawn on demand. A router with durable continuations.
4 · Pipeline
Known sequential stages; a state-machine transition() advances one stage per child completion, passing output forward as the next initialMessage.
5 · Map-reduce
Split input into N chunks (N varies per input), spawn all workers in one loop, gate on all done, reduce. Fan-out without blocking anything.
6 · Blackboard
Participants coordinate through a shared StreamDB (mkdb + observe(db(…))) instead of messages — collaborative docs, debates, research boards. React with wake: { on: 'change' }.
7 · Reactive observers
An entity that never spawns — it watches another entity's stream (observe(entity(url))) and reacts: monitors, summarizers, alerting, dashboards.

They compose: a blackboard under a manager-worker; a dispatcher whose specialists are pipelines. The topology is always the same three verbs plus state gates — the patterns are shapes, not APIs.

8Tools, MCP, sandboxing, schedules, webhooks

  • Built-in tool factories (runtime): bash, read/write/edit (all sandbox-backed), web_search, fetch_url, send (message another entity), schedule tools (cron + delayed sends), webhook-source tools. Pass ...ctx.electricTools for whatever the host wired in.
  • MCP: @electric-ax/agents-mcp provides a registry, transports and OAuth bridges so agents can consume Model Context Protocol servers as tool sources.
  • Sandboxes: each wake gets ctx.sandbox — unrestricted (host, trusted dev default), docker (digest-pinned image, resource limits, optional gVisor, network policy), or remote (e2b microVMs). Selected per spawn via profiles; write-paths are containment-checked on every provider. LLM tool calls (bash, file ops, fetch_url) execute inside it.
  • Schedules: entities can hold durable cron schedules and one-shot future sends (PUT /_electric/entities/:type/:id/schedules/:sid, or the schedule tools) — the server's scheduler wakes them; no process anywhere holds a timer.
  • Webhook sources: register external webhooks (GitHub, Stripe, …) as observable sources; events land as wakes with payload.type === 'webhook_source_wake'.
  • Signals: POSIX-flavored lifecycle control per entity — SIGINT abort current wake, SIGSTOP/SIGCONT pause/resume, SIGTERM graceful stop, SIGKILL hard kill. electric-ax agents signal /judge/d7 SIGINT.

9Build the UI

The UI story is the same story: subscribe to the entity's stream, materialize, render. No chat-completion endpoints, no bespoke websocket protocol: 

const client = createAgentsClient({ baseUrl })
const db = await client.observe(entity('/assistant/a1'))   // SSE-tailed StreamDB

function Chat() {
  const chat = useChat(db)          // assembles textDeltas → messages, live
  return chat.runs.map(run =>
    run.texts.map(t => <MessageBubble text={t.text} />))
  // chat.state === 'working' → show the streaming cursor
}

Sending a message is an HTTP POST (/_electric/entities/assistant/a1/send). Token streaming falls out of textDeltas arriving as events. And because it's TanStack DB underneath, arbitrary live queries over the timeline — filter tool calls, join runs to steps for token accounting, watch a custom collection — are ordinary useLiveQuery calls. The bundled web UI (localhost:4437) is exactly this, generalized: spawn any type, watch any entity's timeline, expand child trees.
